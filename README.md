# 全能本地播放器

基于 **.NET 8 + Windows Forms + LibVLCSharp** 的本地音视频播放器，经典 Windows 窗体界面。

播放内核使用 VLC（libvlc 3.0.23），因此格式支持范围与 VLC 基本一致：MP4 / MKV / AVI / MOV / FLV / WebM / TS / RMVB……
MP3 / FLAC / APE / WAV / AAC / M4A / OGG / Opus / WMA…… 以及外挂字幕、多音轨和网络串流。

> 第一次接触这个程序？先读 **[docs/介绍.md](docs/介绍.md)**——那一篇是给人看的入口
> （它是什么、在意的几件事、五分钟上手、功能总览、已知限制）。本文是完整参考手册。

> **[docs/维护手册.md](docs/维护手册.md)**。

## 功能

**播放**
- 打开文件 / 文件夹（递归扫描）/ 网络串流（http、https、rtsp、rtmp、udp 等）
- 播放、暂停、停止、上一个、下一个、快进 / 快退 5 秒
- 拖动进度条定位，音量调节与静音——拖动期间"当前时间"显示的是**你要跳到的位置**
  （松手才真正跳转），按住拖到进度条外面也仍然跟手
- 倍速播放：0.5× / 0.75× / 1.0× / 1.25× / 1.5× / 2.0×
- 循环模式：不循环 / 单曲循环 / 列表循环；随机播放
- **A-B 循环**（`播放 → A-B 循环`）：`把 A 点设在当前时间` / `把 B 点设在当前时间` / `清除 A-B`。
  子菜单第一行随时写着当前 A/B（精确到 0.1 秒），两个设点动作的文字里带着"当前时间是多少"。
  播放越过 B 点就跳回 A 点；**A 不早于 B、B 不晚于 A 都会被如实拒绝并说明原因**
  （不偷偷挪成"B 点前一点"——那样设的就不是你点的那一刻）。
  换歌或停止时清除；同一首重新起播（例如下面那个音量均衡开关）不会清掉
- **音量均衡（normalize）**（`播放 → 音量均衡（normalize）`，默认关）：给媒体挂 libvlc 的
  `normvol` 音频滤镜，把忽大忽小的音量拉平。它是**媒体级**滤镜，所以切换时会**重载当前这一首**
  并从头开始播（状态栏说明「已从头开始重播以应用」）——不会假装"已经生效"。
  代价是动态会被压平一些，所以默认关
- 画面比例切换：默认 / 16:9 / 4:3 / 1.85:1 / 2.35:1 / 原始比例
- 全屏播放（工具栏自动隐藏，双击画面或 F11 切换）
- 截取当前画面保存为 PNG

**播放列表**
- 列表视图显示序号、标题、时长；时长在后台自动扫描补全
- 列表标题汇总**整个播放列表的总时长**，随扫描进度实时更新
  （VLC 本体没有这个功能，官方 [2012 年的需求](https://mailman.videolan.org/pipermail/vlc-devel/2012-November/090924.html) 至今未实现，
  社区要靠 [第三方扩展](https://github.com/bentrevor/vlc-total-playlist-duration-extension) 才能看到）
- 添加、移除、清空、上移、下移，支持多选与右键菜单
- **搜索过滤**：空格分隔多个关键字（与关系），在标题和完整路径里匹配；
  筛选时标题改为汇总筛选结果（`筛选 12/187 项 · 总计 …`）
- **排序**：按名称 / 路径 / 时长升降序，随时可恢复原始顺序；**表头也能点**——
  点一下按它排、再点一下反向、第三下回到原始顺序，点 `#` 那一列直接回原始顺序，
  表头上的 ↑ / ↓ 与右键菜单里的勾选永远一致
- **拖动换位**：直接把列表项拖到想要的位置，拖动时有插入位置提示
- **「下一首播放」队列**（列表右键 / `播放` 菜单各两项：`下一首播放`、`清空下一首队列`）：
  把选中的项排到当前这首后面（最多 20 条，重复入队去重），排进队的行标题前显示 `▶`。
  当前这首**自然播完**时先播队首，**列表的当前项不动**（插播完再回到列表原来的位置继续）；
  队列空了就照旧播列表的下一项。状态栏会说明队列里还剩几项。
  队列只在内存里、不落盘——关掉程序就没了（下次打开时那几首多半已经不想插播了）
- 在资源管理器中定位文件、复制完整路径
- **播放列表一个菜单管到底**（`文件 → 播放列表`）：自己常用的存进**歌单库**，
  外来的 / 要外发的走 **m3u 文件**——同一处，中间用分隔线分开
  - `Ctrl+S` 保存当前列表为歌单（进歌单库）、`Ctrl+L` 从 m3u 文件**追加**、
    `Ctrl+Shift+S` **另存为** m3u 文件
  - **追加和替换是两个菜单项**（「从 m3u 文件追加…」/「从 m3u 文件替换当前列表…」）：
    同一件事两种语义，只写「载入」没人分得清是哪种；替换前按和歌单载入同一套规则问一句
  - **歌单库（多个命名播放列表）**：把当前列表命名存下来，在多个歌单之间随时切换
    - 一个歌单一个**标准 m3u8 文件**，放在 `数据目录\播放列表\` 下——资源管理器里看得见、
      能拷给别人、能用别的播放器打开，出问题用记事本就能查
    - **新建空歌单**（菜单里的「新建空歌单…」，或歌单窗口里的「新建空歌单…」）：
      起个名字就得到一张白纸并切过去，接着往里添加文件即可。
      同名**不会覆盖**（覆盖别人的歌单等于删他的东西），换个名字就行；
      切过去要清空当前播放列表，所以会先问一句
    - **歌单窗口**（文件 → 播放列表 → 打开歌单窗口，或播放列表工具条的「歌单」按钮）
      一次列出全部歌单：名字、曲目数、最后修改时间；可载入（替换当前列表）、追加、
      新建、重命名、删除、打开歌单文件夹；外部的 m3u / m3u8 直接拖进窗口就收进歌单库
    - **拖动一行就能调整歌单顺序**（带插入位置提示）：拖完立即写进歌单目录下的
      `歌单顺序.txt`（一行一个歌单名），窗口和「文件 → 播放列表」菜单里都按这个顺序列
      ——菜单只列得出前二十个，所以这个顺序是有用的。**删掉那个 txt 就回到按名字排**
      （新导入 / 新建的、以及顺序文件里已经没有的名字，都跟在后面按名字自然排）
    - **歌单窗口支持多选**（`Ctrl` / `Shift`）：选了两份以上时，「载入 / 追加 / 重命名」会点不动
      （它们是"针对一份歌单"的动作），而「删除」按钮会写成 `删除选中的 3 个`——
      **一次确认、逐个删**，删不掉的会指名道姓（`「X」：删除失败：…`）；
      删掉的正好是当前歌单时，主窗体的关联跟着断开（只是不再对应歌单，列表还在）
    - **批量重命名**（多选之后那一个按钮）：给一个基名，选中的几份按**窗口里的显示顺序**
      依次改成 `基名 1` / `基名 2` …；内容、歌单顺序的位置、当前歌单关联都跟着走。
      名字非法或撞上别的歌单时**先挡住、一个文件都不动**（批量改到一半最难受）
    - 菜单（文件菜单 / 播放列表右键菜单 / 工具栏按钮）里也直接列出手上的歌单，点一下切过去；
      超过 20 个时去窗口里选
    - **不会自动改用户的歌单**：改了列表只在标题上标 `【歌单名·未保存】`，
      只有点「覆盖保存」才落盘；载入别的歌单前会问一句（先保存 / 直接换 / 取消）
    - 歌单里文件已经不在了的条目会**如实报数**（`另外 2 项文件已经不在了，已跳过`），
      不像从 m3u 文件追加那样静默少几首
  - **m3u 文件（外来的 / 外发的）**：写出去时同目录下用相对路径，整个文件夹搬走也认得；
    用一个 m3u **替换**当前列表时，当前歌单的关联留着但内容标成「未保存」——
    想把它收进歌单库接着点「覆盖保存」就行，不想要就点「重新载入」退回原来那份
- 拖放文件或文件夹到窗口即可添加；**拖一个 m3u / m3u8 进来 = 把里面的条目追加进列表**
  （和 `Ctrl+L` 完全同一条路。它本身不是媒体文件，交给 VLC 只会得到一条"无法播放"）
- 无法播放的条目会标红并显示原因，自动跳过坏文件

**播放记忆**
- **默认打开就是一张空列表**：`播放 → 启动时恢复上次播放列表` 默认**不勾**——启动时不恢复上次的列表，
  也**不挂上次的「当前歌单」**。为什么连歌单名一起忘掉：一张空列表挂着歌单名，往里加两首再点
  「覆盖保存」，那份歌单就被这两首替换掉了（`覆盖保存` 这个入口本身就是按"当前歌单"给的）。
  **歌单文件一个字节都不动**，想接着上次听，在 `文件 → 播放列表` 里点一下载入即可；
  空着启动时状态栏也会把这件事说一句（`就绪（本次是空列表，可在「文件 → 播放列表」里载入歌单）`）
- 勾上那个开关之后，**下次启动**恢复上次退出时的列表和「当前歌单」关联。
  勾上**只写设置、下次启动才生效**，不会当场把上次的列表塞进来盖掉正在听的东西（状态栏会说明）；
  退出时**照旧记录**这张列表，所以开关打开后拿到的是"上一次关闭时的那份"，不是几周前残留的旧数据
- **从旧版本升上来的话**：开关默认关，所以上次那份列表不会再自己回来（歌单文件一个字节没动，
  `文件 → 播放列表` 里点一下就能载入回去）；而"退出时照旧记录"没变，
  所以关一次程序之后，设置里记的就是这次打开的这张列表了
- **记住每个文件播到哪儿**，下次打开自动从上次的位置继续（切歌、暂停、关闭时都会保存）
- 刚开头 15 秒以内、或已经播到结尾 20 秒以内的，视为不需要续播，下次从头开始
- **恢复了列表时，启动这一步一次磁盘都不查**：列表原样恢复（窗口立刻出来），"文件还在不在"交给
  **后台线程核对**，打不开的那几条在列表里标红并把原因写出来（`上次的列表里有 3 项现在打不开
  （网络盘离线或文件被移走），已经在列表里标出来了`），**不会把条目删掉**——
  网络盘只是暂时离线时，下次挂上还能直接播
- **文件 → 最近播放**：列出最近听过的文件，菜单里直接显示各自的续播位置；
  可单独清除所有续播进度，或清空整个历史
- 网络串流不记录（地址没有稳定标识），启动核对也不会去查它

**歌词与封面（右侧侧栏）**
- 右侧可折叠侧栏，顶部三个标签：**歌词 / 封面 / 媒体信息**；宽度可拖，整栏可关掉
- 歌词按优先级自动寻找四类来源：
  1. 同目录同名 `.lrc`（也认 `艺术家 - 曲名.lrc`）
  2. **文件内嵌歌词**——FLAC 的 Vorbis comment `LYRICS` / `UNSYNCEDLYRICS`、
     MP3 的 ID3v2 `USLT` 与 `SYLT`、MP4 / M4A 的 `©lyr`
  3. 同目录同名 `.txt`（纯文本兜底）
- 带时间轴的歌词高亮当前行并平滑滚动，**点任意一行直接跳到那一句**；
  **鼠标停在某一行上会弹出这一句对应的时间点**（`时:分:秒`），配合点击跳转不用猜哪句在哪
- **双语歌词**（同一个时间戳的原文 + 翻译）算**同一句**：侧栏里这两行**一起高亮**，
  桌面歌词的**第二行优先放译文**（可在右键菜单里改成总是显示"下一句"）——
  以前只认其中一行，另一行永远轮不到"当前句"
- **歌词字体只能手动导入**（`.ttf` / `.otf` / `.ttc`，可一次选多个，也可以直接拖到桌面歌词窗口上）：
  默认字体、系统已安装字体、自己导入的字体三者里，只有后者能选——
  系统里那几百个字体列出来又长又难找，而桌面歌词要的是用户自己挑过的字体。
  侧栏歌词页与桌面歌词共用同一个字体设置；
  `字体 → 管理已导入的字体…` 里**每一行都用该字体画出它的族名**（族名看不出字形），
  下面还有一行大号样例，选中就能删掉——导入不再是"只进不出"。
  两处歌词用的绘制引擎其实不是一套（GDI+ / GDI），导入的字体**两边都会装上**，
  所以侧栏也会真的跟着换（见「实现要点」里那条踩过的坑）
- 纯文本歌词整段换行显示，可用滚轮浏览
- 自动识别 UTF-8 / UTF-16 / **GBK** 编码的歌词，`[offset:]` 偏移按通行惯例生效
- **歌词时间轴偏移**：歌词和声音差半拍时，把整条时间轴提前 / 延后
  - `视图 → 歌词偏移`（或**在歌词上点右键**、在桌面歌词窗口上点右键、**在托盘菜单里**）：
    `歌词提前 0.5 秒` /
    `歌词延后 0.5 秒` / `偏移归零` / `手动输入偏移…`，快捷键 `Ctrl+]` 提前、`Ctrl+[` 延后；
    菜单上直接写着**当前偏移是多少**，歌词页右上角也常驻一行很淡的 `+1.5s`
    （调完过几天再看歌词，多半想不起来自己动过它）
  - 符号与 LRC 的 `[offset:]` 一致：**正值 = 歌词提前**。菜单和状态栏永远把方向写出来
    （"提前 1.5 秒"/"延后 0.5 秒"），不用去猜正负号；一档 0.5 秒，范围 ±30 秒
  - **按文件记住**（存在 `history.json` 里，和音画 / 字幕延迟同一处）：
    同一首歌的不同版本、不同来源的歌词差得往往不是一个数，下次放这首还是这个偏移
  - 侧栏歌词、桌面歌词、**点歌词跳转**、悬停显示的时间**全都按偏移后的时间走**（只改一处，四处一致）
  - 这首没有歌词、或者歌词是纯文本没有时间轴时，菜单如实**禁用并说明原因**，不会装作能调
- 封面自动读取内嵌图片（ID3 `APIC` / FLAC `PICTURE` / MP4 `covr`），
  没有内嵌图就找同目录的 `cover.jpg` / `folder.jpg` / `front.jpg` / `album.jpg` 等

**在线歌词与封面（LrcAPI）**
- 本地那几处都找不到歌词 / 封面时，按「曲名 + 专辑 + 歌手」去 **LrcAPI**
  （[HisAtri/LrcApi](https://github.com/HisAtri/LrcApi)，一个聚合各家歌词源的服务）上要一份：
  「视图 → 在线歌词与封面」里可以开关自动获取，也能对当前曲目手动要一次
- **服务地址必须自己填**（默认空）：这是要联网的第三方服务，程序不会替你挑一个地址发出去。
  没填的时候什么请求都不发，只在菜单上写「服务地址：未填写（点这里填）」
- **视频不查歌词与封面**：放视频时**一个请求都不发**（自动不查，手动那两项也点不动并写明原因）。
  拿"某某电影.2019.1080p"这种名字去歌词服务里搜，搜回来的多半只是一首同名的歌，
  歌词和画面八竿子打不着；封面同理（画面本身就是封面）。
  本地已有的 `.lrc` / 内嵌封面照旧会用，换回音频立刻恢复
- **支持鉴权**：服务端开了鉴权就填「鉴权密钥」，它作为 `Authorization` 请求头发出去；
  密钥只发给**你填的那台服务**，不会跟着封面图片的地址发给第三方主机（见「实现要点」）
- **两代接口都试**：新版 `/api/v1/lyrics/single`、旧版 `/lyrics`、
  以及批量搜索 `/api/v1/lyrics/advance`；谁的歌词带时间轴就用谁。
  只有纯文本时会去批量结果里挑一条最像的（标题 / 歌手对得上、带时间轴的优先）
- **封面按三条路回退**：搜索结果里附带的 `cover` 字段 → `/api/v1/cover/music|album|artist`
  → 旧版 `/cover`（直接返回图片）。哪条给得出图就用哪条
- **不写盘**：取回来的歌词与封面只在本次运行里用（换回同一首歌不会再联网），
  不会往你的音乐目录里丢 `.lrc` 或封面文件；想离线复用就自己另存一份
- 拿回来之后歌词会进侧栏歌词页与桌面歌词，封面进侧栏封面页，
  并在「媒体信息」里标出来源是 `LrcApi 在线歌词 · 歌名 - 歌手`
- 出问题时会说清楚是哪一种：没填地址 / 需要鉴权 / 没找到 / 连不上 / 封面地址拿到了但下不下来 /
  **服务端自己报的错**（自建实例崩掉时会吐出 Python traceback，
  这里会把那行 `TypeError: ...` 连同状态码一起显示在状态栏）
- 万一你的自建实例"一收到 `Authorization` 就 500"（实试遇到过：Python 端
  `TypeError: string indices must be integers, not 'str'`），程序会**自动去掉鉴权重试一次**
  并在状态栏说明——你要的是歌词，不该替服务端的鉴权 bug 买单

**媒体信息**
- 标题、艺术家、专辑、专辑艺术家、年份、音轨号、流派、备注
- 歌词与封面的来源和体积、文件路径与大小、时长、容器格式
- 采样率、声道数、位深
- **全部轨道清单**：视频轨（编解码器 / 分辨率 / 帧率）、音轨（编解码器 / 采样率 / 声道 / 码率）、字幕轨
- 侧栏窄，放不下的长内容（例如完整路径、编解码器全名）鼠标悬停即可看全

**均衡器**
- 10 段图形均衡器（31 Hz ~ 16 kHz）+ 前置放大，可整体启用 / 关闭
- 内置 VLC 的全套预置（平坦 / 古典 / 摇滚 / 流行 / 重低音 / 现场……），
  曲线数值**直接从 libvlc 读取**，与机器上 VLC 的听感一致，不是凭印象写死的近似值
- 「自定义…」可逐段拖动微调；**没动过的频段保留预置的原始小数**，
  所以"选个预置听"和"自己微调"都不会被无谓地改掉音色
- 设置随配置保存，下次启动自动恢复

**诊断**
- **诊断日志**：内存里留最近 500 条，同时写进 `数据目录\播放器.log`（到 1 MB 自动轮转成 `.1`，不会无限长大）。
  出问题时 `帮助 → 查看日志…` 能直接看到、复制全文，或「打开日志文件」翻更早的
- **不再有"空吞异常"**（只剩日志自己那两处：写日志失败不能再递归记日志）：所有"决定不管这个异常"的地方都写上**为什么可以不管**并记进日志
  （比如"删不掉临时文件就算了，下次会覆盖"），出了问题能在日志里看到那一次
- 未处理异常（界面线程 / 后台线程 / 未观察的 Task 异常）都会先写日志、再弹一句
  "详情已写进日志：<路径>"，而不是关掉对话框后什么线索都不剩
- 时长扫描逐条记录：**哪个文件、解析用了多久、有没有超时**——
  以前界面上只显示"某一项时长未知"，卡在哪儿只能猜
- 不想留记录可以在 `帮助 → 记录诊断日志` 里关掉（关掉后只留内存里的最近若干条）

**章节与音频输出**
- **章节跳转**：MKV / MP4 内嵌章节，菜单里列出全部章节可直接跳，也可上一章 / 下一章
- **音频输出设备切换**：在多个声卡 / 耳机 / HDMI 之间切换，不用去改系统默认设备

**视频工具**（侧栏「视频」页，同时有菜单项与快捷键）
- **音画同步**：音频延迟 ±50 ms、字幕延迟 ±250 ms 实时微调，状态栏与信息页显示当前偏移量；
  **按文件记住**——同一个片源下次打开自动恢复，不用每次重调
- **去隔行**：自动 / 混合 / Bob / 线性 / Yadif / Yadif 2x / IVTC / 荧光，修老 DVD 与电视录制里的横纹
- **画面旋转 / 翻转**（`视图 → 画面旋转`）：不旋转 / 顺时针 90° / 180°（上下颠倒）/ 逆时针 90° /
  水平翻转（左右镜像）/ 垂直翻转（上下镜像）。**按文件记住**——竖屏手机拍的、或者元数据不对的片子，
  下次打开还是你调好的那个方向；切换会重载当前这一首，但**停在原来的位置**。
  只转画面本身（窗口比例、字幕、桌面歌词都不跟着转）；音频文件时整组点不动并说明原因
- **逐帧步进**：暂停时前进 / 后退一帧（`E` / `Shift+E`），另有「跳转到时间码」可按
  `秒`、`分:秒`、`时:分:秒.毫秒` 精确定位
- 逐帧的两个方向都是"按帧长精确定位"实现的：libvlc 的 `NextFrame()` 在本项目里
  实试完全不生效（详见下文「实现要点」），所以没有用它

**窗口布局**
- 三栏布局：**视频 | 侧栏 | 播放列表**，两条分隔条各自独立，宽度互不影响
- **侧栏和播放列表互不牵连**：关掉播放列表不会再连带把侧栏一起收走，反之亦然
- **两者都能脱离主窗口**：「视图 → 侧栏分离为悬浮窗」「视图 → 播放列表分离为独立窗口」。
  分离出来的窗口可自由摆放、能拖到第二块屏幕，位置和大小会记住；
  点它的关闭按钮就自动归位，不用去菜单里找
- **悬浮窗可以吸附在主窗口边上**：把它拖到主窗口任意一条边附近就会自动贴齐，
  贴住之后**跟着主窗口一起移动 / 缩放**（像 Winamp 那样挂在旁边）；
  拖开足够远就恢复自由摆放。四条边都支持，按距离自动挑最近的一条
- 分离出来的窗口归主窗口所有，所以总会浮在主窗口之上——侧栏可以叠在画面上看
- 全屏时两者都会自动收起，退出全屏按原样放回

**桌面歌词**
- 「视图 → 桌面歌词 → 启用桌面歌词」或 `Ctrl+D` 打开一个无边框、置顶的小窗口，
  只显示**当前这一句 + 下一句**，盖在任何程序之上，主界面缩进托盘也照样看得见
- **背景完全透明**：只有字本身有像素，屏幕上不占地方；字外面有一圈深色描边，
  所以在白底网页、亮画面上也能看清（不靠背景板）
- **鼠标停到歌词上会铺出一块半透明背景**（圆角），一眼就能看出"这块可以抓"；
  鼠标移开又恢复全透明，拖动过程中这块背景一直留着
- **窗口范围内随便哪个点都抓得住**：边距和两行字之间的空隙也算（否则用户按在字缝里
  就会觉得"移动不了"）。要完全穿透到下面的程序，用「锁定」
- **外观调节是一个对话框**：菜单里那一项直接写着当前值（`外观（字号 30 磅 · 浓度 88%）…`），
  点开是两条滑块（字号 12~96、浓度 20%~100%），**边拖边改真的歌词窗口**——
  屏幕上的歌词就是预览，不用"点一下、看一眼、再点一下"（以前从 30 磅调到 60 磅要按 15 次菜单）
- **字体只能自己导入**：`.ttf` / `.otf` / `.ttc`，选「导入字体文件…」可以**一次选多个**，
  也可以**直接把字体文件拖到歌词窗口上**；它会复制进数据目录并立刻生效，原文件不会被占用；
  下次启动自动装回来
- **字体管理**（`字体 → 管理已导入的字体…`）：一行一个导入的字体文件，
  **每行都用该文件里的字体画出它的名字**（只看族名是看不出字形的），下面还有一行大号样例
  （中英数都有，顺便能看出这个字体认不认中文）；选中就能删掉，
  删掉当前在用的那一个会自动退回默认字体
- **跟着播放进度自动换句**；前奏（第一句还没开始）和间奏（空行）显示 `♪`
- 这个曲目没有带时间轴的歌词时，退而显示 `♪ + 曲名`——不装作有歌词，
  但也不会留一个空框在屏幕上
- 鼠标左键**抓字拖动**（背景透明，没有别的地方可抓），宽度跟着文字自动伸缩（不用去拖边框），
  位置、字号、文字浓度、配色、字体、锁定状态都会记住
- 下面有一条**控制条**：**播放 / 暂停、上一首、下一首、停止**（和托盘菜单是同一批命令）。
  鼠标没停在这块上时它画得很淡、停上来才清楚；**锁定（鼠标穿透）时它整个不显示**——
  那时候按钮点不到，画出来只会误导；不想要它可以在菜单里关掉。
  另外 **双击歌词本身 = 播放 / 暂停**（不占版面，也不用先解锁）
- 右键菜单（或「视图 → 桌面歌词」子菜单）：显示下一句 / **有翻译时第二行显示翻译** /
  **显示控制条（播放 / 上一首 / 下一首 / 停止）** / 锁定 /
  外观（字号 + 浓度）/
  放大缩小字号 / 提高降低不透明度 / 字体（默认 / 导入字体文件… / 管理已导入的字体… /
  已导入的字体）/ 文字颜色（跟随主题 / 白 / 暖黄 / 青 / 绿 / 粉）/ 居中显示
- **锁定 = 鼠标穿透**：锁上之后这个窗口在鼠标眼里就不存在了，点击会落到下面的程序上
  （全屏看视频、玩游戏时不挡操作）。锁定的那一刻会弹一次托盘气泡，
  把出口说清楚：**`Ctrl+Alt+D`（全局热键，任何程序里都有效）**、
  托盘图标右键 →「桌面歌词」子菜单、或「视图 → 桌面歌词」
- **托盘里的「桌面歌词」是一整套子菜单**（启用 / 锁定 / 外观 / 字号 / 浓度 / 字体 / 颜色 /
  居中），不是只有一个开关：主界面缩在托盘里看片时，这里是唯一能操作歌词的地方
- **不抢焦点、不进 Alt+Tab**：它是工具窗口且带 `WS_EX_NOACTIVATE`，
  点它、弹它都不会把焦点从正在看的视频或游戏上抢走
- **全屏时不会像侧栏那样被收起来**——它的用处恰恰是"主界面藏起来也能看"；
  进入全屏时会把它重新提到最上层，免得被同样置顶的全屏画面盖住
- 屏幕分辨率或显示器布局变了也不会跑到屏幕外：摆放、拖动、改字号之后都会钳回工作区

**系统集成**
- **单实例**：从"打开方式"或命令行再次启动时，复用已经打开的窗口，
  新传入的文件直接加进列表并开始播放，不会开出第二个窗口
- **系统托盘**：托盘图标常驻，菜单可直接播放 / 暂停 / **停止** / 上一首 / 下一首 / 显示主界面 /
  桌面歌词开关 / **歌词偏移**（提前 / 延后 / 归零 / 手动输入）/ 退出，双击图标恢复窗口；
  托盘提示跟随当前曲目。桌面歌词一锁定，右键就点不到了，所以**托盘这一份是完整的一套**
- **全局媒体键**：程序在后台时键盘上的 ⏯⏭⏮ 依然有效（可在「播放」菜单里关闭）；
  媒体键是**独占资源**，被别的播放器占用时注册会失败——这时会**说清是哪几个键没注册上**
  （`全局媒体键有 1 个没注册上：下一首（可能已被其它播放器占用；这几个键只在前台有效）`），
  以前只报"成功几个"，那一个键按下去没反应却完全看不出来
- **任务栏缩略图按钮**：鼠标悬停任务栏图标，预览面板上直接有上一个 / 播放暂停 / 下一个
- **系统媒体控件（SMTC）**：`Win` 键调出的音量弹窗与锁屏界面上显示当前这一首的**曲名 / 歌手**、
  **封面**、播放状态与进度条，并且带**播放 / 暂停 / 停止 / 上一个 / 下一个**那几个按钮
  （1.4.0 起；封面优先用文件里的**内嵌图**，没有就用**同目录的 `cover.jpg` / `folder.jpg`** 这类外挂图，
  与侧栏封面同一份判定）。1.3.0 那版只有"显示"、没有按钮与封面——原因与改法见下文
  「实现要点 · 系统媒体控件的 WinRT 互操作」。媒体键那条路不受影响，照旧好用。
  老系统或策略禁掉时**安静降级**（记一条日志，界面上什么都不说）。

**字幕与音轨**
- 自动加载同名字幕，也可手动加载 srt / ass / ssa / sub / idx / vtt / smi 等
- 字幕轨道与音轨切换菜单，可关闭字幕

**主题**
- 5 套内置主题：跟随系统 / 浅色 / 深色 / OLED 纯黑 / VLC 橙
- 「视图 → 主题」即时切换，不用重启，选择自动保存
- 菜单、工具栏、状态栏、播放列表（含滚动条与表头）、窗口标题栏全都会跟着变

**设置方案（多套设置）**
- `文件 → 设置方案`：把当前这一套设置命名存下来（`数据目录\设置方案\*.json`），随时切过去
  - 一份方案就是**一份 settings.json**（同样的字段、同样的格式）：拷给别人就是拷一个文件，
    出问题用记事本打开就能看
  - **载入时可以只挑几组**：勾选窗口里一次列出播放 / 界面与主题 / 窗口与悬浮 / 歌词与桌面歌词 /
    音视频输出 / 行为 / 会话七组，每行还写着**这一组和当前有几项不一样**；
    没勾的那些保持现在这样（"把这套外观搬过来、音量别动"）
  - 载入 / 另存为之后它就是**当前方案**，之后的改动跟着设置一起**自动写回**它
    （退出时、以及切换方案前各写一次），不需要再点一次"保存方案"；
    菜单里当前那一行带勾，`关于` 里也写着现在用的是哪一份
  - **停用当前方案**只是不再往方案文件里写（设置改回只存 `settings.json`），文件留着；
    **删除方案**只删那一个文件
  - **从文件导入方案…** 把别处的设置文件收进方案库（原文件不动）；**导出当前设置到文件…**
    写到你挑的位置（备份、拷给另一台机器）。导进来的坏文件会被挡住并说明理由，
    库里已经存在的坏文件也会被列出来并标成「读不出来」（好让你看到并删掉它）
  - 和「播放列表」一个套路：方案库管自己常用的那几套，文件管外来的、外发的

**其他**
- 窗口位置、大小、音量、倍速、循环模式、播放列表、主题、排序方式、侧栏宽度与当前页、
  均衡器、音频输出设备等设置自动保存
- 桌面歌词的开关、位置、字号、不透明度、字体（含导入的字体文件）、配色、
  是否显示下一句、是否锁定也一并保存
- 把媒体文件作为命令行参数传入即可直接播放
- 记住上次打开的目录
- 数据目录可用环境变量 `播放器_DATA_DIR` 改写，便于做便携版（见下文）

## 主题

在 **视图 → 主题** 里切换，即时生效并保存到设置文件。

| 主题 | 窗口 / 列表 | 面板 / 传送栏 | 强调色 |
| --- | --- | --- | --- |
| 跟随系统 | 读 Windows 的浅色 / 深色设置自动切换 | — | — |
| 浅色 | `#F0F0F0` / `#FFFFFF` | `#202024` | `#0A84FF` |
| 深色 | `#1E1E1E` / `#1E1E1E` | `#181818` | `#4CC2FF` |
| OLED 纯黑 | `#000000` | `#000000` | `#4CC2FF` |
| VLC 橙 | `#2B2B2B` / `#262626` | `#1A1A1A` | `#FF8800` |

选「跟随系统」时，改动 Windows 的浅色/深色设置，播放器会立即跟着切换。

### 为什么主题要这么实现

WinForms 原生控件基本不理会调色板，想让深色主题真正"像样"，必须分别处理四类东西：

1. **菜单 / 工具栏 / 状态栏** —— 自绘 `ToolStripProfessionalRenderer`（`Ui/ThemedToolStripRenderer.cs`），
   连文字、箭头、勾选、分隔线、悬停背景一起接管，否则会从系统色里漏出来。
2. **列表的滚动条与表头** —— 系统主题引擎绘制，只能靠 `uxtheme` 切换
   （`Ui/NativeTheme.cs`，滚动条 `DarkMode_Explorer`，表头还要靠 `LVM_GETHEADER`
   单独拿到句柄再设 `DarkMode_ItemsView`）。
3. **窗口标题栏** —— `dwmapi` 的 `DWMWA_USE_IMMERSIVE_DARK_MODE`
   （Windows 10 2004 起是 20，更早是 19，代码里做了回退）。
4. **进度条 / 音量条** —— 直接用自绘控件 `Ui/FlatSlider.cs` 替换了原生 `TrackBar`。
   原生 TrackBar 的轨道恒为系统白色，在深色主题下非常扎眼；换成自绘后轨道、已填充部分、
   圆点全部跟随强调色，悬停时还能显示时间气泡。顺带也消除了
   `TrackBar.AutoSize` 默认 true 带来的高度失控问题。

侧栏里的三页同样是自绘的（`LyricsView` / `CoverView` / `SidebarTabs`），媒体信息页则复用
`ListView` + 上面第 2 条的 `uxtheme` 处理，所以滚动条也会跟着深色。均衡器对话框里的滑块
用的还是 `FlatSlider`，因此不会在深色主题下冒出白色系统控件。

新增一套主题只需要在 `Ui/Themes.cs` 里补一组 `ThemePalette` 数据。

## 构建与运行

```powershell
# 还原依赖（首次需要联网）
dotnet restore 播放器.csproj

# 生成
dotnet build 播放器.csproj -c Release

# 运行
.\bin\Release\net8.0-windows10.0.19041.0\播放器.exe
```

也可以直接用 Visual Studio 打开 `播放器.csproj` 后按 F5。

> **关于输出体积**：`VideoLAN.LibVLC.Windows` 会把 win-x64 / win-x86 / win-arm64 三套原生库
> 全部复制到输出目录，合计约 280 MB。本项目固定为 x64，x64 进程根本加载不了 I386 / ARM64
> 的 DLL，所以另外两套是纯粹的浪费。
>
> 工程文件里已经把包自带的开关关掉了，**生成结果只保留 x64 一套，约 102 MB / 437 个文件**，
> 不需要再手动删任何东西：
>
> ```xml
> <VlcWindowsX64Enabled>true</VlcWindowsX64Enabled>
> <VlcWindowsX86Enabled>false</VlcWindowsX86Enabled>
> <VlcWindowsArm64Enabled>false</VlcWindowsArm64Enabled>
> ```
>
> ⚠ 这三个属性的默认值是「按 `$(Platform)` 判断」，而本项目只写了 `PlatformTarget=x64`、
> `$(Platform)` 仍然是 SDK 默认的 `AnyCPU`，于是三个条件同时成立、三套全被复制。
> 详见「实现要点」里的说明。

## 安装与卸载

两种发行形态都由 `tools\pack.ps1` 产出到 `dist\`（不入库）：

| 形态 | 适合 | 装出来是什么 |
| --- | --- | --- |
| `全能本地播放器-1.2.1-安装程序.exe` | 日常使用 | 每用户装到 `%LocalAppData%\Programs\全能本地播放器`，**不弹 UAC**；开始菜单两项（程序 + 卸载），桌面图标可选；可把本程序加进常见音视频格式的「打开方式」候选；**自包含**，装完即用，不需要先装 .NET。实测装出来 671 个文件 / 250.5 MB（`libvlc\win-x64` 下 425 个文件，其中 325 个是 `plugins` 里的插件） |

- **卸载不删用户数据**：设置 / 历史 / 歌单 / 设置方案 / 字体都在 `%AppData%\播放器`，
  卸载器一个都不碰（要清干净自己删那个目录）；
- **「打开方式」只加候选、不抢默认**：只写 `HKCU\Software\Classes\Applications\播放器.exe`
  这一支自己的键（`SupportedTypes` 里是 52 种音视频 / 播放列表格式，**不含 `.txt`、`.lrc`**——
  把字幕格式也塞进"打开方式"只会添乱），每项都带 `uninsdeletekey`，卸载即还原。
  Win10/11 本来也不允许安装程序静默抢默认程序；
- 安装包**没有数字签名**，第一次运行会弹 SmartScreen「未知发布者」——这是没买代码签名证书的必然结果，
  不是包坏了；
- 从 [Releases](https://github.com/non266/local-player/releases) 下载时，资产名是
  `local-player-<版本>-setup.exe` / `local-player-<版本>-portable.zip`（ASCII 名，免得各家下载工具
  对中文名处理不一致；下到本地想改成什么名字都行）；
- **发布包是被验过的**：装出来那一份和便携 zip 解出来的那一份，各自在**自己的目录里**
  跑过全量 20 步冒烟（全绿），不是只验了开发目录里那份。

## 设置文件

播放器把数据保存在：

```
%AppData%\播放器\settings.json    设置（含主题、排序方式、播放列表等）
%AppData%\播放器\history.json     播放历史（每个文件播到哪儿、最近播放、音画/字幕延迟、歌词偏移、画面旋转）
%AppData%\播放器\fonts\           导入的字体文件（导入时复制进来的那一份）
%AppData%\播放器\播放列表\         歌单库：一个歌单一个 m3u8 文件
%AppData%\播放器\播放列表\歌单顺序.txt  歌单在窗口 / 菜单里的顺序（一行一个名字；删掉就回到按名字排）
%AppData%\播放器\设置方案\         设置方案库：一份方案一个 json 文件（内容就是一份 settings.json）
%AppData%\播放器\播放器.log        诊断日志（到 1 MB 轮转成 播放器.log.1）
```

> **设置方案和 settings.json 的关系**：`settings.json` 永远是"现在这一套"，
> 方案是它的一份**具名副本**。有当前方案时，退出（以及切换方案前）会把现在这一套写回方案文件，
> 所以方案文件等于"你现在这一套"，不是"上次保存时的快照"。
> 载入方案时只勾了一部分分组的话，没勾的那些保留当前值，方案文件也跟着变成合并后的样子——
> 这是"当前方案 = 你现在这套设置"的必然结果。不带方案用也完全没问题，那时一切照旧。

> **歌单是标准 m3u8**：可以直接拷给别人、用别的播放器打开，也可以把别人的 m3u
> 拖进歌单窗口收进来（会用绝对路径重写一份，免得相对路径拷过来就失效）。
> 删歌单只删这里的文件，**不会动任何媒体文件**。
> `settings.json` 里只记一项"当前列表对应哪个歌单"（`CurrentPlaylistName`），
> 以及"现在在用哪份设置方案"（`CurrentSettingsProfileName`）。

> **LrcAPI 的服务地址与鉴权密钥也在这个设置文件里**，密钥是<b>明文</b>存的
> （和这个文件里其它东西一样）。不想留痕就每次自己填，或者用完把「鉴权密钥」清空。

删除这两个文件即可恢复默认状态；`fonts` 目录里放的就是导入的字体，
**在界面上就能删**（`字体 → 管理已导入的字体…`），退出程序后直接删目录当然也可以。
导入的字体是**读进内存**装进 GDI+ 的，所以程序运行期间文件并没有被占着
（少数只能按文件加载的格式除外，见下文实现要点）。

> `history.json` 里除了续播进度与「最近播放」，还存着**按文件记下的音画 / 字幕延迟和歌词偏移**。
> 在界面上用「清除最近播放」只会清掉历史与进度，这些调整会保留；
> 直接删掉整个文件则连它们一起丢。

> **写入方式**：两个文件都不是直接覆盖，而是「先写同目录下的临时文件 → 落盘 → 改名覆盖」
> （`Core/SafeFile.cs`）。`File.WriteAllText` 是"先截断再写"，写到一半断电会留下半截文件；
> 而这两份文件的读取端都是"读坏了就退回默认值"。
>
> **读不出来时先试着把能救的项救出来**（`AppSettings.TrySalvage`）：把每个属性的原始片段
> **单独**反序列化一遍，好的留着、坏的记名字；用 `Utf8JsonReader` 一项一项读，
> 所以**语法坏在中间也能救出坏点之前的部分**。结果是这样告诉用户的：
>
> ```

  **改动自动写回**（关窗之后方案文件里就是新值。变异：去掉那次写回，立刻以
  `改动没有自动写回方案文件（音量 80，期望 85；主题 Auto，期望 Vlc）` 失败）；
  改名 / 停用 / 删除之后关联都跟着走，**停用不会删掉方案文件**；
- **载入时可以只挑几组**：勾选窗口默认全勾，每行写出「与当前不同」的项数（没区别的写
  「没有区别」），一组都不勾时「载入」点不动、硬点也不生效，DPI 缩放下控件不越界。

> 一条值得记住的语义：**方案文件等于"你现在这一套"，不是"上次保存时的快照"**。
> 所以载入当前方案时只勾了一部分，没勾的那些保留当前值、方案文件也跟着变成合并后的样子。

末尾那段"真接口"检查默认不跑（试试不该依赖外网），要用时：```powershell
$env:播放器_TEST_LRCAPI = "http://127.0.0.1:28883"   # 或自建实例的地址；写 1 就用这个默认端口
$env:播放器_TEST_LRCAPI_KEY = "<服务端配的鉴权密钥>"   # 服务端开了鉴权时才有用
dotnet SmokeTest.dll 在线
```

第 13 步需要真实视频（`播放器_TEST_VIDEO`），因为它要验的是"画面到底有没有变"：
先做一次**对照实验**——播放中连拍两张快照，像素必须不同，以证明截图抓到的是实时画面。
它**会真的播放那段视频并出声**，属正常现象。

逐帧那一小段是本项目里**改动最多、也最容易写错**的一处断言，现在的做法是：
先用一次"前进 + 后退"让基准落到 seek 的落点上（**不能拿暂停时截的那张图当基准**，
vout 比时钟滞后约 100~200ms），然后一次走 **5 帧**（相邻帧的白板画面可能只差 0.00~0.54，
走一帧等于在量重绘噪声），最后要求：

1. 前进 5 帧之后画面与基准明显不同（实试差 8~11）；
2. 后退 5 帧之后**像素级回到基准**（实试差 0.00）；
3. 连按 5 次（不留间隔）落在与慢速前进完全相同的那一帧上（实试差 0.00）。

这三条都做过**变异验证**：把后退那一支的 `SeekTo` 去掉，第 13 步会以
`上一帧没有退回原来那一帧（后退 5 帧之后与基准的像素差还有 11.13）` 失败并返回退出码 1。
（旧写法是"暂停时截一张当基准、走一帧、比 0.05 阈值"，它其实一直在量 0.5 量级的重绘噪声，
所以既会漏报也会误报。）

第 14 步钉住的是一批"改之前是坏的、但平时看不出来"的点：设置与历史必须是原子写、
读坏的文件要留下备份并给出提示、批量删除只通知一次界面、路径索引取首次出现、
时长扫描器"清空列表后重新添加同一个文件必须能重新扫出时长"，
以及**引擎事件必须在 UI 线程上派发（窗体还没建句柄时也不能例外）**。
其中扫描器和事件派发两条都做过**变异验证**：把修复去掉之后，第 14 步会分别以
`ClearPending 之后同一个文件没有重新排队` 和
`引擎事件在原生回调线程（46）上就地执行了` 失败并返回退出码 1。

> ⚠ 第 14 步能验证原子写的**可观察契约**（内容被替换、不留下残留的 `.tmp`），
> 但验证不了"原子性"本身——那需要在写到一半时杀掉进程，做不到可靠复现。
> 所以原子写这条是靠 `Core/SafeFile.cs` 的实现方式（临时文件 + 改名覆盖）保证的，
> 不是靠试试。

> 试试工程把输出直接写到主程序的生成目录，这样 `Core.Initialize()` 能在旁边找到
> `libvlc\win-x64`；因此**必须先构建主工程**。运行时窗口会短暂闪现约 1 秒，属正常现象。
> 只保留一套原生库之后，首次运行不再需要从磁盘读入近 300 MB 的库文件。
>
> 试试**不会碰你的真实配置**：它把 `播放器_DATA_DIR` 指到生成目录下的临时子目录，结束时删除。

除了自动试试，标签解析还对着一个真实的 185 个 FLAC 音乐库逐文件核对过：
**185/185** 都能读出标题、艺术家、专辑、年份、音轨号与内嵌封面（平均 1.2 MB 的 JPEG），
**185/185 含内嵌歌词，其中 176 个带时间轴**，0 个解析异常，平均 6 ms/文件。
侧栏四页也是在真实文件上逐个截图确认过的（歌词滚动高亮、封面圆角裁剪、
媒体信息里的采样率与轨道清单）。

## 架构与边界

这一节回答两个问题：**为什么这些地方要这么实现**（踩过的坑、实试结论），以及
**哪些事明确不做**。按领域分组，每组内大致按"越容易再踩越靠前"的顺序。

> 想改这个项目的话，先看这一节；内部债务清单与收敛顺序在 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)。

### 播放与内核（libvlc 那一层）

原生库、解析、滤镜、逐帧、时长扫描——这一层的坑几乎都是"libvlc 的规则和托管代码不一样"。

#### 均衡器预置要从 libvlc 现读

`Equalizer` 类没有名为"按预置创建"的方法，但 **`new Equalizer(uint)` 的参数其实是
预置序号**（内部就是 `libvlc_audio_equalizer_new_from_preset`），**不是频段数**——
文档里写得很清楚，方法签名却极具误导性。用它把 VLC 的全部预置曲线读出来，
比凭印象硬编码一组近似值可靠得多。

顺带纠正一个凭印象极易写错的数据：VLC 的 10 段是**从 31.25 Hz 开始的等程划分**
（31.25 / 62.5 / 125 / 250 / 500 / 1k / 2k / 4k / 8k / 16k），不是 60 Hz 起的那一套。
`EqualizerCatalog` 里仍留了一份兜底频率，但那只是 libvlc 读不到时的降级样子。
冒烟试试第 10 步会断言：从 libvlc 读到的预置 ≥ 5 套、Rock 曲线不是全零、频段频率严格递增。

滑块是整数 dB 而预置曲线带小数，所以约定：**用户没碰过的频段保留原始小数**，
只有真的拖动过的那一段才写成整数。

#### ⚠ libvlc 的画面上滤镜与逐帧：哪些能用、哪些不能用

这一批"视频功能"踩到的坑比较集中，下面每一条都是**实试**结论
（快照像素对比 + 真实按键 + 屏幕取样，用了三个不同的视频）：

| 接口 | 机制 | 实试结果 |
| --- | --- | --- |
| `libvlc_video_set_adjust_*`（亮度 / 对比度 / 饱和度 / 色相 / 伽马） | 在 media player 对象上设变量 | **画面完全不变**。变量能设也能读回来，只看返回值会以为成功了 |
| `:video-filter=adjust{...}` 媒体选项 | 滤镜链参数 | 画面不变 |
| `--video-filter=adjust{...}` 实例级选项 | 全局选项 | 画面不变 |
| 同上再加 `--avcodec-hw=none` / `--vout=direct3d9` | 换解码与视频输出 | 画面不变 |
| `libvlc_media_player_next_frame()`（逐帧前进） | 在 input 上设 `next-frame` | **画面完全不变**（快照像素差 0.00，屏幕取样也几乎不动） |
| `libvlc_audio_set_delay` / `libvlc_video_set_spu_delay` | `input_Control` | **有效**，往返一致 |
| `libvlc_video_set_deinterlace` | `input_Control` | 接口接受，9 个模式都能设进去 |

分界线看起来是：**走 `input_Control` 的接口有效，"
在 media player 对象上设变量"的接口到不了视频输出**。据此最后的取舍是：

- **音画同步**用 `SetAudioDelay` / `SetSpuDelay`（可靠），并且按文件记住；
- **逐帧**不用 `NextFrame()`，两个方向都改成"按帧长精确定位"——
  暂停时 libvlc 会解码到目标时间并显示那一帧。落点精确且可复现：同一个时刻来回 seek
  像素差 0.00，后退 5 帧能像素级回到出发帧，连按也不丢（见下文"已知限制"里的实试数字）；
- **亮度 / 对比度那类画面调整没有做**：上面五种办法都试过，画面像素纹丝不动。
  与其放几个不起作用的滑块，不如不做。

另外两个实现细节：

- 逐帧**不能**用 `MediaPlayer.Time` 判断有没有生效：暂停时它是播放时钟，**不推进**。
  所以自己维护"相对暂停点走了几帧"的序号，跳转或重新播放时清零。
- 暂停是**异步**生效的：`SetPause(true)` 之后要等到 `IsPlaying` 变成 false 再定位，
  否则在播放状态下走帧，画面会直接继续播下去。
- ⚠ **不要拿"暂停时截的那张图"当逐帧的基准**：那一刻画面上显示的并不是时钟所指的那一帧
  （vout 滞后约 100~200ms，实试 seek 到时钟所指时刻画面会变 11 左右）。
  这个坑让冒烟试试第 13 步长期在量重绘噪声，既漏报也误报。

#### ⚠ `Media.Parse` 必须同步等待，不要 `await`

这是本项目踩过最严重的一个坑，后续改动 `DurationScanner` 时务必注意。

`Media.Parse()` 返回的 Task 是在 **libvlc 自己的解析回调线程**上完成的。如果写成：

```csharp
using (var media = new Media(libVlc, path, FromType.FromPath))
{
    await media.Parse(MediaParseOptions.ParseLocal, 5000);   // ← 危险
    var duration = media.Duration;
}                                                            // ← 在此释放 Media
```

`await` 的续体可能**就地运行在那个 libvlc 回调线程上**，于是 `media.Dispose()` 会在 libvlc
仍处于回调栈内时释放该 media。回调返回后 libvlc 继续访问已释放内存，触发
**原生访问违例 `0xC0000005`**——进程直接消失，`Application.ThreadException` 与
`AppDomain.UnhandledException` 都拦不住（事件日志里只有 "exception code c0000005"，
托管堆栈为空），表现出来就是"打开文件后闪退"。

正确写法是**阻塞等待**（并且分片等待，以便退出时能及时取消；
超时那一项的释放方式见下一节），让释放发生在扫描器自己的工作线程上：

```csharp
var parseTask = media.Parse(MediaParseOptions.ParseLocal, 5000);

// 分片等待而不是一次等 15 秒：每片检查一次取消，Dispose 时最迟 250ms 就能放手。
while (!parseTask.Wait(250)) { /* 处理取消 / 超时，见下一节 */ }

var duration = media.Duration;   // 解析已结束，此时释放是安全的
```

实试对照（每轮解析不同文件，同一进程内连续进行）：

| 写法 | 结果 |
| --- | --- |
| `await` + 续体内立即释放 | 第 2 轮内必崩 |
| `await` + 主线程延迟释放 | 通过 |
| `await` + 不释放 | 通过 |
| **同步阻塞等待 + 立即释放** | **通过（120 次解析压试无崩溃）** |

`tools/SmokeTest` 的第 7 步就是针对这个问题的回归试试。

#### ⚠ 超时那一项不能"不释放"了事

上一版在解析超时时写的是 `media = null;`——把引用扔掉，留给进程结束时回收。当时的理由是
"就地释放会在 libvlc 的回调栈里访问违例"，这个理由是**对的**，但代价是每次超时都永久泄漏一个
`libvlc_media_t`，而且被放弃的 `Parse` 任务还有可能抛出无人观察的
`TaskException`。

正确做法是把释放**挂到解析任务自己身上**，让它在解析真正结束时于线程池上执行：

```csharp
var parseTask = media.Parse(MediaParseOptions.ParseLocal, 5000);

// 分片等待：每片结束检查一次取消，Dispose 一取消最迟 250ms 就能放手，
// 不会在退出流程里继续握着 LibVLC（那是原生的访问违例）。
while (!parseTask.Wait(250))
{
    if (_cts.IsCancellationRequested || waited >= 15000)
    {
        var abandoned = media;
        media = null;
        // ContinueWith 不会内联到"完成它的那个线程"上，所以这里安全。
        _ = parseTask.ContinueWith(_ => abandoned.Dispose(), TaskScheduler.Default);
        return TimeSpan.Zero;
    }
    waited += 250;
}
```

`ContinueWith` + `TaskScheduler.Default` 是关键：它保证释放发生在**线程池**线程上，
而不是把 `media` 释放到 libvlc 自己的回调栈里。

#### ⚠ `_seen` 只清队列不清它，重新添加同一个目录就再也没有时长了

`DurationScanner` 用 `_seen` 记住"哪些路径排过队"来避免重复解析。解析**成功**的路径**故意**
不移除（这是对的），失败才移除。

问题是清空播放列表时调用的 `ClearPending()` 原来只排空队列：

```csharp
public void ClearPending()
{
    while (_channel.Reader.TryRead(out _)) { }   // 队列空了，但 _seen 里还留着全部路径
}
```

于是**清空列表 → 重新添加同一个目录**时，每个文件都还在 `_seen` 里，`TryAdd` 全部失败，
一条都不会重新排队。新加入的条目就永远停在 `--:--`，总时长显示 `总计 --:--`，
**非得重启程序才恢复**。修法是两个一起清（`_seen` 是 `ConcurrentDictionary`，清它不会
影响正在解析的那一项）。

`tools/SmokeTest` 第 14 步用真实 WAV 钉住了这条：排一次队等到时长、`ClearPending()`、
再排同一个文件，必须能**第二次**收到 `DurationFound`。

#### ⚠ 时长回填要能撑住"句柄还没建好"

时长扫描是**在构造函数里**就开跑的（启动参数里的文件当场入列表、当场入队），
而结果是从后台线程回来的。以前这一支写的是：

```csharp
if (_disposed || !IsHandleCreated) return;   // ← 句柄没就绪就把结果丢掉
```

结果：**那一条时长永久丢失**，界面上表现为某一项一直是 `--:--`。
它只在"扫描比建窗口快"的时候出现（实试三次里红两次），所以看起来像随机故障；
冒烟试试里那条"播放列表汇总"断言就是被它抽中过（标题里的"（1 项未知）"）。

现在改成先攒着，`OnHandleCreated` 时补上——和 `PlayerEngine` 早就有的
`FlushPendingUiActions()` 是同一个道理（"句柄就绪之前回调线程上攒下的事件，
现在可以安全派发了"）。新增的 `CheckDurationsBeforeHandle` 刻意**不碰句柄**、
先把扫描跑完再要句柄，把那个时间窗固定下来当回归。

> 这条是加日志之后才查出来的：日志里六条"时长解析"全都成功，而界面上仍有一项未知——
> 数据把猜试直接排除了。以前只能靠猜"是不是扫描器卡住了"。

### 列表与搜索

列表行索引、拖放事件、批量回填的性能。

#### ⚠ 列表行的索引不能当成播放列表索引

启用搜索过滤之后，界面行号和模型索引就不再一一对应了。为此 `ListViewItem.Tag` 里固定存
**播放列表模型的索引**，所有"界面行 → 条目"的转换都必须走 `FindRow` / `GetSelectedPlaylistIndices`。
序号列显示的也是模型索引 + 1，所以筛选时编号保持稳定、不会跳动。

如果之后再加"从列表里删除某一行""把选中项导出"之类的功能，务必用这两个方法取索引，
直接拿 `SelectedIndices` 当模型索引用会在筛选状态下删错文件。冒烟试试里专门有一段逐行校验
序号列与 `Tag` 是否一致。

#### ⚠ 拖动换位与文件拖放共用同一组拖放事件

列表同时支持"拖入文件"和"拖动行换位"。两者都走 `DragEnter` / `DragOver` / `DragDrop`，
靠 `_draggingRow` 标志区分，并且各自都要在开头判断"是不是我这种拖放"再处理。
筛选状态下拖动换位会主动禁用（行号与模型索引不连续，容易产生歧义）。

#### 逐条回填不要重复线性扫描

时长扫描是**逐条**回调的，每回填一条原来要做四次线性扫描：`Playlist.IndexOfPath`（找条目）、
`SetDuration` 内部**再**扫一次、`FindRow`（遍历整个 `ListView`）、以及重算标题总时长时
`GetDurationSummary` 再扫全部条目。也就是说给 n 条记录补全时长要 O(n²) 次字符串比较，
外加 n 次全量重算。185 个文件完全无感（实试 6 ms/文件），上千条时后面几次每次都要几百万次比较。

现在：`Playlist` 维护一份路径 → 索引的字典（`Add`/`AddRange` 增量登记，只有插入 / 删除 /
移动 / 排序这些本来就已经 O(n) 的操作才重建），界面维护一份"行号 → `ListViewItem`"的映射
（在重建列表时一起建），标题总时长改成置一个脏标记、由 200ms 的界面计时器统一重算一次。

同一批里还修掉了两处同类的"循环里干重活"：

- `PlayIndex` 顺延找可播项时**每跳过一个就整体重建一次 ListView**。整份列表都失效时
  就是"重建上千次"，窗口直接假死。现在循环里只标记，循环外刷一次。
- `Playlist.RemoveMany` 原来对每个索引走一次 `RemoveAt`，而 `RemoveAt` 每次都会触发
  `Changed` → 界面整体重建。删掉 500 项就是重建 500 次。现在整批只触发一次通知。

另外拖进来的文件夹以前是**在 UI 线程上递归枚举整个目录树**的，拖一个音乐库或一个盘符会
白屏几秒到几十秒且没有任何提示。现在只有"取出路径列表"放在后台线程，真正改动播放列表仍然
回到 UI 线程做（`AddPathsWithFolders`）。

### 内容：标签 / 歌词 / 字体

标签与歌词自己解析、在线接口的实试结论、字体的两条装载路径。

#### 标签与歌词为什么自己解析

libvlc 只暴露 `Media.Meta()` 的十几个字段，**没有歌词**，也不给内嵌封面。
所以 `Core/TagReader.cs` 按格式规范自己读文件结构：

| 格式 | 读取内容 |
| --- | --- |
| ID3v2.2 / v2.3 / v2.4 | `TIT2 TPE1 TALB TCON TRCK COMM`、`USLT`（纯文本歌词）、`SYLT`（带时间轴）、`APIC`（封面）、`TXXX:LYRICS` |
| FLAC | `STREAMINFO`（采样率 / 声道 / 位深 / 时长）、`VORBIS_COMMENT`（含 `LYRICS`）、`PICTURE` |
| MP4 / M4A | `ilst` 里的 `©nam ©ART ©alb ©day ©gen ©cmt ©lyr covr trkn` |
| ID3v1 | 最后 128 字节，只在前面的标签全部为空时兜底 |

几个容易写错的地方：
- **ID3v2.4 的帧长度是 synchsafe 的**（每字节只用低 7 位），v2.3 是普通大端，混了就完全读不出帧。
- **MP4 的 atom 类型里带 `©`（字节 0xA9）**，必须按 Latin-1 解码；用 ASCII 会变成 `?` 而匹配不上。
- **`meta` 是 full box**，子原子前面有 4 字节版本/标志，遍历时不能漏。
- 声明为 ISO-8859-1 的中文标签实际几乎都是 **GBK**，所以先做一次 GBK 字节结构校验，
  通过就按 GBK 解，否则退回 Latin-1（它解码永不失败）。见 `Core/LegacyText.cs`。
- `SYLT` 帧本身不是 LRC 文本，代码把它**转写成 LRC 格式**，这样下游只需要维护一套解析逻辑。

歌词装载优先级（`Core/Lyrics.cs`）：**带时间轴的优先于纯文本**；同级之间先外挂 `.lrc`、
再内嵌，最后才看同名 `.txt`。`[offset:]` 按通行惯例是**正值表示歌词提前显示**，
即最终时间 = 时间戳 − offset。

#### ⚠ LrcAPI：两代接口、封面从哪来、鉴权怎么发（都是实试）

在线歌词用的是 **LrcAPI**（`/api/v1/...` 是新版，`/lyrics`、`/cover` 是旧版）。
手上那台自建实例（`http://127.0.0.1:28883`，waitress/Flask）实试下来是这几个结论，
客户端就是照它们写的：

| 请求 | 实试结果 |
| --- | --- |
| `GET /api/v1/lyrics/single?title=&album=&artist=` | 200，**LRC 文本（带时间轴）** |
| `GET /lyrics?...`（旧版） | 200，同样是带时间轴的 LRC |
| `GET /lyric?...` / `/api/lyric?...` | 404（这两个路径不存在） |
| `GET /api/v1/lyrics/advance?...` | 200，JSON 列表，字段是 `id/title/artist/lyrics/**cover**` |
| `GET /api/v1/cover/music?...` | **302 → 404**：它重定向到 `http://api.lrc.cx/cover/music/title=…`，**少了问号**，所以取不到 |
| `GET /api/v1/cover/album` / `artist` | 同样是 302 到 `http://api.lrc.cx/cover/...` 的拼错地址 |
| `GET /cover?...`（旧版） | **401**，而且**带不带密钥都 401**（换 `Cookie` / `X-Api-Key` / `?auth=` 查询参数也都 401，返回的是网页登录页那一套） |

另一台（公网自建，`http://61.124.15.26:28883`）表现得完全不一样，也一并记在这里，
因为客户端要同时伺候这两种：

| 请求 | 实试结果 |
| --- | --- |
| 不带 `Authorization` | **一律 401**（鉴权是开的） |
| `Authorization: Bearer <key>` | 401（**格式是裸密钥，不是 Bearer**） |
| `Authorization: <key>` + `/api/v1/lyrics/single` 与 `/lyrics` | **404 "Lyrics not found."**（鉴权过了，但它上游对任何曲子都没结果） |
| 同上 + `/api/v1/lyrics/advance` | **500**（这个接口本身就坏） |
| 同上 + `/cover` | **200，858 KB 的 JPEG** ✔ |
| 同上 + `/api/v1/cover/music` | 302 到拼错的官方地址 |

所以"封面能不能拿到"完全取决于**哪台服务、哪条路活着**——
三条路都留着、按可用性依次回退，并且把每条的结局写进失败信息里（见下）。

也就是说，这台实例上**歌词根本不需要鉴权**（`/api/v1/lyrics/single`、`/lyrics`、`advanced`
不带任何头都是 200），而**封面接口怎么都没有**：新版接口 302 到一个拼错的官方地址再 404，
旧版接口 401。**能用的只有搜索结果里的 `cover` 字段**（指向各家平台的图片地址）——
所以客户端的封面顺序就是"搜索结果优先"，另外两条只当回退。

于是歌词是"两代都试、谁给带轴的用谁"，而**封面优先从搜索结果的 `cover` 字段里拿**——
那台实例上只有这条路是通的。三条路都带图类型校验：拿回来的是 HTML 错误页（403/404 页面）
一律丢掉换下一条，最后如实报"没找到"还是"下不下来"。

**鉴权**（官方文档：[用户鉴权](https://docs.lrc.cx/docs/deploy/auth/)）是请求头
`Authorization: {auth key}`。四个实现上的点：

- 鉴权头**逐请求**加，不挂在共享 `HttpClient` 的 `DefaultRequestHeaders` 上：
  那是全局状态，几个请求并发时最后带上的是谁的密钥都说不清；
- 只发给**用户自己配的那台服务**（主机 + 端口都对得上），
  因为搜索结果里的封面图往往挂在 `p2.music.126.net` 这类**第三方主机**上——
  一股脑带上就等于把用户的密钥交给了第三方。这条有专门的单元检查
  （`ShouldSendToken`：同主机发、别的端口 / 别的域名 / 空密钥都不发）。
- **默认不带，被挑战了才带**：先不带 `Authorization` 发一次，只有收到 401/403
  才带上重试，成功之后记住"这台服务要带"。理由是实试出来的——
  很多实例的歌词接口压根不需要鉴权，无脑带上反而会在它的日志里刷
  `ERROR:mod.auth:Unauthorized access: 未经授权的用户请求`（真实反馈）。
- **带了反而 5xx 就不带——但只在"去掉鉴权真的好使"时才算**：
  某自建实例一收到 `Authorization` 就 500
  （Python 端 `TypeError: string indices must be integers, not 'str'`）：
  去掉鉴权再试，成功了才认定"这个服务的鉴权实现有问题"并记下来。
  这一条是**对着真实自建实例跑才发现的**：那台的批量搜索接口**自己**就 500
  （带不带密钥都 500），早先的写法看到"带了鉴权就 500"就武断地把密钥判成有毒，
  于是同一台服务上本来正常的封面接口也不带头了、全都 401。
  现在会先不带鉴权再试一次：**去掉之后好了** = 鉴权的问题；**去掉也一样坏** = 这个接口自己的问题，
  密钥照常保留（冒烟试试两个方向都钉住了）。

**已经确认不可用的封面来源会被记下来**（按"端点 + 密钥"记）：
自建实例上常见的情况是封面接口整体坏掉（新版 302 到拼错的地址、旧版一律 401），
既然第一次就试出它不行，后面找封面时就不再敲它——既省时间，
也不会在对方日志里反复刷"未授权请求"。冒烟试试直接数请求：
第二次找封面时**不该再出现 `/cover` 或 `/api/v1/cover` 的请求**，
失败信息里也会写「已确认不可用（不再尝试）」。

还有两个刻意的取舍：
- **服务地址没有默认值**。这是要联网的第三方服务，程序不替用户挑地址；
  没填时一个请求都不发，只在菜单上写「服务地址：未填写（点这里填）」。
  打开"自动获取"却没有地址时，会把填地址的对话框直接弹出来，用户按了确定才算数。
- **歌词与封面不写盘**：只在本次运行里用（按曲目路径缓存在内存）。
  这是明确的取舍——不会往用户的音乐目录里丢 `.lrc` / 封面文件，
  代价是下次打开同一首要重新联网。

失败时的说法也分了几种（都是被真实反馈逼出来的）：

- **没填密钥**却撞上 401 → 提示去「鉴权密钥…」填；
- **填了密钥**还是 401 → 不会再喊"去填密钥"（那只会让人以为没保存），
  而是说"密钥没被接受：检查密钥是否正确，或者这个接口不认 Authorization 头
  （有的实例只认网页登录的 Cookie）"；
- **封面失败**会把三条路各自的结局一起报出来，例如
  `在线封面：服务端拒绝了鉴权（HTTP 401）…（试过：搜索结果里没有封面地址 → 歌曲封面接口 404 → 旧版 /cover 401）`
  ——"哪一步倒下的"才是能拿去排查的信息。

#### 导入的字体从内存装进 GDI+（文件才不会被占住）

`PrivateFontCollection.AddFontFile` 会**占用**字体文件，于是"卸载字体"这件事根本做不了：
字体库里的那一份删不掉（实试 `File.Delete` 失败），界面上再怎么加删除按钮都是假的。

改成读一次字节、钉住（`GCHandle.Alloc(bytes, Pinned)`）之后 `AddMemoryFont`：
GDI+ 拿的是那块内存的地址，**文件不再被锁**，删除当场就成。
钉住的句柄留在列表里、进程退出时统一释放（`AddMemoryFont` 的数据必须在集合存活期间一直有效，
这里不赌 GDI+ 有没有偷偷复制一份）。

两个配套细节：

- `.ttc` / `.otc` 这类**字体集合**内存加载探试出来是 0 个字体族（实试），自动退回文件方式；
  那一份会被占住，删除就记进 `fonts\pending-delete.txt`，下次启动、还没加载字体之前再删一次。
- 同一族名来自多个文件是**常态**（同一个字体导入两次、或者同族的两个字重来自不同文件），
  所以删除是按**文件**做的：只有当一个族名最后一个文件也没了，它才从字体菜单里消失。
  冒烟试试钉住了这一点（"删一个不会带走别的字体"）。

#### ⚠ 判断"这是不是字体文件"不能交给 GDI+（它会报出上一个装过的字体）

导入时先看**文件头**，再让 GDI+ 去装（`FontLibrary.LooksLikeFontFile`：
`0x00010000` / `OTTO` / `true` / `ttcf` 四种 sfnt 魔数，正好覆盖支持的四种扩展名）。

理由是实试出来的：**GDI+ 探试一个坏文件时会报出进程里上一个装过的字体族**——
一个 21 字节的文本文件（扩展名改成 `.ttf`）被报成了 `Arial`，也就是刚刚导入的那个系统字体。
不预检的后果是垃圾文件被当成"导入成功"留在字体库里、菜单里多出一个幽灵字体。
（这条是压试逼出来的：同一个进程里先真导入一个字体，再连打 200 次垃圾，1 次被接受。）

留了一个**已知容忍**：**截断的真字体**（比如 `arial.ttf` 的前 32 字节）文件头合法，
预检会放行、GDI+ 也照样报出 `Arial`。没有为它加解析——半个字体文件不是正常输入，
真要做就得自己解析 sfnt 表结构，不划算。

#### ⚠ 导入的字体要同时装给 GDI+ 和 GDI（侧栏歌词曾经"换了字体却没变"）

同一个程序里，两处歌词用的绘制 API 不是一套：

| 位置 | 用的 API | 背后的引擎 |
| --- | --- | --- |
| 桌面歌词 | `Graphics.DrawString` | GDI+ |
| 侧栏歌词 | `TextRenderer.DrawText` | **GDI** 的 `DrawText` |

而 `PrivateFontCollection`（`AddMemoryFont` / `AddFontFile`）是 **GDI+ 的私有字体集合**，
**GDI 完全看不到它**：字体的名字在 GDI 的字体表里查不到，它就**静默换成默认字体**。
于是出现了一个很别扭的现象——桌面歌词换了字体，**侧栏歌词一动不动**，
而且从代码上看两边改的是同一个设置（`MainForm.ApplyLyricsFont`），完全看不出问题在哪。

修法是同一块内存喂给两个引擎：GDI+ 用 `PrivateFontCollection.AddMemoryFont`，
GDI 用 `gdi32` 的 `AddFontMemResourceEx`：

```csharp
// 内存是钉住的托管数组（GCHandle.Pinned），两个引擎拿的都是它的地址
var handle = GCHandle.Alloc(bytes, GCHandleType.Pinned);
var pointer = handle.AddrOfPinnedObject();

Imported.AddMemoryFont(pointer, length);                  // GDI+
AddFontMemResourceEx(pointer, (uint)length, IntPtr.Zero, out _);   // GDI（进程私有）
```

`AddFontMemResourceEx` 只对**本进程**可见，不写进系统字体库，程序退出就没了——
相当于给 GDI 单独开了一份字体表（进程退出时用 `RemoveFontMemResourceEx` 还回去）。

验证这件事有个坑：**必须用一个系统上绝对没有的字体族名**。拿 Arial 这种系统自带字体来试，
GDI 就算看不见私有字体，也能从系统字体表里找到同名字体，两边看起来一模一样，
检查会一直通过而 bug 一直在。冒烟试试的做法是把字体文件 `name` 表里的族名
**原地改成等长的占位名**（`Zzqzz`；改长度会破坏记录里的偏移，等长最安全），
唯一标识 / 完整名 / PostScript 名也要一起改（只改族名的话它在身份上仍然"是 Arial"），
然后用 `GetTextFace` 直接问 GDI"你最终用的是哪个字面"：

| 状态 | `GetTextFace` 的结果 |
| --- | --- |
| 只装给 GDI+（改之前） | `Microsoft YaHei UI`（被替换掉了） |
| 两个引擎都装（现在） | `Zzqzz`（导入的那个字体） |

这条做过**变异验证**：把 `AddFontMemResourceEx` 那行去掉，第 15 步立刻以
`GDI 认不出导入的字体族「Zzqzz」，它会把字画成「宋体」` 失败。

> `GetTextFace` 比"比像素"硬：像素差会受采样、抗锯齿影响，
> 而且"换成另一个被替换的字体"也能凑出一个差值。所以像素那条只作为端到端补充
> （侧栏歌词换字体后重绘像素差必须大于 0），真正的判据是 GDI 报出来的字面名。

另外，`.ttc` / `.otc` 字体集合的内存加载 **GDI+ 不认**（探试出来 0 个字体族），
所以那条路退回按文件加载、文件会被占住（删除排到下次启动）；
但 **GDI 那边照样注册得上**——实试 `SitkaB.ttc` 里 6 个字体族，
在侧栏歌词（GDI）上都能正确落到对应字面。

#### 歌词偏移：换一份平移过的歌词，而不是到处减偏移

歌词和声音差半拍是最常见的抱怨。改法有两种：把偏移塞进每一处"位置 → 该显示哪一句"的计算里，
或者**换一份每行时间都平移过的歌词**（`LyricsDocument.Shifted`）。这里选后者——
读歌词时间的地方不止一处：侧栏的高亮行、桌面歌词的当前句 / 下一句、鼠标悬停显示的时间点、
点某一行跳转。只要有一处忘了算偏移，那一处就会和别处对不上（点了歌词跳过去正好差一个偏移量，
这种 bug 最难发现）。换文档就只改一处，四处自然一致。

几条定下来的事：

- **符号与 LRC 的 `[offset:]` 一致**：正值 = 歌词提前（每行时间 = 时间戳 − 偏移）。
  界面上永远写成"提前 1.5 秒 / 延后 0.5 秒"，不让用户对着正负号猜；
  状态栏、菜单上的当前值、歌词页右上角的小字都是这个方向。
- 提前到 0 之前的时间戳**压在 0**（和解析 `[offset:]` 时一样）：
  变成负数的话，悬停提示会显示 `-00:00:00.5`，比"压在 0"更难理解。
- 偏移**按文件记**，存在 `history.json`（和音画 / 字幕延迟同一处）：
  同一首歌的不同版本、不同来源的歌词差得往往不是一个数，一首歌每次打开都重调一遍最烦人。
- 顺手修掉一个连带问题：`PlaybackHistory.Clear()`（清除最近播放）以前是 `_records.Clear()`，
  会把按文件记下的音画 / 字幕延迟一起清掉——那属于无声的数据丢失。
  现在只清"历史与续播进度"，保留这些用户一项项调出来的调整；
  同时 `Recent` 跳过"没播过、只是被记下了某个调整"的空壳记录，
  否则调一下歌词偏移就会在「最近播放」里凭空多出一条。
- 歌词页右上角常驻一行很淡的 `+1.5s`：偏移是上次调完就留在那儿的，
  过几天再看歌词对不上时，多半已经想不起来自己动过它。

#### 歌词的时间气泡：只在换行时重弹

鼠标停在歌词某一行上要显示这一句的时间点，用的是 `ToolTip`（`Ui/LyricsView.cs`）。有几个
不写出来就会踩的点：

- **只在换行时重弹。** 如果跟着 `MouseMove` 每次都 `Show`，气泡会随着鼠标不停闪，
  而且它自己会盖住歌词。所以用一个 `_tipIndex` 记住"当前是哪一行"，同行内不再刷新。
- **重弹前先 `Hide`。** 在同一个控件上直接 `Show` 新文字，气泡的位置不会更新。
- **纯文本歌词不弹。** 没有时间戳的歌词每一行的时间都是 `0`，弹出来就是误导性的
  `00:00:00`；`TimeTipTextFor` 对非同步歌词直接返回 `null`。
- **滚动 / 换歌词 / 移出控件都要收掉。** 滚轮滚动之后光标底下已经不是原来那一行了，
  留着那个气泡就是错的。
- `ToolTip` 是本类自己 `new` 的，所以 `Dispose` 里要显式释放。

`tools/SmokeTest` 第 11 步直接验 `TimeTipTextFor`：带时间轴的歌词每一行都要给出正确时间，
纯文本歌词与越界下标都必须返回 `null`。

### 界面：布局与窗口

分隔条、侧栏与列表的牵连、分离成独立窗口、吸附、桌面歌词这个"不该被注意到"的窗口。

#### 两个分隔条：算视频宽度时必须给侧栏留位置

界面是「视频 | 侧栏 | 播放列表」，而侧栏嵌在播放列表面板的**内部**（`splitSide` 套在
`splitMain.Panel2` 里）。所以 `splitMain.Panel2MinSize` 必须 ≥「侧栏最小宽 + 分隔条 + 播放列表最小宽」，
否则侧栏会把播放列表挤成 0 宽——**实试出现过播放列表整条从界面上消失**。
宽度分配统一走 `MainForm.Sidebar.cs` 的 `ApplyPanelLayout()`，不要再去单独摆某一个分隔条。

另外默认宽度常量（320 / 300）是逻辑像素，用之前要按 `DeviceDpi / 96f` 放大，
否则在 125% 缩放下会比设计的窄四分之一。

#### 侧栏与播放列表为什么会互相牵连（以及怎么分开的）

第一版把侧栏和播放列表叠在**同一个** `SplitContainer` 面板里（侧栏在"播放列表面板"的内部），
于是 `splitMain.Panel2Collapsed` 一收，两个一起消失——想在只听歌的时候关掉播放列表，
侧栏也跟着没了。宽度也是相互制约的：算视频宽度时得手动把侧栏那一份减掉，
否则播放列表会被挤成 0 宽（真的出现过整条列表消失）。

现在改成两个互不相干的层级：

```
splitMain
├── Panel1: splitVideo          ← 视频区
│   ├── Panel1: 视频 + 传送栏
│   └── Panel2: 侧栏              ← 侧栏跟着视频，固定宽度
└── Panel2: playlistHost        ← 播放列表自己一栏
```

这样两个折叠开关各管各的，两条分隔条也各算各的。**布局的视觉顺序没变**，
仍然是「视频 | 侧栏 | 播放列表」。

#### 分离成独立窗口：其实就是换个父容器

WinForms 里 `Controls.Add` 会自动把控件从旧的父级摘下来，所以"分离 / 归位"就是搬一次家：
把 `sidebarPanel`（或装着播放列表的 `playlistHost`）从分隔条挪到一个 `Form` 里，或者挪回去。
停靠方式、主题、事件订阅全都不受影响，不需要重画一遍。

几个要注意的地方：

- **播放列表包装成了一个 `Panel`**（`playlistHost`）：搬一个控件比搬四个省事。
- **悬浮窗的 `Owner` 设成主窗口**：这样它总在主窗口之上（正好满足"叠在画面上"），
  主窗口最小化时也跟着收起来；同时 `ShowInTaskbar = false`，不在任务栏里多占一个位置。
- **关闭 = 归位**：`FormClosing` 里判断 `CloseReason`，只有用户自己点 ✕（`UserClosing`）
  才取消关闭并归位；主窗口关闭时是 `FormOwnerClosing`，必须放行，否则会卡住退出流程。
- **位置大小要记两次**：不只是"归位"时记，退出时也要记——用户完全可能一直让窗口飘着就直接退出。
- 恢复分离状态放在 `OnLoad` 而不是 `OnShown`：要在窗口可见之前把控件搬走，否则会闪一下停靠布局。

#### 侧栏的滚轮要自己转发

Windows 把 `WM_MOUSEWHEEL` 投递给**焦点窗口**，而不是鼠标下的窗口。歌词页又刻意不抢焦点
（抢了会打断播放列表搜索框的输入），所以滚轮消息根本到不了它手上。
`SidebarPanel` 因此装了一个 `IMessageFilter`：鼠标确实落在侧栏内、且当前停在歌词页时，
把滚动量转交给歌词控件并消化掉消息。

写这类过滤器时注意参数拆分：**`lParam` 的低字是 x、高字是 y（屏幕坐标）**，
而**滚动量在 `wParam` 的高字**；两者都要按**有符号** 16 位取（多显示器下坐标可能为负）。

#### 悬浮窗吸附：两个阈值 + 沿边偏移

把分离出去的侧栏 / 播放列表拖到主窗口边附近就贴齐，贴住之后跟着主窗口走
（`MainForm.Floating.cs`）。实现上有四处是必须的：

**1）吸附与脱离用两个不同的阈值。** 吸附距离 18px、脱离距离 40px。如果两者相同，
把窗口拖到临界点上会反复"贴上去又掉下来"，抖得没法用。

```csharp
var limit = current == WindowSnapEdge.None
    ? SnapPixels(SnapAttachDistance)      // 还没贴住：要拖得很近才吸
    : SnapPixels(SnapReleaseDistance);    // 已经贴住：要拖开更远才放
```

**2）沿贴合边方向必须有足够重叠。** 否则会出现"窗口在主窗口右下方老远，
却斜着贴到角上"这种莫名其妙的行为。四条边里挑距离最小的那条。

**3）要记的是"沿边偏移"，不是坐标。** 贴住之后窗口位置是**算出来**的
（`y = main.Top + offset`），所以坐标没有意义；用户沿着边拖动时还要反过来
从当前位置更新这个偏移，否则它会一直弹回最初贴上去的那个位置。

**4）主窗口的 `Move` 和 `Resize` 都要接。** 只接 `Move` 的话，贴着右边时把主窗口拉宽，
悬浮窗会被主窗口盖住而不是跟着让位。

两个容易忽略的细节：

- **程序摆放窗口时要把 `Move` 通知屏蔽掉**（`_adjustingFloating`），否则自己触发自己。
- **第一次分离时给的默认位置（间距 28px）刻意比吸附距离（18px）大**：不然一点"分离"
  就立刻被判成贴在边上，用户还没动手就看到"已吸附"。

主窗口最大化时，"贴在外侧"的位置会整个落到屏幕外。这时**不把窗口藏起来**，
而是钳进屏幕工作区当浮层——窗口突然消失比位置不完美更让人困惑；吸附关系仍然记着，
主窗口一还原它就回到外侧。同一条边上贴了两个窗口时，后者会沿边让开，不会叠在一起。

吸附状态与沿边偏移都会存进设置，下次启动按主窗口的位置重新贴回去。
`tools/SmokeTest` 第 11 步验的是：贴齐（左边界正好等于主窗口右边界）、
**移动主窗口后跟着走**、拖开脱离，以及下边也能贴（说明不只支持左右）。

#### 桌面歌词：一个"不该被注意到"的窗口

桌面歌词（`Ui/DesktopLyricsWindow.cs`）和侧栏那种悬浮窗看着像，其实是两套东西。
它天生要和别的程序抢屏幕，所以每条设定都得有理由：

**1）不设 `Owner`。** 设了之后主窗口一最小化 / 缩进托盘，它就会被一起带走——
而"主界面藏起来还能看歌词"正是它存在的理由。代价是主窗口关闭时要自己释放它。

**2）`WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE` + `ShowWithoutActivation`。**
不出现在 Alt+Tab 里（`ShowInTaskbar = false` 只管任务栏），并且点它、弹它都不激活自己——
全屏看视频时弹出歌词窗口绝不能把焦点抢走。

**3）锁定 = 鼠标穿透，用两条路一起保证。** 主路径是扩展样式
`WS_EX_TRANSPARENT | WS_EX_LAYERED`；`WndProc` 里再对 `WM_NCHITTEST` 回
`HTTRANSPARENT` 兜底（文档里那条路只对**同一个线程**的窗口继续往下传，不能只靠它）。

这里有个连带的坑：`Opacity` 被设成 100% 时 WinForms 会把 `WS_EX_LAYERED`
**摘掉**，而穿透要靠它。所以每次改完不透明度都得把扩展样式补回来：

```csharp
style |= WsExLayered;                       // 分层窗口是 TRANSPARENT 生效的前提
if (_locked) style |= WsExTransparent;
else style &= ~(long)WsExTransparent;
WriteExtendedStyle(Handle, new IntPtr(style));
SetLayeredWindowAttributes(Handle, 0, alpha, LwaAlpha);   // 改完样式要重灌 alpha
```

**4）宽度跟着文字自动伸缩，缩放时保持水平中心不动。** 歌词换一句就变宽变窄，
锚在左边窗口会左右乱跳。度量与绘制必须用**同一套 `TextFormatFlags`**，
而且都要带 `NoPadding`——少一个，量出来的宽度就比画出来的多几像素，
短句会被挤到第二行去。

**5）全屏时它不能跟着侧栏一起被收走。** `SetFloatingWindowsVisible(false)` 只管
侧栏和播放列表。另外主窗口进全屏时会把自己也设成置顶，两个置顶窗口之间按激活顺序排，
后置顶的会盖在上面——所以进全屏、以及主窗口切"窗口置顶"之后，都要用
`SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` 把它重新提上来（不能激活，否则视频丢焦点）。

**6）没歌词时显示 `♪ + 曲名`，不显示空白框。** 纯文本歌词没有时间轴，
在"一次只看一句"的窗口里没法定位，所以按"没有歌词"处理，
但也不会因此把一个空框留在屏幕上。

**6.5）背景透明是逐像素的，不是 `Form.Opacity`。** 这一点值得说清楚：
`Opacity` 只能让<b>整窗</b>均匀变淡，背景仍然是"一块变淡了的颜色"，
在深色桌面 / 视频上就是一块灰板。要"只有字，没有板"必须走
`UpdateLayeredWindow` + 32 位 ARGB 位图：

```csharp
var surface = new Bitmap(width, height, PixelFormat.Format32bppArgb);
using (var g = Graphics.FromImage(surface)) { g.Clear(Color.Transparent); /* 画字 */ }
// GetHbitmap(Color.FromArgb(0)) 拿到的 HBITMAP 是预乘过的，
// 正合 UpdateLayeredWindow 的要求；直接送原始位会得到发白的光晕。
var hBitmap = surface.GetHbitmap(Color.FromArgb(0));
UpdateLayeredWindow(Handle, screenDc, ref dest, ref size, memoryDc, ref src, 0, ref blend, UlwAlpha);
```

连带的三件事：

- **不能再设 `Form.Opacity`**：它内部调的是 `SetLayeredWindowAttributes`，
  和 `UpdateLayeredWindow` 是互相打架的两套机制（后调用的那个赢）。
  用户看到的"不透明度"改成 `BLENDFUNCTION.SourceConstantAlpha`，
  叠在字的逐像素 alpha 之上，语义还是"整窗浓度"。
- **内容不能再靠 `OnPaint`**：窗口的画面完全来自那张位图，
  `OnPaint` / `OnPaintBackground` 都留空，否则 WinForms 会往一个"根本没有背景"的窗口上刷底色。
- **命中试试也跟着变成逐像素的**：alpha 为 0 的地方点击直接穿透到下面的程序
  （这本身是想要的效果），所以拖动要去抓字本身。锁定（`WS_EX_TRANSPARENT`）时连字也不让点。

顺带两个必须自己处理的细节：

- **不能画在 96 DPI 的位图上**：字体按磅算，GDI+ 按 `Graphics` 的 DPI 换算像素。
  位图默认 96 DPI，125% 显示下量出来 / 画出来的字会比预期小一圈。
  位图和量文字用的 `Graphics` 都要 `SetResolution(DeviceDpi, DeviceDpi)`，两边一致。
- **⚠ `StringFormat.GenericTypographic` 里带着 `StringFormatFlags.LineLimit`。**
  它的意思是"只画完整的行"——矩形高度只要比行高差那么零点几像素，
  整行就**一个字都不画**，位图整张全透明。第一版就是这么踩的（"尺寸都对，就是没字"）。
  现在既把这个 flag 清掉，画的时候再给行高留 2px 余量。
- 描边（深色、8 个方向偏移各画一遍）不是装饰：没有背景板之后，
  白底网页上白字、亮画面上浅色字都会看不见，描边是唯一一个"不靠背景也能读"的办法。

**6.6）鼠标停上来才铺背景，而"什么时候算离开"不能问系统。**
平时背景全透明，用户看到的就是一串悬空的字，看不出哪里可以抓，所以鼠标停上来要铺一块背景
（不透明、圆角）。进入的判定很便宜：**背景透明时命中区域只有字的像素**，
所以"收到 `WM_MOUSEMOVE`"就等于"光标在歌词上"。

麻烦的是离开。第一版按常规写了 `TrackMouseEvent(TME_LEAVE)` + 处理 `WM_MOUSELEAVE`，
结果**背景刚画出来就被收掉**：命中区域是逐像素的，光标只要落在两行字中间那种透明像素上，
系统立刻认为"鼠标已经离开窗口"，`WM_MOUSELEAVE` 当场就到了。
（试试里连"只发合成消息"都不够——那个判定只看真实光标压在哪儿，
所以冒烟试试必须真的把光标挪过去、再挪走。）

最后改成自己判：

```csharp
// 进场：收到鼠标移动就算进来了，顺手起一个 150ms 的计时器
if (m.Msg == WmMouseMove) BeginHover();

// 出场：计时器里按"窗口矩形"判断，矩形之内都算还在歌词上
if (ClientRectangle.Contains(PointToClient(Cursor.Position))) return;
EndHover();
```

按矩形而不是按像素，正好把"两行字之间的空隙"也算进可抓范围；
拖动过程中光标可能被拖到窗口外，这时按 `_dragging` 跳过检查，背景留着。

**6.7）⚠ 背景"全透明"会让窗口几乎抓不住。** 逐像素命中试试是按 alpha 来的：
alpha 为 0 的地方点击会直接穿透到下面的程序——也就是说**只有笔画的像素能点**，
而用户把鼠标挪过去想拖它时，十有八九按在字缝里，表现就是"移动不了"。
（这条是用户报上来的，而当时的冒烟试试只验了"发消息给窗口它会不会动"，
绕过了命中试试，所以一直没发现。）

两个一起修：

1. **整块留一层 alpha = 1 的底**（`Color.FromArgb(1, 0, 0, 0)` 铺满客户区）。
   1/255 的变暗肉眼看不出来，但足够让整个窗口矩形都参与命中试试，
   于是边距、行间空隙都能抓。锁定时不铺——锁定就是"这个窗口在鼠标眼里不存在"。
   代价是这一圈边距内的点击不再穿透到下面的程序（窗口本身很紧，就一圈内边距）。
2. **冒烟试试改成用系统的命中试试来验**（`WindowFromPoint`）：
   在窗口范围内取边距、行间、正中、字上等好几个点，全都必须命中歌词窗口。
   这比"发消息"那一条更贴事实。实试 `WindowFromPoint` 是认 alpha 的：
   悬停之前透明边角命中的是别的窗口，铺了背景之后同一个点才命中歌词窗口。

**7）⚠ "不抢焦点"光靠窗口样式是不够的。** 窗口带 `WS_EX_NOACTIVATE`、
也覆盖了 `ShowWithoutActivation`，但**实试显示它的时候前台窗口仍然会变成它**——
条件是"前台本来就是本进程的窗口"（前台属于别的程序时，Windows 本来就不让它抢，
所以这个问题在随手一试时很容易漏掉）。抢走焦点的后果很具体：全屏视频收不到键盘、游戏里丢按键。

试过但**没用**的写法：在 `Show()` 后面顺着写一句 `SetForegroundWindow(原来那个)`——
实试激活会比 `Show()` 晚一步生效，那一句查的时候还是"没被抢"，等到真被抢时已经过去了。
在 `WM_ACTIVATE` 里判断"现在前台是不是我"也同样会漏（那一刻 `GetForegroundWindow()` 还没更新）。

最后是靠两条一起才成立的：

```csharp
// 1) 构造窗口时就把"该还给谁"记下来（这时句柄都还没建，前台一定还是别人的）
_focusReturnTarget = GetForegroundWindow();

// 2) 收到"不是用户点出来的"激活就还回去；再补一次延迟核对，兜住"激活比 Show() 更晚"
//    ⚠ 注意这里必须判 == WA_ACTIVE，写成 != 0 会把点击引起的激活也还掉 —— 见下面第 8 条
if (m.Msg == WmActivate && m.WParam.ToInt64() == WaActive) GiveBackForeground(force: true);
BeginInvoke(new Action(() => GiveBackForeground(force: false)));
```

这条检查在冒烟试试里**先把主窗口推到前台**（`form.Activate()`）再验——
不这么做的话它就会随环境时灵时不灵，而"时灵时不灵"的检查等于没检查。
推不上去时（前置条件不成立）会打印一行说明，让人知道这一次检查是空的。
把 `_focusReturnTarget` 那一行去掉做**变异验证**：第 15 步 3/3 次都以
`显示桌面歌词把前台窗口抢走了（前置条件成立=True）` 失败。

**8）⚠ 上一条的补丁把鼠标点击一起吃掉了：还前台要区分"是不是用户点出来的"。**
这是 6.7 之后紧接着踩的坑，而且**是上一条修复自己造出来的**：

```csharp
// 原来是这样：任何激活都还回去
if (m.Msg == WmActivate && m.WParam.ToInt64() != 0) GiveBackForeground(force: true);
```

用户点这个窗口时，系统先激活它（`WM_ACTIVATE`，wParam = `WA_CLICKACTIVE`），
然后才轮到左键"按下"。而上面那行在激活的当口就把前台还给了别的窗口，
**那次点击被整个取消**——`WM_LBUTTONDOWN` 再也不会送到窗口。
表现就是：窗口看得见、`WindowFromPoint` 说点得到、移动和抬起消息都到，
唯独"按下"永远不来，用户的感觉就是**点不动、拖不动**（锁不锁定都一样）。

改法是按 wParam 分流：

```csharp
private const int WaActive = 1;   // 非点击引起的激活（Show() 之后系统补上来的）
if (m.Msg == WmActivate && m.WParam.ToInt64() == WaActive) GiveBackForeground(force: true);
```

于是三种诉求同时成立：**显示它不抢焦点**（`WA_ACTIVE` 还回去）、
**点它能拖动**（`WA_CLICKACTIVE` 放行）、**不进 Alt+Tab**（`WS_EX_TOOLWINDOW`）。

排查时先怀疑了 `WS_EX_NOACTIVATE`（加上它点击送不到）和 `WS_EX_LAYERED`，两个都摘掉试过、
都不管用；直到把那句"还前台"注掉，真鼠标拖动立刻通了。
教训是**别急着怀疑系统，先怀疑自己上一个补丁**。

对应的断言现在是硬的：真鼠标按下 + 拖动之后窗口必须跟着走。
把那行改回"任何激活都还"做**变异验证**，第 15 步 2/2 次都以
`真鼠标拖不动（…；本线程收到 按下0 移动8 抬起1）` 失败。

**9）导入的字体文件复制一份再用。** `PrivateFontCollection.AddFontFile` 会**占用**字体文件，
直接引用的话用户就删不掉自己的字体了；而且设置里只存字体族名，
不复制一份的话下次启动根本找不到它。所以导入 = 复制进 `<数据目录>\fonts` + 装进进程，
原来的文件碰都不碰（试试里就是靠"导入之后还能把原文件删掉"来验这一点的）。
另外：同一个文件重复导入是**幂等**的——判断"这个文件里有哪些字体族"用的是一个临时集合，
不能靠"长期集合里新增了哪些"来判断，否则第二次导入会被误判成"里面没有能用的字体"。
读不出来的字体文件要**立刻删掉**，否则每次启动都会再失败一遍。

`tools/SmokeTest` 第 15 步走的是**用户会走的那条路**（从「视图 → 桌面歌词」菜单点下去），
验：跟着进度换句（含最后一句之后不再有下一句）、纯文本歌词退回曲名、
排版跟着字号与"显示下一句"变、不透明度被钳在 20~100、锁定后扩展样式真的是
`TRANSPARENT|LAYERED` 而解锁后清理干净、右键菜单在 `WS_EX_NOACTIVATE` 窗口上
**真的能弹出来**、能被鼠标拖动（发真的鼠标消息）而锁定之后拖不动、不抢前台、
`Ctrl+D` 能开关、进全屏时窗口还在（**对照组**：同一时刻侧栏悬浮窗必须已经被收起，
否则证明不了它被区别对待）、窗口始终留在屏幕工作区内，
以及**直接检查它推给系统的那张位图**——四个角的 alpha 必须是 0（背景真透明）、
中间在鼠标停上来之后必须变成不透明（悬停背景铺出来了）、鼠标挪走之后又回到全透明，
另外不透明像素要上千个（字真画上去了）。这条断言比原来用 `DrawToBitmap` 更贴事实：
内容是 `UpdateLayeredWindow` 推上去的，`WM_PRINT` 那条路拿不到任何东西。
（悬停那一条要真的挪动光标，理由见上面 6.6。）
字体那一部分另验：两处歌词一起换、不存在的字体族安静退回默认且两处一致、
导入之后原文件仍可删除、重复导入幂等、垃圾文件与错误扩展名都被挡掉且不留残留，
以及**字体菜单里只有"默认 / 导入 / 已导入的字体"**（拿系统字体列表反证没有被混进来）。

### 界面：自绘与排版

GDI+ 与 GDI 的差别、DPI 缩放、对话框排版、配色取用、图标。

#### 自绘控件不要在绘制里 new Font

`Font` 是 GDI 对象。若在 `OnPaint` 里每次都用 `new Font(Font, FontStyle.Bold)` 造一个加粗字体，
**每帧都会漏一个 GDI 句柄**。正确做法是缓存，并且只在父字体变化（`OnFontChanged`）
或尺寸变化时重建，最后在 `Dispose` 里释放。`LyricsView` / `CoverView` 都是这么做的。

#### 均衡器对话框必须自己按 DPI 缩放

项目整体用 `AutoScaleMode.Dpi`，`EqualizerDialog` 里的坐标却曾经全是写死的 96 DPI 像素，
而字体是点值、会随 DPI 变大。结果在 125% / 150% 显示下文字撑大而位置不动，
右侧的 dB 数值和底部按钮会被挤出客户区——**看不见，也点不到**。

现在对话框维护一张"设计坐标表"，由 `ApplyDpiLayout()` 按 `DeviceDpi / 96` 统一摆放，
并在 `OnHandleCreated` 与 `OnDpiChangedAfterParent` 里重算（构造函数里 `DeviceDpi` 还不可信）：

```csharp
private void Place(Control control, int x, int y, int width, int height)
{
    // AutoSize 的控件宽高由字体决定，这里只管位置。
    var bounds = control.AutoSize ? new Rectangle(x, y, 0, 0) : new Rectangle(x, y, width, height);
    _layout.Add((control, bounds));
    control.Bounds = bounds;
    Controls.Add(control);
}
```

实试（这台机器 125%）：客户区 575×633，控件最大右边界 558 / 下边界 613，无越界。

#### ⚠ 对话框排版：别用"行数 × 行高"估算

`Ui/InputDialog.cs` 是"服务地址""鉴权密钥""网络串流"共用的输入框。它原来按
"提示有几行 + 额外行数 × 18 像素"算高度，而服务地址那段提示有**四行**，
估算少了一行，文本框正好压在最后一行上（就是"挡住了"）。

现在每一段都接在上一段的**真实高度**下面：`Label.PreferredSize` 给出这段文字在这个字体下要多高，
输入框摆在 `padding + labelHeight + gap`，按钮再跟在输入框下面，
客户区高度由最后一段反推。顺带补上了 DPI 缩放（`DeviceDpi / 96`，
并在 `OnHandleCreated` / `OnDpiChangedAfterParent` 里重排一次）——
固定坐标在 125% 缩放下会越挤越紧，因为文字会随 DPI 变大而坐标不会。

冒烟试试里有一条专门盯这个：四行提示下要求 `输入框.Top >= 提示.Bottom`、
掩码要生效、所有控件都在客户区内。

#### 提示文字不要借用"禁用菜单"的颜色

侧栏里"没有找到歌词""侧栏太窄"这类提示，以及未选中的标签文字，原来用的是
`MenuDisabledFore`。那是**禁用菜单项**的颜色，浅色主题下是 `#A0A0A0` 画在 `#F0F0F0` 上，
对比度只有 **2.29:1**，当正文用太淡了；深色 / OLED / VLC 橙三套也只有 2.96 / 3.04 / 3.16:1，
同样不达标。

现在配色表里多了一项 `HintFore`，取值都按"在 `PanelBack` 上不低于 4.5:1"
（WCAG AA 正文标准）挑过：

| 主题 | 旧（`MenuDisabledFore`） | 新（`HintFore`） |
| --- | --- | --- |
| 浅色 | 2.29:1 | **4.65:1** |
| 深色 | 2.96:1 | **4.71:1** |
| OLED 纯黑 | 3.04:1 | **5.51:1** |
| VLC 橙 | 3.16:1 | **5.03:1** |

同理，歌词控件的"悬停高亮"曾经被 `ApplyPalette` 赋成了和常态完全相同的颜色
（字段初始值本来是不同的 `Color.White`，一换主题就被永久拉平），于是"鼠标移上去这一行会变色"
的提示彻底消失——光标还是手型、点击也还能跳转，就是看不出哪一行可以点。现在悬停用
`PlayingFore`，四套主题下都与常态色不同。

#### exe 图标与运行时图标是两套

窗口图标和托盘图标是**运行时用 GDI+ 现画**的（`Ui/MediaIcons.cs` 的 `AppIcons.For`：
圆角方块 + 白色播放三角，颜色跟着主题的强调色走），好处是五套主题各有各的图标、
任意 DPI 下都清晰。

但**资源管理器里显示的、以及固定到任务栏/开始菜单时用的那个图标，必须是 exe 里的
`RT_GROUP_ICON` 资源**，运行时怎么画都影响不到它。所以还需要一个真正的 `app.ico`，
由工程文件的 `<ApplicationIcon>` 交给编译器嵌入。两者图案保持一致。

`app.ico` 由 `tools/IconGen` 生成（已经提交，平时不用跑）：

```powershell
dotnet run --project tools/IconGen/IconGen.csproj
```

它打包 7 种尺寸（16/24/32/48/64/128/256），全部用 32 位 DIB 条目，**只有 256 那张用 PNG**。
原因是实试发现的：Vista 以后资源管理器确实支持 ICO 内嵌 PNG，但 **.NET 的
`System.Drawing.Icon` 读不了 PNG 条目**——对它调用 `ToBitmap()` 会抛
"Requested range extends past the end of the array"，只能回退到能解析的最大 DIB。
256 那一档只有资源管理器的"超大图标"视图会用到、走的是 shell 自己的解码，
而 .NET 的 `Icon` 本来也拿不到 256（实试请求 256 返回的是 128），
所以只有它用 PNG：文件从 364 KB 降到 103 KB，而 .NET 侧的可读尺寸一个都没少。

### 界面：健壮性与交互细节

窗口消息、菜单生命周期、线程判断、按键归属——都是"平时看不出、出问题很难查"的地方。

#### ⚠ `WndProc` 里不能对任意消息调用 `WParam.ToInt32()`

64 位下 `WParam` / `LParam` 经常是句柄甚至指针，值会超出 `Int32` 范围。
曾经写成"每条消息都先解析一遍按钮 id"，结果 `ToInt32()` 抛 `OverflowException`，
表现为一个"程序遇到了未处理的错误"弹框（真实踩过）。

正确做法是**先按 `m.Msg` 分流，再读取参数，并且一律用 `ToInt64()`**：

```csharp
switch (m.Msg)
{
    case TaskbarThumbnailButtons.WmCommand:
        switch (TaskbarThumbnailButtons.ResolveClick(m.WParam)) { ... }
        break;
    case WmHotKey:
        // ResolveHotKey 内部用 wParam.ToInt64() 再掩码
        break;
    case WmAppCommand:
        // ResolveAppCommand 内部用 lParam.ToInt64() 再掩码
        break;
}
```

`tools/SmokeTest` 会用反射直接调用 `WndProc`，喂进 `0xFFFFFFFF00000000` 这种
超大句柄参数，确认不再溢出。

#### ⚠ `new T[n]` 得到的是 n 个 `null`：均衡器对话框曾经根本打不开

```csharp
private readonly FlatSlider[] _bandSliders = new FlatSlider[EqualizerCatalog.BandCount];
private readonly Label[] _bandValues = new Label[EqualizerCatalog.BandCount];
```

数组元素**从来没有被实例化过**，而 `BuildLayout` 直接把 `_bandSliders[band]` 传给 `BuildRow`，
`BuildRow` 第一句就是 `slider.Minimum = MinimumGain;` —— 点一下「均衡器」立刻
`NullReferenceException`，对话框完全打不开，只会弹出未处理错误的提示框。

`tools/SmokeTest` 第 10 步现在会**真的把对话框实例化并打开**，既断言 11 条滑块都在，
也逐个控件比对边界（见下一条）。这类"从来没被真正打开过的窗口"是最容易藏 bug 的地方。

#### ⚠ 文本框里的按键不要当快捷键（以及怎么"真按键"试出来）

单键快捷键（空格 / `S` / `M` / `V` / `G`… / 方向键 / `Delete`）都在 `MainForm.ProcessCmdKey`
里统一处理。问题是 **WinForms 会把同一条 `WM_KEYDOWN` 既交给焦点控件、又交给窗体的
`ProcessCmdKey`**，而 `ProcessCmdKey` 一旦 `return true`（"这个键我处理了"），
那条按键就被整个吃掉：**字符进不了搜索框，播放控制的动作却照跑**。

实试（真按键）后果是：

- 在搜索框里**根本打不出空格**——"空格分隔多个关键字"这个搜索用法实际上是坏的，
  而且每按一次空格还会把播放暂停；`s` 会停止、`m` 静音、`v` 关字幕、`g/h/j/k` 改延迟；
- 按 `Delete` 会**删掉播放列表里选中的条目**（状态栏显示"已从播放列表移除 1 项"）；
- 方向键不会在文本框里移动光标，而是去快进快退 / 调音量。

修法是让位：判据取**消息的落点**（`Control.FromHandle(msg.HWnd) is TextBoxBase`），
只有拿不到真实消息（试试用反射直接调）时才退回看当前焦点；放行 Ctrl / Alt 组合键与 `F1`~`F24`：

```csharp
if (IsTypingTarget(msg) && !IsCommandKeyWhileTyping(keyData))
    return base.ProcessCmdKey(ref msg, keyData);
```

这个 bug 能藏这么久，是因为**原来的搜索试试是直接 `search.Text = token` 赋值的**，
从来没走过按键路径。现在的回归检查用 `PostMessage` 往搜索框句柄投真实的
"按下 + 抬起"，并且反向确认没有矫枉过正（把 `Delete` 投给列表时**仍然要**删掉选中项）。

> ⚠ 合成按键的 `lParam` **必须按真实按键填**（扫描码 + 抬起时的 bit30/bit31，扩展键还要 bit24）。
> 图省事写成 `lParam = 0` 时，那条 `WM_KEYUP` 看起来像又一次按下，
> 一次"按下 + 抬起"会往文本框里塞进**两个**字符——这条弯路本身就是靠
> "只发 KEYUP 不进字 / KEYDOWN + 真实 KEYUP 进一个字 / KEYDOWN + lParam=0 的 KEYUP 进两个字"
> 三个对照实验定下来的。

#### 菜单项上带当前值，能拖动就别让人点 15 次

桌面歌词的字号和不透明度原来只有"放大 / 降低"两项：字号 12~96、每次 2 磅
（从 30 调到 60 要按 **15** 次），浓度 20~100、每次 5%（**16** 次），
而且菜单上**看不到现在是多少**。现在菜单项直接写成
`外观（字号 30 磅 · 浓度 88%）…`，点开是一个带两条滑块的小对话框，
拖动时**真的在改屏幕上的歌词**（那块歌词就是预览），所以"取消"要把原值写回去、
不能只关掉对话框。快速微调的"放大 / 缩小"仍然留着。

#### ⚠ `DropDownItems.Clear()` 不会释放菜单项

字幕轨道、音轨、"最近播放"三个下拉菜单都是**每次状态变化就整体重建**的。原来写的是
`DropDownItems.Clear()` 之后重新 `Add`，看起来没问题，但 WinForms 的 `Clear()` 只是把项
从集合里摘下来，**不调用 `Dispose`**（实试移除后 `IsDisposed` 仍是 `false`，只是 `Owner`
变成了 `null`）。长时间使用会攒下大量 `ToolStripItem` 以及它们在展开时创建的下拉窗口句柄。

现在统一走 `ClearMenuItems()`：先复制一份快照（`Dispose` 会改动集合，直接 `foreach` 会抛
"集合已修改"），逐个 `Dispose` 之后再 `Clear()`。

同一批里还补了三处原生资源的释放：列表加粗行用的 `_playingItemFont`（此前从未 `Dispose`）、
`AppIcons` 缓存里由 `GetHicon()` 产生、`Icon.FromHandle` 不接管所有权的 HICON
（每套主题色一个），以及 `TaskbarThumbnailButtons` 里从未 `Release` 的 `ITaskbarList3` RCW。

#### ⚠ 判断"是否在 UI 线程上"不能用 `InvokeRequired`

`PlayerEngine` 把 libvlc 回调派发回 UI 线程时，原来写的是最常见的那套：

```csharp
if (_ui.InvokeRequired) _ui.BeginInvoke(action, null);
else action();                                  // ← 这里会在原生线程上就地执行
```

问题在于 **`Control.InvokeRequired` 在控件还没创建句柄时返回 `false`**。
主窗口的构造函数里就会打开命令行传入的媒体，而那一刻句柄可能还没建好，
于是 libvlc 回调线程上的 `Opening` / `Playing` 会**直接在原生线程上**跑进
`UpdateTransportState` 之类的地方——跨线程操作 `ToolStrip` / `ListView`。

这不是理论推试：冒烟试试实际撞到过一次，栈顶是

```
System.Windows.Forms.ToolStripStatusLabel.OnTextChanged
播放器.MainForm.UpdateTransportState()          MainForm.cs:1734   ← lblMediaInfo.Text = ...
播放器.MainForm..ctor(String[], SingleInstance) MainForm.cs:89
```

而且它**偶发**——要刚好在构造那一小段时间里收到 libvlc 回调才会触发，
30 次左右才撞到 1 次。

修法是改用**构造时记下的 UI 线程 id**，并把暂时派发不出去的事件排队，
等窗口建好句柄后由 `MainForm.OnHandleCreated` 补发（事件不丢）：

```csharp
private readonly int _uiThreadId = Environment.CurrentManagedThreadId;

if (Environment.CurrentManagedThreadId == _uiThreadId) { action(); return; }
try { _ui.BeginInvoke(action, null); }
catch (InvalidOperationException) { /* 句柄还没建好：先排队 */ }
```

`tools/SmokeTest` 第 14 步直接钉住这条：新建一个**没有句柄**的窗体、从后台线程
调用 `SetState`，断言事件**不会**在该后台线程上执行；句柄就绪后调用
`FlushPendingUiActions()`，断言事件被补发且落在 UI 线程上。这条做过**变异验证**：
把 `Post` 改回 `InvokeRequired` 版本，第 14 步立刻以
`引擎事件在原生回调线程（46）上就地执行了、没有派发回 UI 线程` 失败。

#### 交互细节：哪些地方必须让出空格键

给侧栏标签条加键盘操作时，**不能接管空格**：空格在这个程序里一直是"播放 / 暂停"，
焦点跑到侧栏上时也应保持这个习惯。所以标签条只认 `Enter` 切换、`Ctrl+Enter` 折叠，
并且用 `IsInputKey` 声明自己处理方向键 / `Home` / `End`，避免被窗体的"快进快退"抢先。

`FlatSlider` 的键盘支持是**可选**的（`KeyboardEnabled`）。传送栏上的进度条和音量条依赖
窗体级的方向键处理，打开键盘支持反而会让"快进快退"失灵；均衡器对话框是模态的，
窗体的快捷键照顾不到它，那里的 11 条滑块就必须自己接受键盘。

### 系统集成

托盘、任务栏、单实例转发。

#### ⚠ 自定义消息号不享受 WM_COPYDATA 的跨进程编组

本批功能里最难排查的一个坑。

跨进程传数据时，**只有系统定义的 `WM_COPYDATA`（固定值 `0x004A`）**会被 USER32 编组：
系统把发送方的数据映射到接收方地址空间，接收方拿到的 `lParam` 指向自己进程内的副本。
如果像最初那样用 `RegisterWindowMessage` 注册一个自定义消息号、再往 `lParam` 里塞
`COPYDATASTRUCT`，**编组根本不会发生**——接收方拿到的是发送方进程里的裸指针地址，
一读立刻**原生访问冲突 `0xC0000005`，进程直接消失**，托管异常处理器完全拦不住。

判断依据很直观：**接收方打印出的 `lParam` 与发送方打印的 `header` 指针完全相同**，
就说明数据没被搬过来。改用 `0x004A` 之后两侧指针不同、数据可读，功能正常。

配套三点：
- 用 `COPYDATASTRUCT.dwData` 放一个魔数来区分"是不是自己发的"。`WM_COPYDATA` 任何程序都能
  往我们窗口里发，魔数不符就当没看见，顺便也避免了拿坏数据去解析。
- 发送必须用同步的 `SendMessage`（编组只在这条路径上发生）。为了不让对方卡死把自己也挂住，
  先发一条不需要编组的 `WM_NULL`，用 `SendMessageTimeout` + `SMTO_ABORTIFHUNG` 探活，
  确认对方在响应再发数据。
- 找不到接收窗口是正常情况（第一个实例可能还在启动），要按 100ms 间隔重试到超时为止。

#### 托盘图标：不要动 ShowInTaskbar

"收进托盘"只调用 `Hide()`。**千万不要**顺手把 `ShowInTaskbar` 设成 `false`：
改这个属性会让 WinForms 销毁并重建窗口句柄，而全局媒体键、任务栏缩略图按钮、
单实例登记用的窗口属性、视频输出窗口全都挂在原句柄上，会一起失效。
窗口隐藏之后任务栏按钮本来就会自动消失，不需要额外做什么。

另外 `NotifyIcon.Text` **上限 63 个字符**，超长会抛异常，显示曲名时必须先截断。

#### 任务栏缩略图按钮的 COM 互操作

`ITaskbarList3` 的方法顺序必须和系统头文件完全一致，否则 vtable 会错位。代码里把
`ITaskbarList` / `ITaskbarList2` / `ITaskbarList3` 的全部方法按原顺序声明齐了，
**后续维护时不要删改顺序**。所有调用都包了容错，系统不支持时自动降级为没有这组按钮。

#### 系统媒体控件的 WinRT 互操作（`Ui/SmtcSession.cs`）

**1.3.0 那一版是"手写 vtable 的 COM"**，1.4.0 起改成**引 WinRT 投影**
（目标框架 `net8.0-windows10.0.19041.0`）：曲名 / 歌手 / 封面 / 进度 / **按钮事件**
都是普通属性与事件，不必再自己声明 vtable、也不必自己揉 HSTRING。
四处值得记下来的事：

1. **只有一处还得手写**：`GetForWindow` 属于**头文件里的互操作接口**
   （`SystemMediaTransportControlsInterop.h`，IID `ddb0472d-…`），投影里没有它。
   所以照旧自己声明一次（`IUnknown` + `IInspectable` 那三个占位方法 + `GetForWindow`），
   从 `RoGetActivationFactory` 拿到工厂，再拿裸指针用
   `WinRT.MarshalInspectable<SystemMediaTransportControls>.FromAbi` 换成投影对象。
   ⚠ 这个声明里的**方法顺序仍然不能动**：错一个槽就调到别的方法上。
2. **当初为什么绕远路（留作档案，别再踩）**：.NET 运行时不支持两个 WinRT 编组方式
   （都是实测报错挣来的）——`UnmanagedType.IInspectable` /
   `ComInterfaceType.InterfaceIsIInspectable` →
   `Marshalling as IInspectable is not supported in the .NET runtime.`；
   `UnmanagedType.HString` → `Cannot marshal 'parameter #1'`。
   手写 COM 那版只能拿普通方法占住第 4~6 个槽、字符串走 `WindowsCreateString` 自己管。
   更关键的是**按钮事件**：`ButtonPressed` 要一个 WinRT 委托，托管委托包出去的 CCW 是
   `IDispatch` 布局、槽位对不上（按一下就是栈错乱），所以那版索性把
   `IsPlayEnabled` 那几个开关一律关掉——宁可不显示按钮，也不显示一排按不动的按钮。
   投影把这些全部变成一行普通代码，这也是"改 TFM"换来的东西。
3. **封面喂给系统只能走文件**：`DisplayUpdater.Thumbnail` 收的是
   `RandomAccessStreamReference`，而它只能从 `StorageFile` 造（异步）。
   于是内嵌封面图先落到数据目录的临时文件（`smtc-cover.jpg` / `.png`…）；
   **同目录的外挂封面（`cover.jpg` / `folder.jpg`…）本来就在盘上，直接用那个文件**，
   不必再抄一份。喂过之后**必须调一次 `DisplayUpdater.Update()`**，不然系统那边不刷新。
   ⚠ 切到**没有封面**的那一首时要**显式清一次**（`Thumbnail = null` + `Update()`），
   否则音量弹窗里会一直挂着上一首的封面。挑哪张外挂封面由 `Core/SidecarCover.cs` 定，
   和侧栏封面、"要不要去网上找封面"是**同一份判定**（`cover.jpg` 优先于 `album.jpg` /
   `folder.jpg`，不看文件系统的枚举顺序）。
4. **验到哪一层**：冒烟读的是**系统那个对象本身**（`IsEnabled` / `PlaybackStatus` /
   `Title` / `Artist` 的 getter 都真的去问系统），封面那一段还验了
   "交给系统的文件被系统读了"（`CoverSet`）；但**系统界面上画没画出来、按钮按下去系统
   有没有把事件送过来，只能人眼看**。另外有一个坑就是靠这条断言当场抓出来的：会话在
   `OnLoad` 里建，而启动那一首的元数据在**构造函数**里已经推过（那时还没有会话）→
   第一首永远是空的；现在建好后补推一次。

### 数据与文件

原子写、备份、歌单文件的位置与"不自动写回"。

#### 设置与历史必须原子写

`File.WriteAllText` 是"先截断、再写"：写到一半断电或进程被杀，留下的就是半截 JSON。
而 `AppSettings.LoadFrom` 和 `PlaybackHistory.Load` 的读取端都是"读坏了就静默退回默认值"，
于是一次坏运气就等于把窗口尺寸、主题、音量、`LastPlaylist`（整份播放列表）、
所有续播位置**无声清零**。

现在统一走 `Core/SafeFile.cs`：写同目录下的临时文件（名字带随机后缀，两个写者也不会互相
覆盖半个文件）→ `Flush(true)` 推到底层设备 → `File.Move(overwrite: true)` 原子改名覆盖。

配套两点：

- **不再静默**。读不出来时把坏文件改名成 `xxx.corrupt` 留档，并在返回的对象上挂一个
  `LoadWarning`，主窗口启动后显示在状态栏里。以前用户只会发现"设置全没了"，不知道发生过什么。
- **历史的定期落盘移到线程池**。播放时每 20 秒要落一次盘，最多 2000 条记录序列化成缩进 JSON
  是几百 KB，整段放在 UI 线程上会周期性顿一下。现在只在 UI 线程取快照（`SaveInBackground`），
  写文件交给线程池；退出路径仍然用同步的 `Save()`，因为进程马上就要结束，不能只排队。

> 第 14 步能验证"内容被替换、不留下残留 `.tmp`"这个可观察契约，但**验证不了原子性本身**
> ——那需要在写到一半时杀掉进程，做不到可靠复现。原子性是靠实现方式保证的。

#### 多个歌单：一个歌单一个文件，而且不自动写回

"保存多个播放列表"没有做成一个大 JSON，而是**一个歌单一个标准 m3u8 文件**，
放在 `数据目录\播放列表\`（`Core/PlaylistLibrary.cs`）。理由是这份数据用户能直接看见：

- 资源管理器里就能看到、改个名就是改名、拷给别人就能用、别的播放器也能打开；
- 坏了只坏一个歌单，不会连累设置文件（`settings.json` 坏了会连带丢掉窗口尺寸与主题）；
- 排查问题时用记事本打开就能看出哪里不对。

几个刻意定下来的行为：

- **不自动写回**。改了列表只把标题标成 `【歌单名·未保存】`，只有用户点保存才动磁盘上的歌单。
  判断"改没改"用的是播放列表模型上新加的 `ContentChanged`，而**不是**原来的 `Changed`：
  后者把"开始播下一首"也当成一次变化，用它就会变成"每播一首歌都提示歌单有改动"。
  冒烟试试钉住了这一点（变异：让 `SetCurrent` 也发 `ContentChanged`，立刻失败）。
- **载入会替换当前列表**（这是"切换歌单"的直觉），替换前问一句；有未保存改动时给
  "先覆盖保存 / 不保存直接换 / 取消"三个选择。文件已经不在了的条目单独计数上报，
  **不静默少几首**（`PlaylistFile.Load` 会过滤掉不存在的文件，那份语义留给"打开别人的 m3u"；
  歌单库走的是新加的 `PlaylistFile.ReadPaths`，只解析不过滤）。
- **导入时重新写一遍，而不是原样拷贝**。外面拿来的 m3u 常写相对路径
  （`../音乐/01.mp3`），那是相对**它原来所在的目录**的，文件一拷进歌单库就全部指错地方。
  导入时先按原目录解析成绝对路径，再写回歌单库（实试：原样拷贝的话 5 首一首也找不到）。
- **名字不静默替换**。非法字符（`/ \ : * ? " < > |`）直接告诉用户是哪个字符不能用，
  而不是替他改成下划线——改完他就找不着了。Windows 保留名（`CON`、`COM7`、连 `CON.m3u8`）
  和结尾的点号也一并处理（点号会被悄悄去掉，因为 Windows 自己也会吃掉它）。
- **自然顺序**：`歌单2` 排在 `歌单10` 前面。纯字符串比较会反过来，用户一眼就觉得是乱的。
- 歌单窗口底下那行明细里有**完整路径**，必须给它 `MaximumSize` 限宽：`AutoSize` 的 `Label`
  不限宽会一路撑到 1000 多像素、直接超出客户区（这条是冒烟试试当场量出来的）。

### 构建、部署与试试

只带 x64 的 libvlc；假 HTTP 服务器为什么必须把响应写完。

#### ⚠ 假 HTTP 服务器：不回完请求头就关连接，客户端会读不到响应

搭上面那个"假 LrcAPI"时踩的坑，记下来免得下次再花时间：
最初只读了请求行就把 socket 关掉（`using var client` 一出来就 Dispose），
结果客户端报 `Error while copying content to a stream.`，
而现象看起来完全像是"客户端根本没发第二个请求"（请求日志里只有第一条）。

原因是接收缓冲区里还留着没读完的请求头，Windows 会发 **RST 而不是正常 FIN**，
把刚写出去、还没被读走的响应数据一起冲掉。修法是**先把整个请求头读到空行**，
回完响应再 `Shutdown(SocketShutdown.Send)` 半关连接。

#### ⚠ 只复制 x64 那一套 libvlc

`VideoLAN.LibVLC.Windows` 自带三个开关，默认值是按 `$(Platform)` 判断的：

```xml
<VlcWindowsX64Enabled Condition="... ('$(Platform)' == 'x64' OR '$(Platform)' == 'AnyCPU')">true</...>
<VlcWindowsX86Enabled Condition="... ('$(Platform)' == 'x86' OR '$(Platform)' == 'AnyCPU')">true</...>
<VlcWindowsArm64Enabled Condition="... ('$(Platform)' == 'ARM64' OR '$(Platform)' == 'AnyCPU')">true</...>
```

本项目只写了 `<PlatformTarget>x64</PlatformTarget>`，**`$(Platform)` 仍然是 SDK 默认的
`AnyCPU`**，三个条件同时成立，于是三套原生库全被复制进输出目录（280 MB / 1269 个文件）。
实试三个 `libvlc.dll` 的 PE `Machine` 分别是 `0x8664`(x64) / `0x14C`(x86) / `0xAA64`(ARM64)：
x64 进程**根本无法加载**另外两个，LibVLCSharp 也是按进程架构只挑 `libvlc\win-<arch>` 一个目录。
在工程文件里显式关掉另外两套即可，输出降到 102 MB / 437 个文件。

> 这里用**属性**而不是"生成后再删目录"是有原因的：`RemoveDir` 只删结果，
> 那些文件仍然在 `Content` 的复制列表里，**每次增量生成都会把删掉的 178 MB 重新复制一遍**。
> 关掉开关则是从一开始就不复制。

### 边界：明确不做的事

- **不做重写 / 大爆炸式改造**：每一步都要"行为不变 + 全量冒烟试试通过"。
- **不引 DI 容器 / MVVM 框架**：单窗口本地播放器，收益不抵学习与调试成本。
- **不为分层而分层**：要削的是耦合与重复，不是行数；一个只做转发的类不算"解耦"。
- **不加媒体库 / DLNA / 歌词翻译 / 视频滤镜 / 皮肤**：功能已经够用，
  再加下去复杂度会超过现有架构的承受能力。
- **不自动写回歌单、不往媒体目录写文件**：在线取回的歌词与封面只在本次运行有效，
  想离线复用就自己另存一份 `.lrc`。
- **不为试试去改产品行为**：安全检查要能红，但"跳过"必须如实说出来。

## 已知限制与可继续做的方向

> 这一节回答"**有没有这个问题、要不要改**"；"**什么时候改、按什么顺序、什么条件才动**"
> 记在 [docs/维护手册.md](docs/维护手册.md) 第 3 节的「更新节奏」里（带触发条件与放弃判据），
> 下一版（1.2.1 / 1.3.0）具体做什么见 [docs/1.3.0计划.md](docs/1.3.0计划.md)。

- 播放列表复用同一个 `ListView` 整体刷新（只是去掉了循环里的重复重建），几万条的规模下
  仍会偏慢；需要的话可以改成 `VirtualMode`。
- **画面旋转是靠"换一个 libvlc 内核"实现的**（1.3.0 批次 B）：libvlc 3 的 `transform` 滤镜
  **只认内核级选项**（`--video-filter=transform` + `--transform-type=…`），媒体级选项四组写法
  实测全不生效（详见 [docs/1.3.0计划.md](docs/1.3.0计划.md) 的 B-2），所以"按文件记住旋转"
  只能按旋转值各留一个内核（惰性创建、最多 6 个）。代价与边界：
  ① 切换旋转时**有几百毫秒的停顿**（媒体要重载）；
  ② 装了硬件解码的机器上滤镜会打 `Unsupported pixel size 0 (chroma DX11)`，
  本次实测**画面照样转**，但换一种编码 / 位深会不会退化成"不转"没有逐种验过；
  ③ 只转画面本身，窗口比例、字幕、桌面歌词都不跟着转。
- **没有画面调整（亮度 / 对比度 / 饱和度 / 色相 / 伽马）**。这是有意留空的：
  libvlc 3.0.23 在这台机器上怎么调都不影响输出画面（五种办法逐一实试，见上文），
  与其给几个不起作用的滑块，不如不做。
- **逐帧前进/后退走的是"按帧长定位"而不是 libvlc 的 `NextFrame()`**，因为后者实试无效。
  定位落点是精确且可复现的：同一个时刻来回 seek，像素差是 **0.00**；后退 5 帧能像素级回到
  出发的那一帧；连按 5 次（两次之间不留间隔）也落在同一帧上——**不存在"连按会丢定位"**。
  只有可变帧率（帧时间戳不均匀）的片源可能偶尔差一帧。
- **暂停时画面上显示的那一帧，并不等于 `MediaPlayer.Time` 所指的那一帧**：
  实试暂停后画面本身是稳的（间隔 700ms 连拍两张，像素差 0.00），
  但再 seek 到时钟所指的同一时刻，画面会变（像素差 11 左右）——**vout 比时钟滞后约 100~200ms**。
  用户按逐帧不受影响（它就是按绝对时刻定位的），但"拿暂停时截的那张图当基准"是不成立的，
  拿它去比就一定会误判。
- **相邻两帧可能几乎一模一样**：白板 / 静态课件类视频实试一帧只差 0.00~0.54，
  所以"按一下看不出变化"往往是内容问题而不是功能问题，要走 5 帧（约 166ms）才看得出明显区别。
- 去隔行已接到 libvlc 的去隔行接口，9 个模式都能设进去；但手上没有隔行素材，
  **实际画面效果没有验证过**，这一点如实说明。
- 标签解析覆盖 ID3v2 / FLAC / MP4 / ID3v1；**Ogg / Opus 的 Vorbis comment 与
  WMA / APE 的标签没有解析**，这些格式的歌词请放同目录同名 `.lrc`（外挂歌词对所有格式都有效）。
- 歌词只做显示与跳转，没有做歌词编辑和在线歌词搜索。
  （在线获取歌词与封面是另一件事，走 **LrcAPI**，见上文「在线歌词与封面」；
  它只挑一条最像的，同名不同版本时可能挑错，界面上会标出来源歌名 / 歌手供你判断。）
- 均衡器的滑块是整数 dB，预置曲线的小数部分只有在不碰该频段时才会原样保留。
- 筛选状态下不支持拖动换位（会提示先清空搜索框）。
- **系统媒体控件（音量弹窗）**：曲名 / 歌手 / 播放状态 / 进度 / 封面，以及
  播放 / 暂停 / 停止 / 上一个 / 下一个那几个按钮，都会出现在音量弹窗与锁屏上（1.4.0 起）。
  两条**如实说明**的边界：① 封面只喂**内嵌图**或**同目录外挂图**（线上找到的封面也会喂），
  视频只喂内嵌图 / 外挂图，**没有做"从画面截一张当封面"**；②
  **系统界面上真的画出来了没有、按钮按下去系统有没有把事件送过来，冒烟验不到，只能人眼看**。
  系统媒体键那条路是另一套（`RegisterHotKey`），不受影响。
  另外**要 Windows 10 2004（19041）以上**才有完整能力：更老的系统上程序照常启动，
  只是这一段拿不到接口（安静降级，媒体键与任务栏按钮都不受影响）。
- **A-B 循环的几个边界**（1.3.0 批次 A）：A/B 两点取的是"按下菜单那一刻引擎报的时间"，
  所以和你想设的那一刻差个几百毫秒是正常的；换歌或停止会清掉这两点（同一首重新起播不清）；
  没给快捷键（现有单键快捷键已经很挤，避免撞车）。
- **音量均衡验到的是"滤镜挂上了"**（1.3.0 批次 A）：进程里量不到输出电平，
  所以没有"响度被拉平了多少"的数字，效果靠耳朵判断。另外它是**媒体级**滤镜，
  切换会把当前这一首**从头重播**（当前进度会丢）——不想丢进度就在开始播之前设好。
- **「下一首播放」队列不落盘**（1.3.0 批次 A）：关掉程序队列就没了（下次打开时那几首多半
  已经不想插播了），列表里的 `▶` 标记也一样；最多 20 条，重复入队会去重。
  插播期间**列表的当前项不动**，加粗的那一行跟着"真正在播的那一项"走。
- 播放记忆按文件路径记录，文件改名或移动后会重新开始记（**歌词偏移、音画 / 字幕延迟同理**）。
- 歌词偏移的可调范围是 **±30 秒**（一档 0.5 秒），手动输入时超范围会被拒绝而不是悄悄钳住；
  提前过头时前面的若干行会一起压在 `00:00:00`，那时高亮的只会是最后一行——
  这种量级基本可以断定是拿错了歌词（比如现场版配了录音室版的词）。
- **歌单库里改的是列表内容，不是媒体文件**：删歌单、重命名都只动 `播放列表` 目录下的
  m3u8，一个媒体文件都不会被删或被移动。
- 歌单的**「当前歌单」是手动关联**：只有"保存为歌单 / 载入歌单"才会建立关联，
  在资源管理器里自己改歌单文件名之后，下次启动会提示"歌单已经不在歌单库里了"，
  当前列表照常恢复，只是不再对应任何歌单。
- 歌单窗口**支持多选批量删除**，也能**拖动换位**（顺序记在 `歌单顺序.txt` 里）与**批量重命名**：
  只有一份歌单时不会出现顺序文件，名字仍然是自然顺序（`歌单2` 在 `歌单10` 前面）；
  顺序文件里已经没有的名字（删掉的、改名前的）会被**忽略**，不是错误，也不需要手工清理。
- **歌单窗口里的拖拽换位只认"一行"**：多选时拖哪一行都不明确，所以拖动只对单选生效
  （多选是给删除与批量重命名用的）。另外**批量重命名不会做"互换名字"**：
  想改成的新名字如果已经被别的歌单占着（哪怕那一份也在选中列表里），就先整批挡住——
  一个文件都不动，比"改一半、还覆盖掉别人的歌单"好。
- 单实例的互斥体是"每登录会话"一个（`Local\`），所以同一台机器上不同 Windows 用户可以
  各开一个窗口；第二个实例如果比第一个先退出，它传来的文件不会丢（有 2 秒重试）。

以下几条是**已知但本轮没有动**的，如实列出：
- **封面页与歌词页的重绘还有优化空间**：`CoverView` 每次绘制都会重新做一遍文字排版与
  `MeasureText`（同一帧里还算了两遍），`LyricsView` 平滑滚动时每 15ms 重画一次、
  每次都重建当前行高亮的圆角路径与画刷。都不泄漏（都有 `using`），但在大窗口下是热点。
  做法可以照 `LyricsView` 已有的 `_boxes` / `_layoutDirty` 缓存思路推广。
- **`MediaFormats.IsOpenable` 仍是同步的 `File.Exists`**：启动恢复那条路已经不碰它了
  （见上文「播放记忆」），但 `PlayIndex` 顺延、以及用户**刚拖进来**的路径仍会同步查一次。
  已经由后台核对标成"打不开"的条目会直接跳过，不会再等 SMB 超时；没核对过的网络路径
  仍可能停顿一下（这台机器上实测：离线的网络路径一次查询 **>25 秒**，本地不存在的文件 4 ms）。
- 设置文件损坏时会**先试着救出能读的项**（见上文「设置文件」），一项都救不回来才整份退回默认值；
  但**不会把坏字段之外的未知字段写回去**（重写时只写当前这一版认得的字段）。
- 在线歌词与封面来自 **LrcAPI**，服务地址（和可选的鉴权密钥）要**自己填**。
  几个已知的边界：
  - **歌词接口通常不需要鉴权，封面接口不一定给**。开发时那台实例实试：
    歌词三个端点不带任何头都是 200，而封面两条接口一条 302 到拼错的地址、一条 401
    （带不带密钥都一样）。**能用的只有搜索结果里的 `cover` 字段**。
  - 封面图常挂在 `p2.music.126.net` 这类**外部主机**上，所以能不能显示封面还取决于
    这台机器能不能访问外网。本机开发环境实试**连不上外部 HTTPS**
    （`curl` 返回 `000`），所以真接口那一段只验到"封面地址拿到了，但下载失败：
    The SSL connection could not be established"——**这一步是在真实网络下才跑得通的**，
    本地假服务器那条路（三条封面来源）倒是全验过了。
  - 取回来的歌词与封面**只在本次运行里用**，不写盘；重启要重新联网。
  - 选哪一条是打分挑出来的（标题 / 歌手 / 有没有时间轴），同名不同版本时可能挑错。
  - 鉴权密钥是明文存在 `settings.json` 里的，不做额外加密（这个文件本来也没加密）。
- **在线查找失败不再静默**：自动获取失败也会在状态栏说明原因（同一条原因只报一次，
  免得每切一首歌刷一次屏）。以前失败是完全静默的，用户只看到"封面有了、歌词没有"，
  根本不知道是没填地址、要鉴权，还是服务端自己报错——这一条是被真实反馈逼出来的。
- 服务端 5xx 时会把**响应体里第一行有效文字**一起显示出来（HTML 错误页则跳过）：
  自建 LrcApi 崩掉时那一行 Python `TypeError` 比"HTTP 500"有用得多。
- **带鉴权被 500 就自动去掉鉴权重试一次**（并把这台服务记下来，之后不再给它发头）：
  实试有实例的鉴权实现收到 `Authorization` 就崩。带鉴权被 5xx 和"服务端真的出错"
  是两种意思，前者retry一次能救回来，后者 retry 也白搭——所以只在带了鉴权时才重试。
- 只有一个"封面地址拿到了但下载失败"的细节值得留意：封面图常挂在第三方主机上，
  **能不能显示封面还取决于这台机器能不能访问外网**。
- **桌面歌词的下一句和主句同色**，只靠字号（0.62 倍）与字重区分。
  刻意没有减淡：浅色主题的强调色 `#0A84FF` 在透明背景上本来就偏暗，
  再乘 0.62 会掉到 2.4:1（按 WCAG 相对亮度算过），下一句会糊成一片。
- 桌面歌词**只能抓住窗口范围来拖**（鼠标停上去会铺出一块半透明背景，那块范围内都能抓）：
  窗口之外当然点不到，而**锁定之后连范围内也不响应**——锁定的意思就是
  "这个窗口在鼠标眼里不存在"。
- 桌面歌词的"真鼠标拖动"现在是**硬断言**：合成一次真实的按下 + 多格移动 + 抬起，
  窗口必须跟着走（曾经这条检查是缺失的，所以"点不动"这个 bug 一直没被发现；
  详见「桌面歌词：一个"不该被注意到"的窗口」）。合成不出鼠标输入的机器上会先自检、然后跳过。
- 桌面歌词**一次只显示一句 + 下一句，没有逐字染色**（卡拉OK 效果需要逐字时间轴，
  LRC / SYLT 里都没有）。纯文本歌词（`.txt`、只有 `USLT` 的 MP3）在桌面歌词里按
  "没有歌词"处理，显示成 `♪ + 曲名`。
- 桌面歌词**锁定之后可以从更多地方解开**：`Ctrl+Alt+D`（全局热键，任何程序里都有效）、
  托盘图标右键 →「桌面歌词」→ 锁定、或「视图 → 桌面歌词」。**锁定状态会被记住**，
  所以下次启动可能一开出来就是锁着的（状态栏会说明，锁定的那一刻还会弹一次托盘气泡）。
  顺带更正一条旧说法：`Ctrl+D` 只是"开关桌面歌词"，**不能**用来解锁
  （关掉再打开仍然是锁定的）。
- 桌面歌词**不再让"只显示字、连描边都不要"成为选项**：没有背景板又不描边，
  在白底程序上就是完全看不见。宁可没有这个开关，也不给一个会让人以为程序坏了的选项。
- 置顶窗口**盖不住"独占全屏"（exclusive fullscreen）的程序**：那类程序直接把显示模式
  接管了，普通窗口的置顶在这种模式下不生效。无边框窗口全屏（本播放器的全屏、
  大多数游戏的"无边框窗口"模式）不受影响。
- 导入的字体**可以在界面上卸载**（`字体 → 管理已导入的字体…`）：
  `.ttf` / `.otf` 是读进内存装的，删除当场生效；
  **`.ttc` / `.otc` 这类字体集合只能按文件加载**（GDI+ 的内存加载不认它们），
  那一份在程序运行期间仍被占着，删除会排到**下次启动**执行。
  另外 `PrivateFontCollection` 一旦装进去就没法单独取出来，所以本次运行里
  已经装进 GDI+ 的那份数据要等进程退出——对"导错了想删掉"来说这已经够了。
- 导入字体的**拖放**只在桌面歌词窗口上支持（把 `.ttf` 拖到歌词上即可），
  而且**锁定时拖不进去**——锁定的窗口在鼠标眼里不存在，这是预期的。
- 选的字体**如果没有中文字形**，歌词里的汉字会显示成方框——这是选字体的人自己承担的选择，
  程序只保证字体族不存在时安静退回默认字体，不保证它认得你的歌词。
  管理对话框里那一行大号样例（中英数都有）就是给人提前看出来的。
- 字体列表里**只有自己导入的字体，看不到系统已安装的字体**（连"默认"之外一项都不列）。
  这是按需求刻意这么做的：系统字体动辄几百个，列出来又长又难找。
- **双语歌词（同一时间戳的原文 + 翻译）当成同一句**：`LineIndexAt` 返回同一时间戳那一组的
  **第一行**（原文），侧栏里这一组**两行一起高亮**（以前取最后一行，于是译文是"当前句"、
  原文永远是暗的，另一行也永远轮不到）；桌面歌词的第二行**优先放译文**
  （`有翻译时第二行显示翻译`，默认开），关掉它就总是显示"下一句"（会跳过整组，不会把译文当下一句）
  `UiFonts.InstalledFamilies` 还留着（惰性、没人用就不枚举），要恢复"选系统字体"不用重写。

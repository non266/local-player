## 2. 实现

### 2.1 网络位置不阻塞界面（S1）

- `Core/MediaFormats`：
  - 新增 `IsNetworkPath`：UNC 前缀（`\\`、`//`）直接认；盘符走 `DriveInfo.DriveType == Network`
    （GetDriveType，**不连服务器**）。只看路径，一次磁盘都不碰。
  - `IsOpenable`：网络位置只返回"可能打开"，不再同步 `File.Exists`。
- `Core/PlaybackCoordinator`：
  - 播放请求拆成 `PlayRun`（代际号 / 起始索引 / 是否顺延 / 是否抑制续播 / 已标条目 / 最后错误）。
  - 遇到网络位置：`StartProbe` 起后台探测（默认 `Task.Run(File.Exists)`），界面立刻返回。
  - `PumpPendingProbe`（界面计时器每 200 ms 调一次）收结果：先校验代际号与条目还在原位；
    结果是"不存在"→ 标 `MissingFileMessage`、保留条目、顺延下一项；超时（默认 8 秒）→
    只标 `NetworkTimeoutMessage`、不判缺失、不打开；`Stop()` / 新一次 `PlayIndex` 都会作废旧探测。
  - `ReloadCurrent` 用 `suppressResume` 保持"重载从头，不接上次位置"。
- `MainForm`：
  - 计时器每拍先 `_playback.PumpPendingProbe()`，事件与引擎调用都留在 UI 线程。
  - 加列表 / 拖放 / 最近播放 / 「在资源管理器中显示」遇到网络路径不再 `File.Exists` / `Directory.Exists`。

## 3. 测试

- 新增冒烟第 **25** 项「网络位置」（`tools/SmokeTest/Program.Network.cs`，第 21 个运行步骤）：
  1. UNC 被认成网络位置，`IsOpenable` 不下"不存在"的结论；
  2. 假探测没回来时 `PlayIndex` 立刻返回、不打开媒体、`HasPendingProbe` 为真；
  3. 探测为 false → 标缺、**条目不删**、顺延到本地项；
  4. 换目标后旧探测清掉，迟到的结果不能抢当前曲目；
  5. 超时 → 标 `NetworkTimeoutMessage`、不打开、状态栏说"超时"。
  用的地址是 RFC 5737 的 TEST-NET（`192.0.2.1/2`），**所有探测都由假委托接管**，不碰真实网络。
- 「主窗体与主题」加一条：`BuildAboutText()` 含项目地址、运行环境主版本 = 当前进程、没有 ".NET 8"。
- `StepCount` 24 → 25；`release-check.ps1` 标题与说明改成 21 步 / 25 项。

## 4. 变异验证（逐条都按预期以具体的话变红）

| 变异 | 实际失败的话 |
| --- | --- |
| `IsOpenable` 去掉网络分支，恢复同步 `File.Exists` | `网络路径被 IsOpenable 直接判成打不开——它还没探测就下了结论`（这一跑顺便量到：对 `\\192.0.2.1\...` 的一次 `File.Exists` 阻塞了 **68 秒**） |
| 换目标时不清 `_pendingProbe` | `换了目标之后，旧的网络探测还挂着（迟到的结果迟早会回来抢播放）` |
| 超时判断改成 `TimeSpan.FromDays(1)` | `探测超时之后还挂着（没有放弃等待）` |
| 「关于」去掉项目地址 | `「关于」里没有项目主页地址（用户找不到源码 / 问题反馈入口）` |
| `docs-check` 口径：把 README 里的"25 项检查"改成"24 项检查" | `README.md 里找不到「21 个运行步骤 / 25 项检查」…` |

> 还有一条**没有**当变异用：让 `PlayFrom` 在探测回来前直接 `_engine.Open`。它确实能把新判据打红，
> 但 libvlc 会对不可达地址同步卡住，测试进程直接挂死而不是给出一句话——这正好说明这条保护不能省。

## 5. 明确不做 / 已知边界

- 网络**目录**的拖入暂不支持：`AddPathsWithFolders` 不判 `Directory.Exists`，会把它当文件加进去，
  点播时探测失败标缺。要做需要后台枚举 + 另一套取消，不在本轮。
- 网络上的 `.m3u` 仍会同步读取（`LoadPlaylistFromFile` 在 UI 线程）——少数场景，未改。
- `File.Exists` 只是我们能控制的那一层；libvlc 自己的 `Media.Play` 对不可达地址会不会阻塞没有单独量，
  本轮不承诺"任何网络故障都零卡顿"。
- 探测同一时刻只跑一条；超时 8 秒是经验值，没有在真实慢速 NAS 上标定。
- 没有用 UI 帧率 / 输入延迟量化"不卡"，判据是"探测没回来之前不打开 + 调用立刻返回"。

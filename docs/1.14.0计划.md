# 1.14.0 计划：网络位置收尾（网络目录导入 / 网络 m3u / 文档真值）

> 版本：1.14.0（2026-11-07）。范围 = 所有者选定的「网络位置收尾」：把 1.13.0 明确留下的两条
> 已知边界（网络目录、网络 m3u）做完，顺带修掉 README 里 1.13.0 之后就过时的说法。
> 老规矩：断言 + 变异 + 文档，一条不少；没点名的功能一条不动。

## 1. 起因与取舍

1.13.0 把「播放前不在界面线程查存在性」做完了，但留下了两条边界（原文见 `ARCHITECTURE §19.2`）：

| # | 1.13.0 的边界 | 实际后果 | 本轮 |
| --- | --- | --- | --- |
| 1 | 网络**目录**不递归枚举，拖入按单个文件收下 | NAS 上的专辑目录拖进来只得到一条打不开的条目 | **做**：后台判目录 + 递归枚举 |
| 2 | 网络上的 `.m3u` 仍同步读取 | 离线 / 慢速共享上，拖一个 m3u 会冻住窗口直到 SMB 超时 | **做**：后台读，按「追加」语义进列表 |
| 3 | README 说「`IsOpenable` 仍是同步的 `File.Exists`」「网络目录的拖入暂不支持」 | 1.13.0 已经改掉了，文档还写着旧结论 | **做**：改文档，并用 `docs-check` 钉住 |

不做：扫描进度条 / 取消按钮（离线时等满 SMB 超时是网络本身的行为）、m3u 里的网络目录展开、
网络外挂封面与网络字幕的异步化、大列表 `VirtualMode`、DVD 章节、`TrackCoordinator`。

版本号按维护手册第 1 节：网络目录是用户看得见的新能力 → **次版本号 1.14.0**。

## 2. 实现

### 2.1 `Core/NetworkPathImport.cs`（新）

不引 WinForms，只做判定与枚举；三个 I/O 都是可替换的委托（测试注入假实现）：

| 委托 | 默认 | 作用 |
| --- | --- | --- |
| `IsDirectory` | `Directory.Exists` | 判"是不是目录" |
| `EnumerateFolder` | `MediaFormats.EnumerateMediaFiles(folder, true)` | 递归枚举媒体 |
| `ReadPlaylist` | `PlaylistFile.Load` | 读网络 m3u 的条目 |

`Run(paths)` 逐条规则（顺序即结果顺序）：

1. 扩展名是 m3u / m3u8 → `ReadPlaylist`，条目进 `FromPlaylists`；空表 / 读不出来分开记。
   **m3u 自己永远不进 `Items`**。
2. 扩展名是媒体 / 字幕 → 直接进 `Items`，**不调 `IsDirectory`**（离线时省掉一次 SMB 超时）。
3. 其它 → `IsDirectory`：是目录就记进 `Folders` 并枚举；不是就进 `Items` + `Unreachable`
   （可能离线，也可能是没有扩展名的文件）；抛异常也进 `Items` 并记日志（单条失败不影响整批）。

结果 `NetworkPathImportResult` 按用途分桶：`Items / Folders / FromPlaylists / EmptyPlaylists /
UnreadablePlaylists / Unreachable / Failures`。界面只负责"把这些加进列表"。

### 2.2 `MainForm.Playlist.cs` 接线

- 分流仍先看路径、不碰磁盘：网络 **m3u** → 后台；网络**媒体 / 字幕** → 同步收下（一次磁盘都不碰，
  也保住 1.13.0「点网络文件立刻进列表」的行为）；网络**扩展名不认识**的 → 后台判目录。
- 本地目录枚举与 `_networkImport.Run(network)` 合并进同一个 `Task.Run`，一次回投；
  回投后 `AddPathsToPlaylist(Items)`，m3u 条目用 `_playlist.AddRange` + `_scanner.Enqueue`（追加、不去重，
  和本地 m3u 完全一致）。
- 状态栏：扫描时说明在扫网络位置；结束时把「加了几项」与「哪条没成」一次说清。
  `Directory.Exists` 返回 false 分不清"离线"和"真不是目录"，文案只写「**可能离线**」。
- 测试钩子：`internal NetworkPathImport NetworkImport => _networkImport;`。

### 2.3 实现时踩到的一条

第一版把所有网络路径（含 `.wav`）都丢进后台，结果 1.13.0 的第 25 项检查红了：
`网络路径没有进入后台探测（界面线程还在同步查盘）`——它依赖"网络文件立刻进列表"。
改成"扩展名已知的文件同步收下"后恢复，而且这本来就是更好的行为（省一次后台往返）。
判据一条没改。

## 3. 测试

新增冒烟第 **26** 项「网络目录」（`tools/SmokeTest/Program.NetworkFolders.cs`，第 22 个运行步骤），
`StepCount` 25 → 26。夹具是现场合成的 3 个 wav；地址用 RFC 5737 的 `\\192.0.2.x\...`，
探测 / 枚举 / 读 m3u 全部由假委托接管，**不碰真实网络**。

六个场景：

1. 网络媒体文件（`.wav`）**不触发目录探测**（假探测一次都没被调用），条目异步进列表。
2. 网络目录：假探测在闸门上等 → `AddPathsForTest` 立刻返回、状态栏说在扫网络位置、同批的本地文件
   已经进列表；放行后两个文件按枚举顺序进列表、目录本身不在列表里；探测 / 枚举的
   `ManagedThreadId` ≠ 界面线程。
3. 打不开的网络位置（无扩展名、探测 false）→ 保留 1 项、状态栏含「可能离线」。
4. 网络 m3u：假读取在闸门上等 → 调用立刻返回、列表还是空的；放行后追加 2 项、m3u 不成条目；
   读的线程号 ≠ 界面线程。空表 / 抛异常两种都有提示，且都不往列表里塞东西。
5. 空网络目录 → 状态栏说「没有找到可播放的媒体文件」，列表不动。
6. 同批本地项不被网络扫描拖住（并入场景 2）。

### 3.1 判据为什么看线程号

计时会受机器负载影响；线程号是确定的：探测 / 枚举 / 读 m3u 真在界面线程上跑，
`ManagedThreadId` 必然等于界面线程。闸门只负责证明"调用立刻返回"，两者互补。

## 4. 变异验证（逐条按预期以一句具体的话变红）

| 变异 | 实际失败的话 |
| --- | --- |
| 网络路径恢复成"直接收下"（1.13.0 行为） | `扫描网络位置时状态栏没有说明（现在「已添加 2 个文件到播放列表」）` |
| 把 `NetworkPathImport.Run` 拉到界面线程上做 | `网络位置的目录探测跑在界面线程上（离线时会冻住窗口）` |
| 打不开的网络位置不进 `Items` | `打不开的网络位置被丢掉了（现在 0 项；状态栏「1 个网络位置没能当文件夹打开（可能离线）…」）` |
| 网络 m3u 改在界面线程同步读 | `网络 m3u 在界面线程上读取（拖进来时会卡住）` |
| 去掉"扩展名分流"守卫 | `对扩展名已经说明是文件的网络路径还做了目录探测（离线时会白等一次超时）` |
| `docs-check` 口径：README 改回「21 个运行步骤 / 25 项检查」 | `README.md 里找不到「22 个运行步骤 / 26 项检查」…` |

> 两条如实说明：
> ① "扩展名分流"有**两层**守卫（`MainForm` 的分流 + `NetworkPathImport` 的规则 ②），
> 只拆一层时测试仍是绿的——要拆两层才红。这是刻意的双保险，变异记录里写清楚，
> 免得下次有人以为"拆了没红 = 断言没用"。
> ② 第一条变异红在"状态栏没说在扫网络位置"这条断言上（更早、更直接地说明"根本没走网络扫描"），
> 没等到"目录没展开"那一条；两条断言都保留。

## 5. 不做 / 已知边界

- **没有"取消扫描"**：离线时 `Directory.Exists` 要等满 SMB 超时（本机实测一次网络查询 >25 秒，
  1.13.0 变异时量到 68 秒）；等的是后台线程，界面不受影响。
- **目录名带媒体扩展名**（例如 `music.flac` 这个目录）会被当成文件——扩展名分流优先，
  否则每个网络媒体文件都要先白等一次超时。
- 网络目录里的内容**一次性**加进列表；几万条时仍是 O(n) 刷新（与本地大目录一致）。
- m3u 里指向网络目录的条目只按文件收下，不展开；网络字幕仍同步挂载。
- 测试是假委托 + 回环共享手工验证，**没有在真实慢速 NAS 上标定**超时行为。

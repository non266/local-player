# 1.17.0 计划：网络 I/O 的取消与资源管理

> 版本：1.17.0（2026-11-10 立项）。范围 = 所有者选定的「网络 I/O 的取消与资源管理」
> （外部评审 14 条里的第 2 / 3 条，也是那篇评审总结里的第 2 项）。
> 本文是**计划稿**：§2 的量已经做完，产品代码**一行还没动**。
> 老规矩：断言 + 变异 + 文档同步；不设计时断言。

## 1. 起因与取舍

1.13.0 把网络位置的"在不在"丢到后台（`PlaybackCoordinator.PathProbe`），
1.14.0 把网络目录的判定 / 枚举 / m3u 读取丢到后台（`NetworkPathImport`）。
两次都只解决了"界面不等"——**后台那条 I/O 没人管**。

现状的三个缺口（都能指到行）：

| 缺口 | 现状 | 后果 |
| --- | --- | --- |
| 探测只"逻辑作废" | `_pendingProbe = null`（`Core/PlaybackCoordinator.cs:228`、`:548`），`Task.Run(() => File.Exists(path))`（`:176`） | 被放弃的那条 Task 照跑；同一路径重复点会**再起一条** |
| 探测占线程池 | `Task.Run` 默认进线程池 | 一条卡 80 多秒就占一个工作线程（§2 量了余量被吃掉之后的排队延迟） |
| 扫描不可取消、无上限 | `NetworkPathImport.Run` 是阻塞方法（`:45`）；`MediaFormats.EnumerateMediaFiles` 递归无深度 / 条数上限、先收满整棵树再排序（`:220`） | 拖一个大 NAS 目录进来只能等；没有"停"的入口，也没有"已经找到多少" |

本轮只动这两条后台路径。**不动**：本地目录扫描（沿用现有无限版）、播放前的判定顺序、
`IsOpenable` 的语义、诊断与质量、以及反馈里的其余 12 条（§8）。

## 2. 先量（2026-11-10，本机）

| 量 | 结果 | 怎么量的 |
| --- | --- | --- |
| 不可达 UNC 上一次 `File.Exists` | **82.4 / 82.7 / 83.1 / 83.4 / 92.5 秒** | 5 个 pwsh 子进程各 `[IO.File]::Exists("\\192.0.2.N\share\probe.mp4")`，并发跑；1.13.0 记的是 68 秒，同一现象 |
| 8 秒 `ProbeTimeout` 之后 | 界面不再等，但那条线程还要再卡 **约 75 秒** | 上面 5 个数 − 8 秒 |
| 线程池余量被吃掉之后的排队延迟 | 基线空任务 **11 ms**；12 条阻塞探测占满最小工作线程（12 条）后第一个空任务 **312 ms**，随后 ~0 ms（线程池按约 1 条/秒补） | `%TEMP%\poolprobe` 一次性控制台程序（net10.0，不入库） |
| 同一路径重复点 | 每次 `PlayIndex` 都新起一条探测，没有去重 | 读代码（`StartProbe`） |

三条结论：

1. 探测的代价是**几十秒级的线程占用**，不是"一次失败的判断"；8 秒只是界面放弃等待的时间；
2. 线程池会补，所以"一次点一条"的代价有限（312 ms 排队）；但**重复点同一路径 / 连点十几条**
   会把池里的余量吃光一段时间——本轮加的上限（4 条）让这条路径**有界**；
3. 扫描没有上限，比探测更危险：一条离线的 NAS 目录能在后台跑几分钟，用户既看不到进度、也没法停。

## 3. 实现

### 3.1 扫描：`Core/MediaScan.cs`（新文件）

```csharp
internal sealed class MediaScanLimits
{
    internal int MaxDepth { get; set; } = 16;        // 根目录算第 0 层
    internal int MaxFiles { get; set; } = 100_000;
}

internal sealed class MediaScanResult
{
    internal List<string> Files { get; }     // 已经排序（CurrentCultureIgnoreCase）
    internal bool Truncated { get; }         // 到了深度 / 条数上限
    internal bool Cancelled { get; }
    internal int FoldersVisited { get; }
}

internal static class MediaScanner
{
    internal static MediaScanResult Walk(string folder, MediaScanLimits limits,
        CancellationToken token, Action<string>? onFile);
}
```

- 显式栈的 DFS；每进一层先比 `MaxDepth`；
- 每个文件问一次 `MediaFormats.IsMediaFile`，命中就 `onFile(path)` 并收进结果；
- 每 64 个文件查一次 `token`；取消时**保留已经找到的**，置 `Cancelled`；
- 到 `MaxFiles` 或超过 `MaxDepth` 就地停，置 `Truncated`（不把这一层扫完再说——上限就是上限）；
- 结束时排序，口径与现在一致；
- 吞异常的清单与 `EnumerateMediaFiles` 相同（`UnauthorizedAccessException` /
  `DirectoryNotFoundException` / `IOException` 只跳过这一层）。

`MediaFormats.EnumerateMediaFiles(folder, recursive)` 改成调
`Walk(folder, 无限 limits, default, null)`：**顺序、异常口径、排序都不变**，旧签名保留，
本地那一侧一行不用改。

### 3.2 扫描：`Core/NetworkPathImport.cs`

- `Run(IEnumerable<string> paths, CancellationToken token = default, Action<string>? onFound = null)`；
- 每条路径处理前看 token：取消就 `result.Cancelled = true` 并 `break`（后面的路径**一次都不碰**）；
- 目录那一路换成 `MediaScanner.Walk(path, Limits, token, onFound)`，`Truncated` / `Cancelled` 记进结果；
- m3u 的条目也算"找到"，逐条 `onFound`——进度才看着涨，而不是整批结束才动一下；
- 结果类型加 `bool Cancelled` / `bool Truncated`；
- `internal MediaScanLimits Limits { get; set; }` 挂在 `NetworkPathImport` 上，**只对网络路径生效**；
- 冒烟第 26 项里 5 处假 `EnumerateFolder = _ => …` 跟着换签名（`WalkFolder`）。

### 3.3 扫描的界面：`MainForm.Scan.cs`（新分部）

- 状态栏加一个链接标签 `lblScanCancel`（`IsLink = true`，文字「取消扫描」），插在
  `lblStatus` 与 `lblStatusSpring` 之间；**不写进 `MainForm.Designer.cs`**——那文件是手改的，
  改一次就漂一次，所以在 `InitScanUi()` 里建、由构造函数调一次；
- `_scanInFlight` / `_scanFound`（都走 `Interlocked`）、`_scanCts`（List，取消时全 cancel）；
- 进度在 `OnUiTimerTick` 里每拍读一次，写成「取消扫描 · 已找到 1,234 项」——
  **不跨线程 `BeginInvoke`**，否则每个文件一次 Post，扫描越快越卡；
- 点链接 → 取消所有在飞的扫描，状态栏「正在取消扫描…」；
- 取消后结果照收：已扫到的条目**照常加进列表**，状态栏「已取消扫描：已加入前 N 项」；
- `AddPathsWithFolders` 的 `Task.Run` 换成带 CTS 的批次，`PostScannedFiles` 收尾时 `EndScan`。

### 3.4 探测：`Core/PlaybackCoordinator.cs`

- 新增一个私有注册表（同文件内的嵌套类，或 `PlaybackCoordinator.Probes.cs` 分部）：
  - `Dictionary<string, ProbeTicket>`（`OrdinalIgnoreCase`）记在飞的探测；
  - `Dictionary<string, DateTime>` 记"超时冷却"，默认 30 秒；
  - `MaxConcurrentProbes = 4`、`ProbeCooldown = 30s`、`ProbeStarts` 计数（都是 `internal`，测试要改 / 要读）。
- `StartProbe` 的四条分支（按顺序判）：
  1. **冷却中** → 不探，直接按超时处理，状态栏「刚试过，这 30 秒内不再重试（还剩 N 秒）」；
  2. **同一路径在飞** → 复用那条 Task（不新起线程），等它的结果；
  3. **在飞已满 4 条** → 不新起，按超时处理，状态栏「同时检查的网络位置太多，先跳过这一项」；
  4. 否则
     `Task.Factory.StartNew(() => _pathProbe(path), CancellationToken.None, TaskCreationOptions.LongRunning, TaskScheduler.Default).Unwrap()`
     ——**专用线程**，不占线程池。
- `PumpPendingProbe`：超时分支记冷却；完成分支把 ticket 删掉（"确定不存在"不冷却，
  下次点还要再问一次——文件可能刚被拷回来）。
- `DefaultPathProbe` 从 `Task.Run(() => File.Exists(path))` 改成
  `Task.FromResult(File.Exists(path))`：真正的调用发生在上面那条专用线程上。

> **为什么不给 `File.Exists` 一个 `CancellationToken`**：它本身不可取消。给 token 只是
> "取消之后不再等结果"，线程照样要跑到 OS 超时（§2 的 80 多秒）。所以这一轮的"取消"是
> **有界**：最多 4 条专用线程、同一路径只一条、超时后 30 秒内不再问。

## 4. 测试与变异

### 4.1 断言（不插盘、不碰真实网络）

两项新检查：

**第 28 项「扫描上限与取消」**（新文件 `tools/SmokeTest/Program.Scan.cs`，第 23 个运行步骤）

1. 深度：临时目录 3 层，`MaxDepth = 1` → 只收第 1 层，`Truncated`；
2. 条数：10 个文件，`MaxFiles = 4` → 正好 4 个，`Truncated`；
3. 取消：`onFile` 收到第 3 个时 cancel → 结果 3 个、`Cancelled`、不抛；
4. 一致：无限 limits 的 `Walk` 与旧 `EnumerateMediaFiles(folder, true)` 结果**逐项相同**（顺序也算）；
5. 短路：`NetworkPathImport.Run` 里第一条路径扫到一半取消 → 第二条路径的 `IsDirectory` **一次都没调**；
6. 接线：注入假的 `WalkFolder`（每 25 ms 吐一个，共 50 个）拖入一个"网络目录" →
   链接可见且文字含「取消扫描」→ 点它 → 链接消失、状态栏说「已取消」、
   列表里是**已找到的那几个**（> 0 且 < 50）。

**第 29 项「探测去重与有界」**（新文件 `tools/SmokeTest/Program.Probe.cs`，第 24 个运行步骤）

1. 同一路径快速点两次（假探测挂住）→ `ProbeStarts == 1`；
2. 超时（`ProbeTimeout = 100 ms`）后冷却期内再点 → 仍 `== 1`，状态栏含「刚试过」；
3. 冷却改成 50 ms、等过去再点 → `== 2`；
4. 上限：5 条不同路径、假探测都挂住 → `ProbeStarts == 4`，第 5 条立刻说「太多」；
5. 专用线程：假探测里记 `Thread.CurrentThread.IsThreadPoolThread` → **false**；
6. 不回归：探测说"不存在"时仍然标缺、仍然顺延（第 25 项里的那几条照旧）。

## 5. 边界（做不到的与故意不做的）

1. **`File.Exists` 不可取消**：冷却 + 上限让"卡住的线程"有界（最多 4 条、每条几十秒），
   但**不能提前结束**它们；
2. **冷却期内的重试不真的去问**：文件在这 30 秒里出现了也要等过去（或等点别的项把它挤出去）；
3. **上限会在超大目录上少加文件**（深度 16 / 100,000 个）：状态栏必须明说「已达上限，只加了前 N 项」，
   不能静默截断；
4. **本地目录扫描仍然无上限**：本轮只动网络那一侧，免得本地拖放跟着变；
5. **取消只对枚举有效**：正在返回的那一次 `Directory.EnumerateFiles` 要等系统自己回来
   （掉线的 SMB 可能几十秒）；
6. **进度是"已找到多少"，不是"还剩多久"**：总条数事先不知道，不承诺百分比；
7. 反馈第 4 条（VLC 自己打开不可达网络媒体是否阻塞）**不在本轮**：要分别验 SMB / HTTP / RTSP，
   是另一条主线，列进 1.18.0 候选。

### 9.2 与计划的偏差（都写清了理由）

1. **假枚举的接缝换了形状**：计划写"`EnumerateFolder` 换签名"，实际换成
   `WalkFolder(folder, limits, token, onFile) → MediaScanResult`——测试要能看到 `Truncated` /
   `Cancelled` 与被回调的每个文件，只返回 `List<string>` 不够。冒烟第 26 项里 5 处假枚举跟着改。
2. **`Directory.GetFiles` 而不是 `Directory.EnumerateFiles`**：`EnumerateFiles` 的异常是在
   `MoveNext` 里抛的，`try` 包住调用点没用（旧实现就是这样，异常会掀掉整棵树）。每层一次取完
   才能"单层失败只跳过这一层"——这是本轮唯一一处**有意改掉旧行为**的地方，写在 §5.4 与 README。
3. **取消短路是两道**（`Run` 的循环顶部 + `Import` 里的第③步之前）。只去掉一处不会红——
   第一道省掉后面的路径、第二道省掉"已经取消还去问 `IsDirectory`"的那一次 80 秒。变异要去掉
   全部三处（含循环底的 `if (result.Cancelled) break;`）才会红；这是设计如此，不是断言太松。
4. **进度把本地目录也算进去**：本地那一侧没有逐文件的回调，所以是在每个文件夹扫完之后
   `Interlocked.Add` 一次（网络那一路逐条加）。计划只写了"网络那一路"，实现时补上，
   否则只拖本地大目录时链接上的数字一直是 0，看着像卡住。

### 9.3 两条过程教训

- **旧 `播放器.dll` 会让变异假绿**：`SmokeTest.csproj` 用 `<Reference Include="播放器">`
  引二进制，只构建冒烟工程不会重建产品。第一版变异 1 就是这么"绿"的（跑了旧 dll）。
  规矩：先 `dotnet build 播放器.csproj`、再构建冒烟、然后跑；复原之后同样两遍。
- **不要用 `git checkout -- <file>` 复原变异**：这一轮它把还没提交的实现（`PlaybackCoordinator`
  的探测注册表）一起回退掉了，只能重写一遍。复原变异要用**备份文件**（`Copy-Item $p $bak`），
  而且复原之后要重构建（备份的修改时间可能比构建产物旧，见维护手册坑表那条）。

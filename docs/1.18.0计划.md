# 1.18.0 计划：大列表排序与自绘控件的重复工作量

> 版本：1.18.0（2026-11-11 立项）。范围 = 所有者选定的「性能」。
> **这份文档保留了立项时的判断，也写了实测之后的改动**——计划里的核心假设（"把排序挪到后台"）
> 被第一组数字推翻了，见 §2 与 §7。老规矩：先量、断言 + 变异、文档同步。

## 1. 目标与判据（立项时）

| # | 判据 | 结果 |
| --- | --- | --- |
| G1 | 把 50,000 条「按名称排序」拆成 **模型排序** 与 **建行** 两段，各自有数字 | 做到了：45 ms / 1,116 ms（§2） |
| G2 | 若模型排序 ≥ 0.5 秒：挪到线程池，界面不冻那一段 | **门禁未过**（45 ms），按 G6 不做后台化 |
| G3 | 排序结果只在结构没变时应用、新排序取消旧的 | **作废**：没有后台排序，就没有"迟到的结果"可言 |
| G4 | CoverView 同一帧只量一遍字 | 做到了（一帧 3 次测量 = 三行各一次） |
| G5 | 自绘缓存只在探针显示 ≥ 10% 收益时保留 | CoverView **−25～27% 保留**；LyricsView **−0.5% 回退** |
| G6 | 门禁没过就只记数字、写进已知限制 | 做到了，但顺手找到了真正的瓶颈（§2.2） |

## 2. 先量

### 2.1 第一组：拆量（`播放器_TEST_BIGLIST=1`，2026-11-11，本机 125% DPI）

| 规模 | 模型排序 | 建行 | **点击到完成** | 复用行重排（只量） |
| --- | --- | --- | --- | --- |
| 10,000 | 8 ms | 216 ms | **714 ms** | 239 ms |
| 50,000 | **45～46 ms** | 1,116～1,135 ms | **3,055～3,063 ms** | 1,264～1,269 ms |

### 2.2 两条结论（第一条推翻了计划）

1. **模型排序不是瓶颈**：50k 只有 45 ms，远低于 0.5 秒的门禁。把这段挪到后台毫无意义——
   省下的是零头，换来的是快照 / 版本 / 取消一整套机制。**G2 不做，G3 作废。**
2. **3,055 ms 里有一半是白花的**：模型 + 建行 ≈ 1,180 ms，点击却要 3,055 ms。
   加了 `PlaylistRebuildCount` 一数：**同一次点击整建了 2 次**——
   `List.Sort` 的 `ContentChanged` 触发一次，`ApplySort` 里又显式调了一次 `RefreshPlaylistView()`。
   （第二遍走不到增量快路：排序之后"当前项没变"那条判据不成立，只能整建。）
3. 顺带量到：**复用行对象再重排（1,269 ms）比整建（1,135 ms）还慢**，所以"排序复用行"这条路
   不值得做——这个数字留给下一版当一个否定证据。

### 2.3 第二组：改完之后复测

| 规模 | 整建次数 | 点击到完成 |
| --- | --- | --- |
| 10,000 | 2 → **1** | 714 → **431 ms** |
| 50,000 | 2 → **1** | 3,055～3,063 → **1,550～1,566 ms**（−49%） |

### 2.4 第三组：绘制（`播放器_TEST_PAINT=1`，200 帧，`DrawToBitmap` 驱动）

| 控件 | 改之前（平均 / 最慢） | 改之后 | 判定 |
| --- | --- | --- | --- |
| CoverView（360×470，标题 / 艺术家 / 专辑三行） | 2.473 / 3.637 ms | **1.794～1.862 / 3.632 ms** | −25～27%，保留 |
| LyricsView（420×620，30 行带轴 + 偏移提示） | 4.990 / 7.825 ms | 4.963 / 7.232 ms | −0.5%，**按 G5 回退** |

LyricsView 每帧只新建"当前行一个圆角路径 + 两支笔"，摊在 30 行文字绘制里是噪声；
把它缓存起来省不出 10%，所以那部分改动**已撤回**（回退后复测仍是 ~4.97 ms）。

## 3. 实现

### 3.1 去掉重复重建（`MainForm.Search.cs`）

`ApplySort` 不再显式调 `RefreshPlaylistView()`：`List.Sort` 的 `ContentChanged` 已经整建一次，
再刷一遍就是白做。条数 ≤ 1 时 `Sort` 直接返回、不发事件，那也没有值得重建的东西。
菜单 / 表头 / 状态栏照旧在 `ApplySort` 里立刻更新。

### 3.2 整建计数（`MainForm.Playlist.cs`）

`internal int PlaylistRebuildCount`：只在**整建**时 +1（增量快路不计）。这是这一轮唯一的
产品侧"可观测"改动，用来钉住"一次用户动作只整建一次"。

### 3.3 CoverView：一帧只量一遍 + 缓存不随每帧变的东西（`Ui/CoverView.cs`）

- 新增 `TextBlockLayout`（每行文案 + 每行高度 + 总高），缓存键是
  **宽度 / DPI / 三行文案 / `Font` / `TitleFont`**；`MeasureLayout` 与 `DrawTextBlock` 共用一份，
  绘制只读 `Heights[i]`，不再 `MeasureText`。
- 圆角路径按 **（矩形、半径）** 缓存一个字段；画刷 / 画笔按颜色缓存，`Dispose` 里释放。
- 顺手修掉一处每帧泄漏：`Graphics.Clip` 的 getter 每次都 new 一个 `Region`，原来没有释放，
  现在 `using var previousClip = g.Clip;`。
- 测试钩子：`internal int TextMeasureCount`、`internal int PathBuildCount`。

### 3.4 没做的（计划里有、实测后砍掉）

- **后台排序**（快照 / 版本号 / 取消 / 最新优先）：G2 门禁未过。
- `Playlist.StructureVersion` / `BuildSortOrder` / `ApplySortOrder`：同上，一并砍掉。
- LyricsView 的路径 / 画刷 / 偏移提示尺寸缓存：G5 门禁未过，已回退。

## 4. 测试与变异

新增**第 30 项检查**「大列表排序」（`tools/SmokeTest/Program.Sort.cs`，第 25 个运行步骤，
`StepCount` 29 → 30）。自己建窗体（复用探针那份已释放的主窗体会原生崩，1.15.0 记过）：

1. 50,000 条（**倒序插入**，否则按名称排是空操作）点一次「按名称排序」→ `PlaylistRebuildCount` 只 +1；
2. 抽查前 200 项按名称升序；
3. 当前项还是**同一个对象**（排序前 `SetCurrent(25000)`，排完 `Items[CurrentIndex]` 必须引用相同）；
4. 点「#」恢复原始顺序同样只整建 1 次；
5. CoverView **预热一帧再换文案**（缓存键变了）画一帧：`TextMeasureCount == 3`（三行各一次；改之前是 6）；
6. 同一文案同一尺寸再画 5 帧，计数**不再涨**（缓存命中）；
7. `PathBuildCount` 用**跨帧增量**：再画一帧不涨（缓存命中）；换尺寸画一帧 +1；再画一帧还是 +1。
   *为什么不数绝对值*：`DrawToBitmap` 的第一帧 DPI / 尺寸还没定，全量跑与单跑会差一两帧，
   绝对计数在两种跑法下不一样（第一版就是这么红的）。

变异 **5 条**全部按预期变红：

| 变异 | 红在哪（原文） |
| --- | --- |
| `ApplySort` 里把显式刷新加回去 | `点一次「按名称排序」整建了 2 次（期望 1 次——多出来的那遍是白花的）` |
| `Playlist.Sort` 不按引用找回当前项（改成钳制下标） | `排序之后当前项换了对象…：排序前是「song-24999」，现在 CurrentIndex = 25000 指着「song-25000」` |
| 绘制时再量一遍字 | `封面画一帧量了 6 次字（期望 3 次：三行各一次）` |
| 圆角路径不再缓存 | `封面在同一尺寸下建了 6 次圆角路径（期望 1 次）` |
| 文字排版不再命中缓存 | `封面画一帧量了 6 次字（期望 3 次…）`（与上一条同一句、不同原因） |

计划里原本写的"阈值 / 版本校验 / 取消旧排序 / 平局顺序"四条变异**随着后台化一起取消了**——
没有那个机制，就没有可变异的东西；这比留着四条测不到的变异诚实。

## 5. 边界（如实写）

- **排序仍然要整建一次**：50k 约 1.5 秒（10k 约 0.4 秒），冻结还在，只是少了一半。
  再往下要么上 `VirtualMode`（1.15.0 判过"不值得"），要么"复用行"（§2.2 量到比重建还慢）。
- **只量过一种规模与一种字体环境**：125% DPI、本机；其它 DPI 下行的像素成本会变，但重建次数不会。
- **CoverView 在音频窗口里本来就不常重画**：省的是"每帧少量一遍"，不是"卡顿消失"。
- **LyricsView 没改**：量过，不划算（−0.5%），如实记着。
- 崩溃取证、元数据取消、DPAPI、DVD 真盘边界、VLC 网络阻塞探针都不在本轮（见 §8）。

### 7.1 收尾挂起（`0xCFFFFFFF`）与它的修法

验收阶段载荷冒烟 6 次里 2 次进程被关掉，退出码 `0xCFFFFFFF`；Windows 事件日志是
**Application Hang**，崩溃日志停在「音频窗口：按真实轨道判形态正常」之后。触发文件是
只有视频轨的 2 秒 mkv（`audio-window-video.mkv`）——它让窗口形态从音频卡片切回三栏。

根因是收尾顺序：产品 `ShutdownForm()` 先 `_engine.Dispose()`、窗体（含 `videoView` 的 HWND）
后销毁，libvlc 的 vout 还在往那个 HWND 上画；而第 11 项检查又自己直接调了一次 `Engine.Stop()`——
产品里并不存在这个顺序。修法两处：产品先 `videoView.MediaPlayer = null` 再放引擎；
检查改成泵一下 → `Close()` → `Dispose()`，由产品自己的关窗路径停引擎。
修后 4 次载荷冒烟 **3 绿、1 次红在画面旋转换内核那族老问题**，没有再挂在第 11 项。

# 1.19.0 计划：切歌时界面在等什么

> 版本：1.19.0（2026-11-12 立项）。范围 = 所有者选定的「A：切歌时的等待」。
> 老规矩不变：**先量、断言 + 变异、文档同步**；没量到收益的改动不留。
> 这一版没有新功能、没有新设置项；改的是"切歌到标签读回来这段时间，界面到底说了什么"。

## 1. 目标与判据

| # | 判据 | 结果 |
| --- | --- | --- |
| G1 | 切歌后读得慢时，**≤200 ms** 内侧栏 / 音频卡片 / 音量弹窗都不再显示上一首的封面与曲名，改成新文件名 + 「正在读取标签…」 | 做到了（宽限 150 ms 常量 + 一次界面拍）。**墙钟不进断言**：检查只断言"宽限过后占位出现"，不拿"必须多快"当判据 |
| G2 | 连切 20 首时**实际读文件 ≤3 次**（在飞最多 2 + 最新待读 1） | 做到了：2 次（放行后 3 次）；改前是 20（变异 1 量的） |
| G3 | 迟到的读取结果**永不覆盖**当前这一首 | 做到了（`MediaSession` 的 token 仍是唯一真值） |
| G4 | 关窗时还有在飞的读取：**不崩、不等待** | 做到了（`MetadataLoadQueue.Dispose` 只关门，不 join） |
| G5 | 读取跑在**专用线程**上，不占线程池 | 做到了（`LongRunning`；检查里断言 `IsThreadPoolThread == false`） |
| G6 | 反馈第 4 条（引擎打开不可达网络流是否冻界面）有数字 | 有：`PlayIndex` **11～13 ms**（http）/ **5 ms**（rtsp），之后 1 秒界面计时器跳 **5 拍**——**不冻** |
| G7 | 全量冒烟 **31 项 / 26 步**全绿；干净树 `release-check` 绿；5 条变异全红 | 做到了（§9） |

## 2. 先量（改之前的现状）

| 事实 | 位置 |
| --- | --- |
| 每切一首起一个 `Task.Run`，**没有上限、没有取消**；只有结果回填时用版本号丢弃 | `MainForm.Metadata.cs`（改前 53 行附近） |
| **切歌到标签读回之间，界面挂着的还是上一首的封面 / 词曲 / 音量弹窗信息**：占位状态根本不存在（全仓库搜不到「正在读取」） | `ApplyMetadata` 只在读取完成后调用 |
| 读的是**真文件两趟**：标签 + 外挂歌词（`.lrc`） | `TagReader.Read` → `LyricsLoader.Load` |
| 引擎打开在界面线程上（`_engine.Open`），反馈第 4 条从 1.13.0 起一直没量过 | `Core/PlaybackCoordinator.cs` 的 `TryOpen` |

三组数字：

| # | 量法 | 改前 | 改后 |
| --- | --- | --- | --- |
| 1 | 占位什么时候出现 | **永不出现**（没有这个状态） | 慢读时 **150～170 ms**（宽限 150 ms + 一次界面拍） |
| 2 | 连切 20 首实际读几次（`播放器_TEST_BIGLIST` 那种只是量，这里是变异 1） | **20** | **2**（+1 次待读 = 3） |
| 3 | `播放器_TEST_NETOPEN=1`：`PlayIndex` 打开 `http://192.0.2.1/probe.mp3` 的耗时 / 之后 1 秒界面拍数 / 60 秒内状态 | 没量过 | **11～13 ms / 5 拍 / 60 秒还是 `Opening`**（rtsp：5 ms / 5 拍 / 同样没报错） |

第 3 条是个**结论**，不只是数字：**libvlc 的打开不阻塞界面**（反馈第 4 条到此为止）；
但不可达的流会一直停在「正在打开…」——60 秒都没有错误事件。这条**如实写进已知限制**，
要"过一会儿就说连不上"是另一套超时策略，排下一版（见 §8）。

## 3. 实现

### 3.1 `Core/MetadataLoadQueue.cs`（新，约 210 行）

```csharp
public readonly record struct MetadataResult(MediaTags Tags, LyricsDocument Lyrics);
public sealed class MetadataLoadQueue : IDisposable
{
    public MetadataLoadQueue(Func<string, MetadataResult> read,
                             Action<string, int, MetadataResult?> completed,
                             int maxLoads = 2);
    public void Request(string path, int token);   // 界面线程调用
    public void Clear();                           // 丢掉待读，不再起新的
    public void Dispose();                         // 关门：不等待在飞的那条
    public int Starts / Skips / InFlight / Pending; // 计数（Interlocked）
    public bool IsClosed;
}
```

三件事分开：**没开始的就别开始**（连切时只有第一条在飞 + 最后一条待读，中间那些不读）、
**在飞有上限**（2 条）、**跑在专用线程上**（`TaskCreationOptions.LongRunning`，和 1.17.0 的探测同一套写法）。
队列只按 token 比大小决定"还该不该起"，**是否应用结果一律由 `MediaSession.IsCurrent` 决定**（不引入第二个真值）。

### 3.2 `MainForm.Metadata.cs`

- `LoadTrackMetadata`：空路径 / 光盘 / **网络流**（以前会给 `http://…` 白开一次 `FileStream` 再失败）
  三个分支都 `Clear()` 队列并撤掉占位；其余走「排队读 + 宽限占位」。
- **宽限 150 ms**：本地读标签通常几十毫秒，那就**不要**把上一首的封面摘掉再放回来（每切一首闪一下更碍眼）；
  超过 150 ms 才换成占位。计时器是一次性的，到点就停。
- 占位走同一个 `ApplyMetadata(..., pending: true)`：信息页只写两行（**不调 `FormatFileSize`**）、
  封面留空、系统媒体控件也不查外挂封面——**占位期间一处磁盘都不碰**。
- 回填：`PostMetadata` → `BeginInvoke` → 不是当前这一首就 `MetadataDiscards++` 并丢掉；是当前就撤掉占位再铺真数据。
- 新钩子：`Metadata`（队列）、`MetadataLoad`（假读取接缝）、`MetadataDiscards`。

### 3.3 界面占位

| 文件 | 改动 |
| --- | --- |
| `Ui/CoverView.cs` | `ShowTrack(path, tags, bool pending = false)`：pending 时标题 = 文件名、副标题 = 「正在读取标签…」、封面留空，**不走 `LoadCover`**（不枚举目录、不解码）；新钩子 `TitleText` / `ArtistText` / `AlbumText`，常量 `PendingText` |
| `Ui/NowPlayingView.cs` / `Ui/MiniPlayerView.cs` / `Ui/AudioWindowModule.cs` | 转发 `pending`（迷你卡片的副标题也换成本文） |
| `Ui/SidebarPanel.cs` | 转发给封面页；信息行由主窗体给 |
| `MainForm.Shell.cs` | 收尾时 `_metadata.Dispose()` + 占位计时器停 / 放（**不等待**在飞的那条） |

> 为什么把「正在读取标签…」放在**艺术家那一行**：复用现有的三行排版与 1.18.0 刚做好的缓存键，
> 不新增测量路径。代价是"提示出现在词曲人的位置"，这里写明。

## 4. 边界（如实写，也都进了 README）

1. **读取本身不可取消**：`FileStream` 打开不可中断（与 D6 同一类）。能省的只是"没开始的不开始"。
2. **被替掉的请求不会补读**：下次播到那一首才读（有意，避免后台攒活）。
3. **占位可能长时间留着**：离线共享 / 极慢的盘上会一直显示「正在读取标签…」——比挂着上一首的封面诚实。
4. **最多 2 条在飞**：两条都被离线共享卡住时，最新那条要排队（最多等到其中一条回来）。
5. 网络流 / 光盘**不打占位也不起读**（它们没有文件标签）；本地与 UNC 文件都读。
6. 封面解码仍在界面线程（每次切歌一次，1.18.0 量过 CoverView 一帧 1.8 ms 量级）；本版不搬。

## 5. 测试与变异

新增**第 31 项检查**「切歌时的等待」（`tools/SmokeTest/Program.MetadataQueue.cs`，第 26 个运行步骤，
`StepCount` 30 → 31）。全部用受闸门控制的假读取（`MetadataLoad` 接缝）：

1. 先放行第一首 → 封面上来；再把第二首卡住 → 宽限过后**封面被摘掉**、副标题是「正在读取标签…」、
   标题是新文件名、信息页第一行是「状态 / 正在读取标签…」；此刻在飞 1 条。
2. 放行 → 真标签换掉占位；`IsThreadPoolThread == false`。
3. 另起一个窗体连切 20 首（全卡住）：`Starts == 2`、`InFlight == 2`、`Pending == 1`、`Skips == 17`。
4. 放行前两条（已过期），**最新那条继续卡住**：界面必须还是占位（迟到的两份不许盖上来），`MetadataDiscards ≥ 2`。
5. 放行最新那条 → 停在**第 20 首**（不是中间任何一首）。
6. 再起一个窗体：读取卡住时 `Close()` + `Dispose()` 不抛、`IsClosed` 为真；之后放行，迟到的回调不崩。

变异 **5 条**全部按预期变红：

| 变异 | 红在哪（原文） |
| --- | --- |
| 去掉有界（每首直接起一条） | `连切 20 首起了 20 条读取（期望 2 条——只有第一条和最后一条该被读）` |
| 占位时不清旧封面 | `切到第二首之后封面还是上一首的（期望空）` |
| 回填不判 token | `迟到的结果盖到当前这一首上了（标题变成「标题：meta-00」，期望还是占位）`（两条迟到的谁最后回来不定，也可能是 `meta-01`） |
| 读取改回 `Task.Run` | `标签读取跑在线程池上（离线共享卡住时会占着池里的工作线程）` |
| 待读位"留住最早那条"而不是最新 | `放行之后最后停的不是最后一首（标题「」，期望「标题：meta-19」）` |

真实网络那一段（`播放器_TEST_NETOPEN=秒数`，默认 10 秒，只量不判）留在第 29 项检查里：

```
[29/31] 引擎打开不可达网络流（http://192.0.2.1/probe.mp3）：PlayIndex 用了 11 ms、
        之后 1 秒界面计时器跳了 5 拍、60 秒内状态还是「Opening」
```

## 8. 本轮不做

| 事项 | 理由 |
| --- | --- |
| 不可达网络流的"多久算连不上"超时提示 | 本轮只量到现象（60 秒都停在「正在打开…」）；要定超时值、要能和 libvlc 自己的重试分清，单独一轮 |
| `LrcApiToken` 的 DPAPI 加密 | 选项 B；约 1 天，牵涉方案导出 / 导入与损坏抢救 |
| 崩溃取证 | 选项 C；本机无 `cdb` / `windbg`、无管理员 |
| DVD 真盘那两条（D5） | `L:` 现在不在驱动器里 |
| 后台排序 / `VirtualMode` / 复用行 | 1.18.0 已量：模型排序 45 ms、"复用行重排"1,269 ms 比重建还慢 |
| 在线歌词 / 封面落盘缓存 | 新能力，要先定"写哪、多大、怎么清、隐私怎么说" |
| 网络导入第 9 条（目录名带媒体扩展名） | 改成先 `Directory.Exists` 会给每个网络媒体文件多一次 SMB 往返 |

- 全量冒烟 **31 项 / 26 步全绿，222.6 秒**（新加那一步 3.8 秒；1.18.0 是 30 / 25、182.3 秒）；
  干净树 `release-check` **260 秒**全绿（冒烟 238.5 秒；Debug / Release 0 警告、`docs-check` 绿）；
  `播放器_TEST_NETOPEN=60` 单独跑过一次（131 秒，只量，两个地址都是 `Opening`）。
- **两条过程教训**（都进维护手册坑表）：
  1. **变异恢复只许恢复"被变异的那个文件"**。这一轮把三个文件一起从备份恢复，结果把备份**之后**
     才写进 `MainForm.Metadata.cs` 的宽限计时器一起回退了——产品编不过，冒烟构建报 80 个错。
     备份要在"每次变异之前"单独做，恢复也只恢复那一个文件。
  2. **恢复之后必须 `-t:Rebuild`**。备份文件的修改时间比构建产物旧，增量构建会跳过，
     于是"恢复了"其实是"还在跑变异版"（这一轮第一次验变异 3 就是这么假的）。

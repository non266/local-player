# 1.21.0 计划：打开慢流要说一声 + 两处假红按三态收口

> 本轮范围由所有者从 A / B 两个候选里选定 **A+B**（「制定一个版本的计划」时）。
> 版本号 **1.21.0**：改了用户看得见的状态栏行为，按维护手册第 1 节的"解冻"规则走次版本号。
> 日期按本机实测：2026-11-14。

## 0. 目标与成功判据

- **A（产品）**：网络流 / 网络位置超过 **12 秒**还没播起来时，状态栏说一次——
  **只提示，绝不自动停、不自动重试、不标错**。
- **B（测试可信度）**：第 15 步"真鼠标拖动"与第 13 项"全屏进度条"改成**三态**：
  环境不成立 → 打印原因后跳过；前置条件成立仍**硬失败**。跳过必须出声。

成功判据：

1. 死流：到点出现一次提示，`停止` 能退出；慢而能播的流**不会**被停，播起来后状态栏回到「正在播放：…」。
2. 本地文件 / 光盘路径**永不**触发；日志里**没有完整的流地址**。
3. 第 15 步 / 第 13 项：用**产品变异**证明"前置成立时仍然红"，不是把断言改没了。
4. 全量冒烟仍 **27 个运行步骤 / 32 项检查**（不新增步骤/编号），连跑 3 次全绿、每次 **≤ 260 秒**；
   `docs-check`、干净树 `release-check` 全绿；13 条变异逐条红在 §5 的原文上。
5. 文档与版本齐；`dist\` 仍是 1.18 / 1.19 / 1.20 三版；**不发版**（等所有者说"发布"）。

## 2. A 的行为

新增 `Core/SlowOpenWatch.cs`（纯状态机）：

- `Applies(path)` = `MediaFormats.IsStreamUri || IsNetworkPath`：流（http/https/rtsp/rtmp/ftp/mms/udp/rtp/sftp/smb）
  与网络位置（UNC / 网络盘）算；本地文件、光盘不算。
- `Tick(now, state, path)`：状态不是 `Opening` 或 `Applies` 为假 → `Reset()` 并返回 false；
  一次打开记一个起点；到 `ThresholdMilliseconds`（默认 **12 000**）且没提示过 → 返回 **true 一次**。
- 复位是双保险：`Tick` 里按状态复位，**`MainForm.OnEngineStateChanged(Opening)` 再显式复位一次**。
  实现时冒烟抓到了只靠计时器的漏洞：用户"按停止、马上再点播放"时，两次状态变化可能落在
  同一拍 200 ms 计时器里，上一次的"提示过"会被带进这一次（`第二个死流没有提示`）。

`MainForm.SlowOpen.cs`：

- `CheckSlowOpen()` 挂在现成的 200 ms 界面计时器里（`OnUiTimerTick`，`UpdateProgress()` 之后），
  返回 true 时说状态栏 + 记日志；播起来时 `LogSlowOpenRecovered()` 再记"实际等了多久"。
- 状态栏只区分两种措辞：流 →「这个网络流还没有播放起来（网络慢或对方没响应；按「停止」放弃）」；
  UNC / 网络盘 →「这个网络位置还没有播放起来（……）」。
- 日志：`网络上的媒体打开超过 X 秒仍未播放（仍在试，不自动停止）`；**不含地址 / 文件名**。
  播起来后：`网络上的媒体在提示之后播起来了（打开共用约 X 秒）`。

边界：

- **不自动停**：流慢不等于流死；`停止`（`PlayerCommandId.Stop`，`HasMedia` 时可用）是唯一出口。
- 播起来后状态栏自然被「正在播放：…」覆盖；按停止是「已停止」。
- 迷你没有状态栏 → 看不到这句（写进 README 已知限制）；音频窗口有状态栏。
- 阈值是 `SlowOpenWatch` 里的一个常量 + `SetSlowOpenHintForTest` 给冒烟调小。

**顺带收口（做 A 时发现的口子）**：日志里「打开媒体：…」与「时长解析：…」两处原本会写完整的流地址
（可能带 `user:pass` 或一次性参数）。新增 `MediaFormats.DescribeForLog`：网络流缩成
`scheme://host:port/…`，本地路径原样。两处都改用它，冒烟直接断言日志里没有完整地址。

## 3. A 的断言（第 29 项检查，不新增编号）

步骤改名：「探测去重与有界」→ **「网络等待与探测去重」**（保留子串"探测去重"，
README 里的 `dotnet SmokeTest.dll 探测去重` 照旧可用）。`StepCount` 仍 32。

新增 `tools/SmokeTest/Program.SlowOpen.cs`：

- `SlowMediaServer`：`TcpListener` 绑 `127.0.0.1:0`，两种模式——
  **黑洞**（收下请求、读到请求头结束就不回应；`Dispose` 才放行）/ **滴滴**（先等 N 毫秒，再一次性发 WAV）。
- `CheckSlowNetworkOpen()`，在 `CheckProbeDedupeAndBounds()` 的第 6 段之后调用：

| # | 断言 | 实测 |
| --- | --- | --- |
| 1 | 慢而能播的流先说「还没播起来」，再真的播起来 | 阈值 1 000 ms、首字节延迟 2 500 ms：1.0 秒提示、2.6 秒 `Playing` |
| 2 | 死流到点提示一次、**仍停在 `Opening`** | 阈值 800 ms，提示后状态仍是 `Opening` |
| 3 | 按停止能退出 | `ExecuteCommand(Stop)` → `Stopped` + 状态栏「已停止」 |
| 4 | 第二条死流还会提示 | 停止后重新 `PlayIndex(0)` → 再次提示（抓出了"只靠计时器复位"的漏洞） |
| 5 | 纯逻辑：到点只一次 / 新打开重计时 / 本地文件不算 / 网络位置算 | `SlowOpenWatch` 直接调，不依赖窗口 |
| 6 | 日志有"等了很久"、没有完整地址；脱敏去掉用户名 / 口令 / 参数 | `AppLog.SnapshotText()` + `DescribeForLog` |
| 7 | 本地回环被拦（`Accepted == 0`）时打印原因后跳过 | 不判红（环境） |

另加 gated 只量探针：`播放器_TEST_SLOWOPEN=<秒数>`（默认 10）——播黑洞流、每 5 秒打印状态，
用来量 libvlc 自己多久才放弃；实现时用 `播放器_TEST_SLOWOPEN=120` 跑一次，数字见 §10。

## 4. B 的三态（第 15 步 / 第 13 项）

### 4.1 第 15 步：真鼠标拖动（`Program.DesktopLyrics.Drag.cs`）

`enum LyricsDragVerdict { Proceed, SkipEnvironment, Fail }`，纯判定
`DecideLyricsDragHit(cursorInWindow, cursorIdle, hitIsOurs, hitOtherProcess, out reason)`：

| 输入 | 结论 |
| --- | --- |
| 光标不在窗口里 | Skip（"光标已经不在歌词窗口里"） |
| 有人在动真鼠标 | Skip（"有人在动真鼠标（合成输入和真人抢同一个通道）"） |
| 命中我们自己的窗口 | **Proceed** |
| 命中别的进程的窗口 | Skip（"被别的程序盖住"） |
| 其余（我们自己的窗口却点不到） | **Fail** |

真实路径：最多 3 次尝试，每次把光标放到窗口中心、等悬停背景；Skip 打印
`被别的程序盖住（尝试 1/3；光标 …，窗口 …，命中 0x…（pid …，进程名），前台 0x…（pid …））`；
3 次都不成立 → 打印原因后跳过。**能不能点中**仍由既有 `CheckLyricsHitTest`（5 个点 + 字上像素）硬验。
新增 P/Invoke `GetWindowThreadProcessId` 用来区分"别人的窗口"与"我们自己的窗口"。

### 4.2 第 13 项：全屏进度条（`Program.Video.FullscreenBar.cs`）

`enum FullscreenBarVerdict { Ok, SkipEnvironment, Fail }`，纯判定
`DecideFullscreenBarReturn(visible, isFullscreen, hasMedia, isPlaying, foregroundOwned, out reason)`：
看得见 → Ok；不在全屏 / 没媒体 / 没在播 / 前台不是本程序 → Skip（各自带原因）；
都在、条却没回来 → **Fail**。真实路径最多 3 次（必要时 `Activate()` 抢回前台），
Fail 时打印全部事实（全屏 / 媒体 / 在播 / 前台句柄 / 窗口句柄）。

### 4.3 安全网

- 两处纯判定都有 5～6 组**直接断言**（不依赖真前台，任何机器都跑得出来）。
- 产品变异证明"跳过没把硬断言吃掉"：拖动不移动窗口 → 第 15 步仍红；
  `NotifyPointer` 不亮进度条 → 第 13 项仍红。

## 8. 本轮不做

| 事项 | 理由 |
| --- | --- |
| 自动停止 / 自动重试 / 断线重连 | 会杀慢流；要另定"多慢算死"的策略 |

  其实是"60 秒左右才放弃"；12 秒的提示在它前面约 48 秒。
- **第一次三连的两次异常，如实记**：
  - 第 1 轮在**第 6 步**红了一次：`按住不动时时间标签被播放时间盖回去了（「00:00:30」→「00:01:00」）`

    没有放宽、也没有改检查。
  - 第 2 轮在**第 13 步「音轨记忆」**处进程挂住 15 分钟：CPU 几乎不动、界面线程不响应、
    没有弹出任何对话框（`SetAudioTrack` / 窗体收尾那一段）；单独跑「视频功能」是绿的。
  - 杀掉之后**串行重跑三次全绿**（上面那组数字）。两次都没有放宽任何判据；若再复现，
    按维护手册"先复现再改"的规矩另起一轮查。
- **一次真实的功能漏洞是冒烟自己抓到的**：只靠 200 ms 计时器复位时，"按停止、马上再播"
  会把上一次的"提示过"带进这一次（`第二个死流没有提示`）。改成 `OnEngineStateChanged(Opening)`
  显式复位之后转绿。
- **13 条变异全部按预期变红**（原文见 §5）。其中 B1 的恢复踩了"增量构建跳过"的坑
  （`Copy-Item` 把源文件时间改回更旧），之后全部改用 `-t:Rebuild`。
- **干净树验收**：删 `bin` / `obj`、两个工程 `dotnet restore` 之后跑 `release-check` **全绿，251 秒**
  （冒烟 **234.3 秒 / 32 项全绿**）；Debug / Release 都是 **0 警告 0 错误**；`docs-check` 绿；
  `dotnet list package --vulnerable` 无漏洞。
- **与 §9 第 5 条的一处如实说明**："默认 12 秒对 `http://192.0.2.1/probe.mp3` 提示一次"这一条，
  实际是在**本地黑洞 + 默认阈值**上验的（`播放器_TEST_SLOWOPEN=90`：12 秒后状态栏出现提示、
  约 60 秒 libvlc 自己放弃）。没有另起一次真 TEST-NET 的手工观察——两条路在 1.19.0 / 本轮
  量到的状态都是"一直 `Opening`"，走的是同一个 `CheckSlowOpen` / `SlowOpenWatch`。

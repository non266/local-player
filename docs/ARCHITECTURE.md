# 架构现状、债务清单与收敛顺序

这份文档只讲一件事：**这个项目现在哪里开始撑不住了，按什么顺序收拾，以及每一步怎么证明"行为没变"**。

它是在一次外部代码评审之后写的（评审给了约 8/10，并明确建议"不要再让 AI 无限加功能，
该做架构收敛了"）。那条建议是对的：功能已经够用，继续加只会让 8 分变成 6 分。

---

## 1. 现状（数字是量出来的，不是估的）

| 位置 | 规模 |
| --- | --- |
| 主程序（`播放器.csproj` 编译的全部 `.cs`） | 约 26,000 行 / 90 个文件 |
| `Core/` | 约 8,700 行 / 34 个文件 |
| `Ui/` | 约 7,700 行 / 26 个文件 |
| `MainForm*` 这一族 partial | 约 9,500 行 / **29 个文件**、81 个实例字段（P1 之前是 14 个文件 / 90 个字段） |
| `tools/SmokeTest/` | 约 10,300 行 / 23 个文件（拆之前是 8,900 行、**单个文件**） |

> 数字最后一次量是在第 16 节那次"设置方案"之后；`Core/` 与 `Ui/` 的文件数比初稿多，
> 是 P1 那四刀把东西从 `MainForm` 挪进了它们里面（后来那次功能又添了几个）。

分层名义上清楚（`Core` 与界面无关、`Ui` 是可复用零件、`MainForm*` 是装配），
但**真正的耦合点是 `MainForm` 这个 god class**：

- 设置、播放引擎、播放列表模型、时长扫描器、播放历史、当前曲目的标签 / 歌词 / 封面、
  在线查找的会话缓存、歌词偏移……全挂在这一个对象上，82 个字段互相可见；
- partial 只做到"文件级"切分，**没有做到职责切分**：任何一个 feature 的改动都要动 3~8 个文件，
  并且要在 4 个菜单宿主（文件菜单 / 播放列表右键 / 工具栏下拉 / 歌单窗口）上手动保持同步；
- 表现层到处是"手写一遍 Tag + 递归刷新"的菜单模式（桌面歌词、在线歌词、歌词偏移、歌单库各写一份）。

症状不是"行数多"，而是：**加一个小功能要动很多文件、而且很容易顺坏别处**。

## 3. 收敛顺序（每一步都要求"行为不变"）

原则：**先让安全网可信，再动结构**。顺序不能反——不然重构就是在赌。

### P0（本轮已完成）

1. ✅ **日志与错误处理**：`Core/AppLog.cs`（内存环形缓冲 500 条 + 落盘 + 1 MB 轮转 + 崩溃处理器）；
   47 处"决定不管"的异常全部换成 `AppLog.Swallowed("理由", ex)`，**空吞异常从 54 处降到 0**（只剩 `AppLog` 自己那两处：写日志失败不能再递归记日志）；
   `帮助 → 查看日志… / 打开日志文件 / 记录诊断日志`；设置里加 `DiagnosticLog` 开关。
2. ✅ **两处抖动检查**：字体样本改成确定性候选 + 撞车重试；真鼠标拖动加"光标是否静止"判据 + **判据自检**。
   关键是"**把夹具撞车和真 bug 分开判**"：
   - 族名压根没进应用的字体表（GDI+ 把改造过的字体并进了已装过的那个族）→ 夹具撞车，换样本；
   - 族名在表里、GDI 却把字画成别的字体 → **真 bug**，硬失败。
   变异验证：把 `RegisterForGdi` 关掉，仍然以
   `GDI 认不出导入的字体族「Zzqzzzzz」，它会把字画成「宋体」` 硬失败（不会被"跳过"掩盖）。
3. ✅ **时长扫描可诊断**：解析超时 / 失败 / 每次耗时都进日志。
4. ✅ **顺手抓出并修掉一个真 bug（时长回填竞态）**：
   扫描在构造函数里就开跑，结果可能**早于窗口句柄**回到主窗体；以前那一支是
   `if (_disposed || !IsHandleCreated) return;`——那条时长就永久丢了，界面上表现为
   **某一项一直是 `--:--`**（而且只在"扫描比建窗口快"时出现，属于抽风式复现：
   实测三次里红两次）。现在改成先攒起来，`OnHandleCreated` 时补上（和 `PlayerEngine`
   早就有的 `FlushPendingUiActions` 一个道理）。
   新增回归检查 `CheckDurationsBeforeHandle`：**刻意不碰句柄**，先把扫描跑完再要句柄，
   把那个时间窗固定下来；变异（改回直接 return）立刻以
   `时长回填检查：句柄就绪前解析好的时长丢了（0 → 0 / 3 项…）` 失败。
5. ✅ **拆测试文件**：`tools/SmokeTest/Program.cs`（9,000 行单文件）→ **22 个文件、最大 1,600 行**，
   按功能/检查点分文件，公共件进 `Program.Harness.cs` / `Program.Native.cs` / `Program.Fixtures.cs`
   （详见第 4 节）。纯搬家：可见性、签名、检查逻辑一律没动。
6. ✅ 顺手修掉一个一直没人看的构建问题：测试工程是 `<Nullable>disable</Nullable>` 却在用
   `string?` / `T?` 注解，全量重编译时冒出 **13 条 CS8632**（以前增量构建只编译改动文件，所以从没露头）。
   改成 `<Nullable>annotations</Nullable>`——只开"注解"上下文、不开可空性分析，与本测试无关的
   几百条可空警告不会被引进来。

**稳定性实测**：上一轮改完之后连续跑 4 次全量，**4/4 通过**；改之前 8 次里红了 3 次
（时长竞态 ×2、私有字体夹具 ×1、真鼠标拖动 ×1）。这一轮（拆测试文件）前后又各跑一次全量，
**2/2 通过**，其中一次连"真鼠标拖动"也真的跑到了（`窗口跟着走了 -60,-40`）。

### 那条"未解释的红"：已解释，并且修掉了

`歌词字体检查：垃圾文件居然被当成字体导入成功了`——曾经在约 10 次全量里红 1 次，单步连跑 15 次
也复现不了。**结论：不是夹具问题，是真 bug**（虽然影响不大）。追它的过程值得留着：

1. **先把复现条件缩到最小**：单步 `桌面歌词` 连跑 15 次 → 0 次红。说明它只在**全量**那种
   "进程里已经干过很多字体活"的状态下出现。
2. **写压力探针逼它**（临时加到第 15 步）：在同一个进程里**先真导入一个系统字体**，
   再连打 200 次垃圾文件（文本 / 全 0 / 真字体截断）。结果：
   ```
   垃圾字体压力：200 次里有 1 次被 GDI+ 接受：#15（21 字节）→ Arial
   ```
   21 字节的文本被认成了 **Arial**——也就是**刚导入的那个字体**。
   根因清楚了：**GDI+ 探测一个坏文件时会报出进程里上一个装过的字体族**
   （`PrivateFontCollection` 探测路径上的状态泄漏，不是这个文件里的东西）。
3. **后果**（真实用户能撞见的）：垃圾文件被当成"导入成功"留在字体库里，
   菜单里多出一个幽灵字体；下次启动又要为它失败一遍。
4. **修法**：碰 GDI+ 之前先看**文件头**——`FontLibrary.LooksLikeFontFile()` 认四种 sfnt 魔数
   （`0x00010000` / `OTTO` / `true` / `ttcf`，正好覆盖支持的四种扩展名）。
   确定性的判断不交给 GDI+。错误提示也直说了："这个文件不是字体文件（扩展名像，但文件头对不上）"。
5. **验证**：
   - 去掉文件头预检（变异）→ 新加的检查**确定性红**：
     `垃圾字体检查：21 字节的垃圾被当成字体导入成功了（报出来的字体族：Arial）`；
   - 加回预检 → 连跑 10 次单步 + 3 次全量，全绿。

**留下的已知容忍（如实记）**：**截断的真字体**仍然会被接受——把 `arial.ttf` 的前 32 字节或前 2KB
当字体导入，GDI+ 照样报出 `Arial`（文件头合法，所以预检放行）。这次不去管它：GDI+ 可能真的从
前缀里读到了 name 表，而且"半个字体文件"本来就不是正常输入；要做的话得自己解析 sfnt 表结构，
代价不划算。压力探针里那两种内容因此**没有**写进正式检查（只留非 sfnt 的垃圾，保证检查是确定性的）。

## 8. P1 第四刀：`PerFileAdjustments`（已完成，但先纠正了前提）

**先说结论**：D3 原话是"同一概念有两三处实现……**三套存储**"，这句是错的。
动手前核对了存储层：三样调整（音画延迟 / 字幕延迟 / 歌词偏移）从一开始就存在
**同一个 `PlaybackHistory` 记录、同一个 `history.json`** 里，没有三套存储。
按原话去"合并三套存储"会是一场凭空的重构。

真实的债只有两条，都不大，但第二条是真 bug：

1. 两处"记住 / 恢复"流程各写一遍：延迟一份（`RememberDelays` / `RestoreDelaysForCurrentMedia`）、
   歌词偏移一份（`ApplyLyricsOffset` / `RestoreLyricsOffsetForCurrentMedia`）。
2. **落盘时机是坏的**：歌词偏移改一次就 `SaveInBackground()`，两个延迟却只等定时器——
   而那个定时器（以及切歌 / 退出时的落盘）全都以**「记住播放进度」这个开关为前提**。
   于是关掉「记住播放进度」之后，用户调的音画 / 字幕延迟**一次都不会写进 history.json**
   （重启回到 0）。那个开关管的是"要不要记播放进度"，跟"要不要记住我调好的延迟"没有半点关系。

**做了什么**：新增 `Core/PerFileAdjustments.cs`，作为"按文件记住的调整"的唯一落点：

| 原来 | 现在 |
| --- | --- |
| `_history.RecordDelays(path, 音, 字)`（不落盘） | `Adjustments.RecordDelays(path, 音, 字)`（**改一次就落盘**） |
| `_history.RecordLyricsOffset(path, ms)` + `SaveInBackground()` | `Adjustments.RecordLyricsOffset(path, ms)` |
| `_history.TryGetDelays(...)` + `_history.TryGetLyricsOffset(...)` | `Adjustments.Get(path)` → `TrackAdjustments`（三样一次拿到） |

- 存储、文件格式、`PlaybackHistory` 一行没动；变的只是"谁来记、什么时候落盘"。
- `MainForm` 族实例字段 80 → 81（多了一个 `_adjustments`，但它替掉了散落各处的落盘判断）。
- **代价写在这里**：调整变成"每改一次就排一次后台写"。连按热键时 `SaveInBackground` 会合并
  （已经有一次写在路上就直接返回，变化由下一次调用带走），所以不会写爆；但一次调整的序列化
  仍在调用线程上做（几毫秒）。歌词偏移早就是这个行为了，这次只是让两个延迟跟它一致。

**测试这边**：新增 `CheckPerFileAdjustments`（第 8 步）——这三样以前**一条检查都没有**
（歌词偏移有几条，两个延迟是零）。现在验：

1. 三样**各记各的**、不会串到别的文件；
2. **读不建壳**：读一个没记过的文件不会凭空多出记录（否则"最近播放"会被读操作污染）；
3. 网络流不记、空路径不炸（和播放进度同一条规矩）；
4. **「清除最近播放」不碰这三样**（以前只对歌词偏移验过，延迟没验）；
5. **改一次就已经落盘**：刻意不调 `Save()`，只等后台那次写 —— 这条钉的就是上面那个真 bug。

**验证**：全量 19 项通过；Debug / Release 均 0 警告 0 错误。三组变异全部被钉住：

- 记延迟之后不落盘（回到等定时器的老样子）→ `按文件调整：改了延迟没有马上落盘（等定时器的话，用户当场关程序就丢了）`
- 「清除最近播放」连调整一起清掉 → `按文件调整：「清除最近播放」把音画 / 字幕延迟也清掉了（0 / 0）`
- 读的时候把音画 / 字幕延迟串了 → `按文件调整：A 的音画 / 字幕延迟没记对（-250 / 150 / 歌词 0）`

**一个过程记录**（值得留着）：这组检查第一次跑就红了，报的是"「清除最近播放」把歌词偏移也清掉了"。
第一反应是"抓到一个 bug"，但查下去发现是我**检查写错了**：`SaveInBackground` 在已有一次写入在路上时
会直接返回（变化留给下一次），所以"连着记两笔、只等第一笔落盘"时，第二笔本来就还没落地——

**顺序很重要：检查红了先分清是代码错还是检查错**，两边都可能是错的。

**顺带记下的另一条**（没改，留作以后）：`CommitHistory` / `FlushHistory` 以

## 13. 一次界面收敛：把「保存 / 加载播放列表」并进歌单菜单

> 这一节是唯一一次"动界面"的改动（用户直接点的名），不属于前面 P0~P3 的搬家清单；
> 记在这里是因为它同前面几节一个规矩：**先量出现状，再改，再用变异证明牙还在**。

**动手前的问题**：同一个动作有两个入口，而且**两边的"载入"语义还不一样**——

| | 保存 | 载入 |
| --- | --- | --- |
| 文件菜单（`Ctrl+S` / `Ctrl+L`） | 存到**任意位置**的 m3u | 从 m3u **追加**进当前列表 |
| 「我的歌单」子菜单 | 存进**歌单库**（固定目录、有名字、可覆盖 / 改名 / 删除） | 点一行**替换**当前列表（会先问一句） |

菜单上没有任何提示告诉你该用哪个；两个"载入"一个追加一个替换，点错一次就是
"列表多出一倍"或者"当前列表没了"。歌单菜单还挂在三个宿主上（文件菜单 / 播放列表右键 /
工具栏按钮），而保存与载入只在文件菜单里。

**改法**：并成 `文件 → 播放列表` 一个子菜单（三个宿主共用同一份重建逻辑，所以一次全改到），
里面用分隔线分成两段：

- **歌单库**：打开歌单窗口 / 新建空歌单 / 保存当前列表为歌单（`Ctrl+S`）/
  覆盖 / 重新载入 / 重命名 / 删除 / 一首一行 / 打开歌单文件夹
- **m3u 文件**：从 m3u 文件**追加**（`Ctrl+L`）/ 从 m3u 文件**替换当前列表** /
  另存为 m3u 文件（`Ctrl+Shift+S`）

顺带修掉的几处毛糙：

1. **语义写进菜单名**——追加和替换是两个菜单项，不再靠猜；
2. 空列表时「保存为歌单 / 另存为 m3u」都**点不动**，而不是点下去才弹一句"没有内容"；
3. 另存为的默认文件名跟着当前歌单（`歌单A.m3u`），不再永远是 `播放列表.m3u`；
4. `Ctrl+S` 回归"保存这个列表"的直觉（进歌单库），存到任意位置让给 `Ctrl+Shift+S`；
5. 提示语里的菜单名跟着改（`可在「播放列表」菜单里切过去`），工具栏按钮的 tooltip 前缀
   从「我的歌单：」改成「歌单：」。

**行为上刻意保留的**：m3u 的**追加不去重**（同一个文件在列表里出现两次是合法用法）；
用一个外来 m3u **替换**当前列表时，当前歌单的**关联留着**、内容标成「未保存」——
想把它收进歌单库接着点「覆盖保存」就行，不想要就点「重新载入」退回原来那份。

**拆出来的两个可测入口**：`MainForm.LoadPlaylistFromFile(path, replace)` 和
`MainForm.SavePlaylistToFile(path)`——对话框只负责选文件，逻辑都在它们身上，
于是冒烟测试能直接把"追加 / 替换"两条语义各跑一遍，不用去点模态窗口。

**验证**：第 17 步加了菜单形状（文件菜单下不再单挂那两项、追加与替换分列、
菜单上的快捷键提示与 `MainForm.Shortcuts.cs` 里真正接的键一致、空列表时保存两项点不动）
+ m3u 往返（另存为写出的条目数、追加不去重、替换整个换掉且关联留着并标「未保存」）。
两个变异都按预期变红：

- 「另存为」在空列表时也点得动 → `列表空着，「保存为歌单 / 另存为 m3u」还能点`
- 把追加与替换的语义对调 → `追加没把条目并进来（5 项，期望 10…）`（状态栏里那句
  `已用这个 m3u 替换当前列表：5 项` 直接把"它走了哪条路"摊在报错里）

`Ctrl+Shift+S` 接另存为对话框、`Ctrl+L` 接选择框——三条都要开模态窗口，冒烟测试驱动不了。
这几条靠"菜单上的显示字符串 + 实际接键的 switch 分支在同一次改动里一起改"来保证，
测试只钉住了前者的字符串。

3. **变异验证**：新加的检查必须"改坏了就会红"。做法是把被测行为临时改错，
   确认测试以一句具体的错误失败，然后改回来。例：

| `Core/SavedName.cs` | 从 `PlaylistLibrary` 抽出来的名字规则（非法字符指名道姓、Windows 保留名、结尾点号、自然排序）。**歌单库与方案库共用一套**——否则会出现"歌单叫 CON 会被挡、方案叫 CON 却存下去了" |
| `Core/SettingsProfile.cs` | 7 组共 60 项的清单 + **按组用 JSON 合并**（不是 60 个属性逐个赋值：那样漏一个没人发现）+ 覆盖率自检（`UncoveredProperties` / `UnknownProperties`） |
| `Core/SettingsLibrary.cs` | 方案库：存 / 列 / 读 / 改名 / 删 / 导入 / 导出；坏文件挡住并如实标出来 |
| `Ui/SettingsLoadDialog.cs` | 载入时挑分组：每行写明这一组和当前**有几项不一样** |
| `MainForm.SettingsProfiles.cs` | 菜单、当前方案、自动写回、把合并后的设置装到界面上 |
| `MainForm.ApplySettings(bool resetTrackPanel)` | 载入方案时**不清掉**侧栏里当前曲目的内容（启动时才清）；顺手把 `_settings` 从 `readonly` 改成可替换 |

**一条必须记住的语义**：**方案文件等于"你现在这一套"，不是"上次保存时的快照"**。
有当前方案时，退出（以及切换方案前）都会把现在这一套写回去；因此"只勾了部分分组载入当前方案"
之后，没勾的那些保留当前值、方案文件也跟着变成合并后的样子。这是"当前方案 = 你现在这套设置"
的必然结果，代码和 README 里都写明了。

**验证**（第 20 步 + 三个变异，都按预期变红）：

- 把 `Theme` 从「界面与主题」里删掉 → `设置分组：有设置项没被归进任何一组（Theme）`
- 让 `Merge` 忽略勾选、整份照搬 → `设置合并：只勾了「播放」，界面与视频输出却被一起改了`
- 去掉退出时那次写回 → `改动没有自动写回方案文件（音量 80，期望 85；主题 Auto，期望 Vlc）`

### 16.1 环境记录：这台机器上的 SDK 与"离线还原"

做这一轮时踩到的两件事，都跟代码无关，但下次会再遇到，记在这里：

1. **默认 SDK 是 10.0.401，而它要 net8.0 的引用包 8.0.31；本机 `packs\` 里只有 8.0.3**
   （那是另一个 SDK **8.0.202** 的版本）。于是 `dotnet build` 直接报
   `NETSDK1127: 未安装目标包 Microsoft.NETCore.App`，而外网恰好不通（SSL 认证失败）。
   把 SDK 钉回 8.0.202 能绕过包的问题，但**会撞上语言版本**：
   `MainForm.DesktopLyrics.cs` 用了 C# 14 的 `_desktopLyrics?.FontFamilyName = …`（null 条件赋值），
   SDK 8 的编译器只认到 C# 12。**结论：这个工程要用 SDK 10 构建，别去钉 8.0.202。**
2. **离线还原的正确姿势**：所需包都在 NuGet 的 HTTP 缓存里
   （`%LocalAppData%\NuGet\v3-cache\**\nupkg_<id>.<version>.dat`，本体就是 nupkg）。
   把它们复制成一个本地文件夹源，再指定它还原即可：
   `dotnet restore 播放器.csproj -s <本地源> -p:NuGetAudit=false`。
   这一轮需要的四个框架包是 `microsoft.netcore.app.ref` / `microsoft.windowsdesktop.app.ref` /
   `microsoft.aspnetcore.app.ref` / `microsoft.netcore.app.host.win-x64`（都是 8.0.31），
   外加三个 libvlc 包。还原一次之后全局包缓存就齐了，之后的构建都能离线。
3. 顺带一提：**别把临时的构建输出目录放在工程目录里**。
   它会被默认的 `**/*.cs` 通配符当成源码（连它自己生成的 `AssemblyInfo.cs` 一起），
   报一堆 `CS0579: 特性重复`——排查了半天才发现是自己留下的临时目录。

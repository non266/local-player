## 1. 什么叫"稳定维护期"

架构收敛那一轮（`docs/ARCHITECTURE.md` 第 2 节的 D1~D9）已经清完，
项目从这里开始进入维护期。三条判据**同时成立**才算：

1. **功能面冻结**：不再新增能力。想加的东西先写进本手册第 3 节或 CHANGELOG 的「计划」，
   不直接动代码。
   （**例外**：项目所有者明确要求加某一条时按"解冻"处理——记进 CHANGELOG 的「新增」、
   按语义化版本升**次版本号**、断言与变异一个不少。1.1.0 的桌面歌词控制条就是这么进来的；
   1.2.0 的「默认空列表 + 启动时恢复上次播放列表开关」也是。）
2. **每次改动都有断言与变异验证**，全量 20 步冒烟必须绿，Debug / Release 零警告。
   *写断言的两条经验*（这一轮第 15 步踩出来的）：
   - **不要拿"早先拍下的状态"当基准**：窗口是跟着文字伸缩的，而界面计时会不断把真实播放位置
     推过来换掉文字。要比"开了控制条之后变高了吗"，就在同一段同步代码里"关掉量一次、打开量一次"，
     中间别泵消息；泵了消息，比的就不是那个开关，而是"换了句歌词"。
   - **别依赖"播放位置还没走到某一句"**：一条只把第一行写长的歌词，会在位置走过第二行时
     随机变成"没有折行"。要么让两行都长，要么设完位置立刻断言。
   *这一轮（1.2.0 的启动开关）又加两条*：
   - **开关类的改动要验两侧的对比**：只验"关掉之后是空的"，在"那个功能压根没生效"时也会绿
     （例如歌单文件根本没建出来，"没挂歌单名"自然成立）。让同一份场景在开 / 关两种设置下各跑一遍，
     差别只能来自那个开关，才算验到。
   - **改默认值等于改所有依赖它的既有断言**：默认改成"空列表"之后，「重启后当前歌单还在」
     那条再也走不到恢复那一步（不是功能坏了，是它的前提变了）。改默认值要全量跑一遍，
     把那些"以前靠默认值顺带成立"的断言的前提**显式**写出来。
3. **已知问题有明确归属**：修 / 不修 / 等触发，每条都写清判据（第 3 节），不靠"以后再说"。

**明确不做**：重写、换 UI 框架、无红测试的重构、为"看起来更现代"改交互、
为了功能数量而加功能。

## 2. 每次改动的四件套

1. **先看现状**：读代码、量数据（"我记得是这样"不算），把现状写进注释或文档。
2. **改**：一次只做一件事；搬家就只搬家（行为零变化），修行为就顺手加断言。
3. **验证**：跑 [tools/release-check.ps1](../tools/release-check.ps1)（Debug + Release 构建 + 全量 20 步），
   **外加一个"改坏了就会红"的变异**——把被测行为临时改错，确认测试以一句具体的话失败，再改回来。
   （变异没红，先确认变异真的写进去了：曾经因为缩进猜错、`Replace` 没命中，导致"测试通过"。）
4. **同步文档**：README（功能面）/ 本手册（分诊表、纪律）/ [CHANGELOG.md](../CHANGELOG.md)（发版）。

```powershell
# 本机默认策略禁止直接跑 .ps1，所以走 -ExecutionPolicy Bypass
powershell -NoProfile -ExecutionPolicy Bypass -File tools\release-check.ps1

# 只看某一块（会把它依赖的前置检查一起带上）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\release-check.ps1 -Filter 歌单

# 只构建不跑测试（改文档时用）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\release-check.ps1 -SkipSmoke
```

### A 必修（2 条已修，0 条待修）

修完的条目**留在这里不删**——"为什么它算必修"这个判据比"修没修"更值得留下。
状态记的是当时那一版；发版后见 [CHANGELOG.md](../CHANGELOG.md)。

| # | 问题 | 为什么算必修（实测） | 修法 | 状态 |
| --- | --- | --- | --- | --- |
| A1 | 启动时逐个 `File.Exists` 上次的播放列表（`RestoreSession`，在窗体构造函数里） | **启动被卡住**：这台机器上实测，访问一个离线的网络路径一次查询 **>25 秒**（本地不存在的文件只有 4 ms）——上次从 NAS 播过的话，几十条就是"双击之后半天不出窗口"；而且那些条目还会被静默丢掉 | 启动恢复**一次磁盘都不查**（列表原样恢复、窗口立刻出来），打不开的交给后台线程核对：标记 + 状态栏说明，**不删条目**（网络盘暂时离线时下次挂上还能播）；`PlayIndex` 对已标记的条目直接跳过，不再等 SMB 超时 | **已修** |
| A2 | 全局媒体键只报告"注册上了几个"，不区分是哪几个 | **静默失败**：4 个里只成功 1 个时界面不提示，另外 3 个按了没反应（媒体键是抢占资源，别的播放器占了就注册不上） | `MediaKeys.Register` 返回**真正成功的那些 id**，`DescribeMissing` 把缺的名字写成一句话（"全局媒体键有 1 个没注册上：下一首…"），启动时并进 `ReportLoadWarnings` 一起显示 | **已修** |

> 两条的共同点值得记住：**改的是"把发生了什么说清楚"，不是加功能**——
> 维护期里最该优先做的往往就是这一类。
>
> 验证（四条变异都按预期变红）：恢复时同步查磁盘 → `构造函数返回时列表里有 2 项，期望 3`；
> 后台核对不标记 → `后台核对没有把打不开的那条标出来（HasError=False、原因「（空）」）`；
> 提示永远为空 → `缺了「下一首」但提示里没写出名字`；
> 把注册失败当成功 → `明明被测试占着，「下一首」却被算成注册成功了`。
> "媒体键被占"那条是<b>真抢占</b>验的：测试自己先用 `RegisterHotKey` 占住那个键再开主窗体。

### B 可修（3 条已修，2 条待修）

| # | 问题 | 判据 | 修法与状态 |
| --- | --- | --- | --- |
| B1 | 歌单窗口一次只能操作一个歌单（不支持多选批量删除），也没有拖拽排序 | 真别扭但可控：删十个要点十次 + 确认十次 | 列表改多选；多选时"针对一份歌单"的按钮（载入 / 追加 / 重命名）点不动、「删除」按钮写着会删几个，一次确认**逐个删**、删不掉的点名说原因；排序保持自然顺序（不做拖拽）。**已修**——变异：批量删除只删第一个 → `选了两份歌单，批量删除只删掉 1 个`；多选时载入还能点 → `多选之后按钮状态不对（选了 9 项、载入 能点…）` |
| B2 | 设置文件损坏时不尝试"丢弃坏字段、保留能读出来的部分" | 不丢数据（有 `.corrupt` 备份），但**丢掉的是用户全部设置**：窗口尺寸、主题、当前歌单、播放列表一起清零 | `AppSettings.TrySalvage`：每个属性的原始片段**单独**反序列化一遍，好的留着、坏的记名字；用 `Utf8JsonReader` 逐项读，所以**语法坏在中间也能救出坏点之前的部分**；提示里写明"保住了几项、哪几项用了默认值"；一项都救不回来才整份退回 + 备份。**已修**——变异：一项都不救 → `能救的项没有救回来（保住 0 项、丢了 []）`；不点名 → `提示里没说清是哪一项用了默认值` |
| B3 | 双语歌词（同一时间戳的原文 + 翻译）只会显示其中一行，另一行永远轮不到"当前句" | 解析后按时间稳定排序、`LineIndexAt` 取最后一条命中的行，于是"译文赢"、原文永远是暗的；桌面歌词的第二行也只能显示下一句 | 同一时间戳的多行算**同一句**：`LineIndexAt` 退回这一组的**第一行**，侧栏里这一组**一起高亮**；新增 `CompanionOf`（同时间戳的译文）与 `NextGroupStart`（跳过整组找"下一句"）；桌面歌词第二行优先放译文（`有翻译时第二行显示翻译`，默认开），关掉就换回下一句。**已修**——变异：不退回组首 → `同一时间戳的两行没有算成一句（当前行下标 1，期望 0）`；视图不分组高亮 → `同一时间戳的两行没有一起高亮（高亮的是 [0]，期望 [0、1]）`；默认不显示译文 → `双语歌词没有显示成「原文 + 译文」（现在「原文一」/「原文二」）`；"下一句"不跳组 → `关掉翻译之后第二行没有换回下一句（现在「原文一」/「译文一」）` |
| B4 | 列表筛选状态下不能拖动换位 | 有意禁用（界面行与模型索引不连续，拖动会有歧义），会提示先清空搜索框 | 要么允许"在筛选视图内移动"并定义清楚插到哪里，要么保持现状；**倾向保持**，除非真的有人被绊住（1.3.0 点名时没点它，维持现状） |
| B5 | **播放中拖动进度条，右下角"当前时间"反复跳回真实播放时间**；同源两处：按住拖到进度条外面就不跟手、右键点一下也会 seek | 所有者实际踩到（"反复显示当成进度"）。不丢数据，但**用户看得见的错**：拖动时界面说的和用户做的是两件事 | 根因：`UpdateProgress()` 里的 `if (!_userSeeking)` 只护住了滑块取值，**时间标签在护罩外**，计时器每 200 ms 覆盖一次；`FlatSlider.OnMouseLeave` 又在捕获期间把拖动状态清掉；`_userSeeking` 还不分按键。**已修（1.2.1）**——第 6 步新增 `CheckSeekBarDragging`（60 秒素材 + `SendMessage` 摆四段时序：按住不动 / 拖出控件 / 松手 / 右键），三个变异逐个变红：`按住不动时时间标签被播放时间盖回去了（「00:00:30」→「00:00:00」）`、`按住拖到进度条外面之后不跟手了（500 → 离开后 500 → 再移动 500）`、`按住右键时界面计时器停摆了（1.5 秒里时间标签一直是「00:00:54」）` |

**M7 · `SaveInBackground` 在"写入在飞"时丢掉那次快照（代码里读得出来，建议进 1.2.1）**

- 现状：`Core\PlaybackHistory.cs` 的 `SaveInBackground()` 在**已经有一次后台写入在飞**时直接
  `return`，注释写的是"那次写入之后的内容变化会由下一次调用带走"。问题是**"下一次调用"不一定存在**：
  `CommitHistory` / `FlushHistory` 都以**「记住播放进度」这个开关**为前提，关掉之后，
  按文件的调整（歌词偏移 / 音画延迟 / 字幕延迟）**只剩** `PerFileAdjustments.Record*` 这一条落盘路径。
  于是：关掉「记住播放进度」→ 调一次偏移（正好撞在那次在飞的写入上，`SaveInBackground` 早退）
  → 立刻关程序，这次调整可能**只留在内存里**。
- 同一处的第二个口子：退出时那条同步的 `Save()` **不看 `_writeInFlight`**，它可能和仍在飞的旧快照
  **交错**——旧快照后落地就把新状态盖回去。两处一起收干净。
- 为什么现在提：1.2.0 验收时第 18 步红过一次（M1′），逐条排查时走到过这个窗口。
  **没有证据说就是它**（当时磁盘上确实是 500），但它是"调整改一次就该落盘"这条承诺上
  **唯一读得出来的缺口**，而修它的成本很低——所以不等复发，直接排进 1.2.1。
- 修法：写入任务的 `finally` 里清掉 `_writeInFlight` 之后**再看一眼 `_dirty`**，仍为真就再排一次
  （"一直写到不脏为止"）；`Save()` 与 `_writeInFlight` 的关系也要理清（要么等它、要么自己也排队）。
- 断言与变异：给 `PlaybackHistory` 加一个**测试用的写入门闩**（`internal`，例如
  `BeforeWriteHook` / 一个 `ManualResetEventSlim`），让测试能把一次写入**按住**：
  按住 → 改一个偏移 → 放行 → 断言文件里最终是**新值**。变异：把"再看一眼 `_dirty`"那步删掉 →
  断言必须以"改动没落盘"变红。
- 成本 S（1 小时）。**已做（1.2.1）**——第 8 步新增 `CheckHistoryWriteBehind`：
  给 `PlaybackHistory` 加了测试用门闩 `BeforeWriteGate`（把一次写入按住），确定性摆出
  "写入在飞时又改了一次"与"退出时同步写在等在飞那次"两段时序；
  两个变异变红：`写入在飞时改的那一次没有最终落盘（磁盘上是 111 毫秒，期望 222）`、
  `退出时那条同步写没有等在飞的那次写入（7 ms 就返回了；在飞的那次要 300 ms 才放行）`。
  ⚠ **修的时候踩到一条更值得记的**：第一版让"写入任务自己复查 `_dirty` 再重写"，
  结果把**别的实例的旧快照**也冲了出去，当场被第 8 步的老断言抓住
  （`按文件调整：改了延迟没有马上落盘`）。历史是"**一个实例一份内存副本、共写同一个文件**"，
  所以补写必须**由持有这次改动的那个实例**去做；现在这条判据写在
  `PlaybackHistory.SaveInBackground` 的注释里。

## 4. 发布纪律

- **版本号**只有一个地方：`播放器.csproj` 里的 `<Version>`（现在是 `1.2.1`，与 tag `v1.2.1` 对应）。
  界面上是"关于"框里那一行，读的就是程序集版本；取不到时显示「未知版本」——
  那里**不要**再写一个数字兜底，否则迟早和 csproj 对不上。
- **每次发版四步**：改版本号 → 在 [CHANGELOG.md](../CHANGELOG.md) 写一节 →
  `tools\pack.ps1` 出安装程序与便携 zip → 打标签（`v1.0.1` 这种格式）；
  发版前跑一次 `tools\release-check.ps1`，把结果记进 CHANGELOG 那一节。
  打包脚本读的是同一个 `<Version>`，所以**不用**在任何地方再抄一遍版本号。
- **发行产物**：落在 `dist\`（不入库）。安装程序与便携 zip 的 SHA256 写进 CHANGELOG，
  别人好核对拿到的是不是同一份。挂到 GitHub Release 时**先复制成 ASCII 文件名再传**：

  ```powershell
  # 直接传 dist\全能本地播放器-….exe 的话，资产名会变成 -1.0.1-.exe（见下表"传中文参数"那条）
  $v = '1.0.1'; $stage = "$env:TEMP\release-assets"; New-Item -ItemType Directory -Force $stage | Out-Null
  Copy-Item "dist\全能本地播放器-$v-安装程序.exe" "$stage\local-player-$v-setup.exe"
  Copy-Item "dist\全能本地播放器-$v-便携版.zip"   "$stage\local-player-$v-portable.zip"
  gh release create "v$v" --verify-tag --latest --title "$v" --notes-file <说明文件> "$stage\*"
  ```

  传完核对（**服务端 digest 必须等于本地 `Get-FileHash`**，这一步能发现上传损坏）：

  ```powershell
  gh api repos/non266/local-player/releases/tags/v1.0.1 --jq '.assets[]|[.name,(.size|tostring),.digest]|@tsv'
  curl.exe -sL -r 0-2047 -o NUL -w "%{http_code} %{size_download}" <资产的 browser_download_url>
  ```

  （资产名带 `-` 开头时 `gh release delete-asset` 会把它当开关拒掉，改用
  `gh api --method DELETE repos/<owner>/<repo>/releases/assets/<id>`。）
  发版前**务必**在产物自己的目录里跑一遍冒烟（装出来那份 / 解压出来那份），
  而不是只验开发目录里的——libvlc 的插件树能不能被找到，只有真装一遍才知道。
  ⚠ Inno 的安装器 / 卸载器会把自己复制到 `%TEMP%\is-*.tmp` 再运行，原进程立刻退出，
  所以 `Start-Process -Wait` **等不到**它真正结束：验证卸载要轮询"目录消失"，
  否则会误判成"卸载没删文件"（本轮踩过）。
- **打包工具**：Inno Setup 6（`ISCC.exe`）+ 7-Zip。⚠ **Inno Setup 商用要买许可**，
  个人 / 非商业免费——写在这里，免得以后拿去卖才发现。
- **数据兼容规矩**：`settings.json` / `history.json` / 歌单（m3u8）/ 设置方案（json）
  **只增字段、不改语义**；读到未知字段忽略、缺字段用默认值（现有实现已经是这样）。
  确实要改语义（比如单位从秒改成毫秒、目录布局变化）时，必须：
  单列一节「破坏性变更」+ 写清用户需要做什么 + 留一版过渡。
- **依赖不追新**：`libvlc` / `LibVLCSharp` 定版是稳定性的来源。
  联网时跑一次 `dotnet list package --vulnerable`，把结果贴进 CHANGELOG；
  只有出现真实漏洞或必须的修复才升，升级后照样跑全量 + 变异。

### 本机环境注意（踩过的坑，和代码无关）

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| **在仓库目录里双击安装程序：什么都不发生，退出码 1，连安装日志都不写**；同一个文件复制到 `C:\...\Temp` 或 `D:\` 根目录就正常 | 早先沙箱 ACL 修复在这棵树上留下了 **Low 完整性级别**（`Mandatory Label\Low Mandatory Level`）。Low 完整性的进程写不了中完整性的 `%TEMP%`，Inno 在初始化阶段建不了自己的临时目录就直接退出——所以是"静默失败"，最难查的一种。`bin\` 那些目录当时是 Medium，所以**平时跑程序一直没事**，只有"在仓库根 / `dist\` 里新建的可执行文件"中招 | `icacls <目录> /setintegritylevel Medium /T /C`（实测 2355 个对象、0 失败）。判断方法：`icacls <文件> \| findstr "Mandatory Label"`——**没有这一行就是 Medium（正常）** |
| `.ps1` 不执行 / 中文乱码 | 这个 shell 是 **Windows PowerShell 5.1**：`.ps1` 需要 UTF-8 **BOM**；`Get-Content -Raw` 默认按 **ANSI(GBK)** 解，读 UTF-8 源码会乱码（还可能吃掉后面一个 ASCII 字符） | 脚本一律存成 UTF-8 with BOM；读文件显式写 `-Encoding UTF8`；**永远不要** `Get-Content -Raw \| Set-Content` 改文件（实测把 `.gitignore` 的中文注释写坏过）：要么用编辑工具，要么 `[IO.File]::ReadAllText/AppendAllText` 显式指定编码 |
| 改完 `.ps1` 突然语法报错 | **编辑工具保存时会把 BOM 去掉**（本轮 `pack.ps1`、`ChineseSimplified.isl` 都中过：前者直接语法报错，后者会让安装向导变乱码） | 改完含中文的 `.ps1` / `.isl` 后补 BOM；用 `[Parser]::ParseFile` 做一次语法自检最快 |
| **判断"安装完了没有"又抢跑了一次** | Inno 的安装器把自己复制到 `%TEMP%\is-*.tmp` 再运行，外层进程立刻退出；而 `播放器.exe` 是**复制中途就出现**的（实测那一瞬只有 369 个文件 / 168 MB，看着像装完了） | 判据要等**三个都成立**：`播放器.exe` 版本对 + **卸载项里的版本对** + **文件数与体积稳定**（安装目录最终是 671 个文件 / 250.5 MB）；只看"exe 出现"一定会抢跑 |
| 给原生程序传含中文的参数：中文被**吞掉** | PowerShell 5.1 用 ANSI 代码页编组原生命令行参数。实测 `gh release create … dist\全能本地播放器-1.0.1-安装程序.exe` 上传后的资产名变成 `-1.0.1-.exe` | 传之前把文件复制成 **ASCII 名**（`local-player-1.0.1-setup.exe`）；需要保留中文就走 `[IO.File]` 或 REST API，别走命令行参数 |
